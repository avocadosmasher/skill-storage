## 무엇을 하나

`gated-tdd`는 작업을 작은 단위로 나누고, 단위마다 테스트를 먼저 쓰고(Red), 통과시키고(Green), 정리한 뒤 커밋하는 개발 절차입니다. 사용자는 모든 단위를 승인하지 않습니다. 두 가지만 판정합니다.

- **결정**: AI가 대신 정할 수 없는 것. 합리적인 안이 여럿이라 의도에 달린 선택, 계획·스펙·테스트 기대값의 변경, 스키마·인증·개인정보·비용·배포처럼 되돌리기 어려운 것.
- **확인**: 사용자 흐름 하나를 처음부터 끝까지 직접 해볼 수 있게 된 기능 묶음. 볼 것이 없는 단위마다 확인을 요청하지 않습니다.

나머지는 묻지 않고 진행하고, 무엇을 왜 자동으로 진행했는지 기록과 함께 다음 정지 보고 맨 위에 모아 알립니다. main 병합은 사용자가 PR로 고릅니다.

어느 단위가 결정이고 어디가 확인 지점인지는 계획 단계에서 에이전트가 제안하고 사용자가 확정합니다. 실행 중에 에이전트는 등급을 올리기만 할 수 있습니다.

기능마다 계획보다 요구가 먼저입니다. 에이전트가 이번 기능이 시스템의 동작을 어떻게 바꾸는지를 요구와 구체적인 시나리오로 써서 판정을 받고, 그 시나리오가 그대로 먼저 쓰는 실패 테스트가 됩니다. 요청이 분명하면 몇 줄로 끝나고, 모호하면 대화로 꺼낸 뒤 씁니다. 기능을 마치면 그 요구를 영역별 동작 명세(`docs/behavior/`)에 합칩니다. 그래서 "지금 장바구니는 어떻게 동작하지?"를 테스트 코드가 아니라 읽을 수 있는 문서로 확인할 수 있고, 시나리오마다 그것을 검증하는 테스트가 적혀 있습니다.

제품이 아직 없으면(빈 저장소) 제품 명세가 먼저입니다. 목적, 성공 기준, 하지 않을 것, 만들 기능과 순서(기능 지도)를 합의하기 전에는 프로젝트를 만들거나 의존성을 설치하지 않습니다. 첫 기능은 가장 얇은 사용자 흐름 하나를 빌드, 테스트, 실행, CI까지 끝에서 끝까지 이어 놓는 골격이고, 그 흐름을 직접 해보는 것이 첫 확인 지점입니다.

말로만 하는 약속이 아닙니다. 스킬에 들어 있는 스크립트와 git 훅을 설치하면, 보호 대상 변경(마이그레이션, 의존성, 비밀값, 인프라, 기존 테스트의 기대값 변경이나 skip, 게이트 자체)은 판정 기록 없이 커밋되지 않고, main으로의 직접 push는 막힙니다(블로그 글처럼 따로 지정한 콘텐츠 폴더만 바꾸는 push는 예외). 커밋 직후에는 컨텍스트와 사용 한도가 임계치를 넘었는지 알려 주어, 에이전트가 STATUS.md에 인계를 남기고 새 세션으로 넘어가게 합니다.

저장소에 남는 것:

- `STATUS.md`: 지금 상태(작업 브랜치, 판정 대기, 확인 대기, 다음 할 일, 자동 진행 내역). 세션은 이 파일 하나로 시작합니다.
- `docs/spec/`: 제품 명세(`product.md`, 기능 지도 포함)와 진행 중인 기능 요구(`<기능 ID>.md`)
- `docs/behavior/`: 영역별 현재 동작. 끝난 기능의 요구가 합쳐지며 자랍니다
- `docs/plan/`, `docs/decision/`, `docs/log/`, `docs/guide/`, `docs/archive/`: 계획(게이트·확인 지점 포함), 결정 근거, 작업 이력, 운영 안내, 끝난 단계
- `AGENTS.md`: 이 저장소가 gated-tdd를 채택했다는 선언과 테스트 명령 같은 저장소 값. 절차 자체는 옮겨 적지 않고, 다음 세션의 에이전트가 이 선언을 보고 스킬을 불러옵니다
- `scripts/manual-review.mjs`, `scripts/budget.mjs`, `scripts/log-new.mjs`, `.githooks/`, `.gated-tdd.json`

## 언제 쓰나

AI에게 개발을 맡기면서도 자기가 만드는 서비스를 계속 이해하고 싶을 때, 에이전트가 "다 됐다"고 했는데 열어 보면 의도와 다른 일이 반복될 때 씁니다.

이 스킬은 model-invoked지만 **사용자가 적용을 요청하거나 저장소 규칙이 이 절차를 채택했을 때만** 동작하도록 description을 좁혀 두었습니다. 평범한 기능 요청이나 `STATUS.md` 파일이 있다는 이유만으로는 켜지지 않습니다.

처음 쓰는 저장소에서는 "1. 도입" 절차로 위 파일들과 훅을 설치합니다. 기존 규칙과 훅이 있으면 덮어쓰지 않고 합칩니다.

빈 저장소에서 처음 시작하는 프로젝트에도, 이미 있는 제품에 기능을 더할 때도 씁니다. 에이전트가 세션을 시작할 때 "제품이 있는가"로 작업 유형을 고르고, 고른 유형과 근거를 첫 보고에 밝힙니다. 이미 있는 제품에 도입해도 기존 시스템 전체를 문서로 옮기지 않습니다. 동작 명세는 실제로 바꾼 영역에서만 채워집니다.

오타, 작은 버그, 문구 변경 같은 작은 수정은 요구 문서와 계획 없이 커밋 하나로 처리합니다. 조건은 셋입니다. 요청만으로 무엇을 할지 분명해야 하고, 커밋 하나로 끝나야 하며, 기존 합의나 권한·데이터·의존성처럼 되돌리기 어려운 것을 건드리지 않아야 합니다. 에이전트가 시작할 때 "작은 수정으로 처리함"이라고 알리고, 버그면 재현부터 합니다. 화면이나 문구처럼 사람이 봐야 하는 수정은 고친 뒤 PR을 열고 확인을 한 번 받습니다. PR에 미리보기 주소가 생기는 저장소라면 그 주소로 확인하면 됩니다. 작업 중에 커밋이 더 필요해지거나 정할 것이 생기면 멈추고 알린 뒤 정식 절차로 올립니다. 작업하다 발견한 다른 문제는 고치지 않고 적어 두었다가 따로 할지 묻습니다.

맞지 않는 경우: 사람이 볼 것도 정할 것도 없는 스크립트 작업. 작은 수정이 아닌 버그 수정이나 리팩터링에는 아직 전용 절차가 없어 기능 개발과 같은 절차를 탑니다(동작을 바꾸지 않는 리팩터링과 의존성 작업은 요구를 생략합니다).

Claude Code, Codex 등 셸로 `git commit`을 실행하는 에이전트라면 같은 방식으로 동작합니다. 예산 신호의 정확한 컨텍스트 수치는 도구별 어댑터가 있어야 들어오고, 없으면 이번 세션에서 끝낸 단위 수로 판단합니다.

## Claude Code에서 정확한 예산 수치 받기 (선택 설치)

예산 신호는 기본으로 "이번 세션에서 끝낸 단위 수"로 판단합니다. 단위 크기는 제각각이라 실제 컨텍스트 소모와 어긋날 수 있습니다. Claude Code에서는 mod `gated-tdd-budget`을 설치하면 실제 컨텍스트 사용률과 사용 한도(Pro·Max 구독의 5시간·7일 한도)로 판단합니다.

```bash
claude plugin marketplace add avocadosmasher/skill-storage   # 이미 추가했으면 생략
claude plugin install gated-tdd-budget@avocadosmasher
```

설치 후 Claude Code를 다시 시작하거나 `/reload-plugins`를 실행합니다. 동작은 이렇습니다.

1. 에이전트가 `git commit`을 실행하려 하면, 실행 직전에 mod가 세션 사용량을 읽어 `.git/gated-tdd-budget.json`에 씁니다.
2. 커밋 직후 `post-commit` 훅의 `budget.mjs`가 그 파일을 읽어 임계치를 넘었을 때만 `[예산]` 줄을 출력합니다.

mod는 스킬보다 넓은 권한으로 동작하므로 [코드](../../mods/gated-tdd-budget/)를 확인하고 설치하세요. 세션 사용량을 읽고, 작업 폴더에서 위로 `.git`을 찾고, 그 안의 파일 하나만 씁니다. 커밋 명령을 바꾸거나 막지 않으며, 어떤 이유로 실패해도 커밋은 그대로 실행되고 단위 수 기준으로 돌아갑니다. `cd 다른-저장소 && git commit`처럼 작업 폴더 밖 저장소에 커밋하면 그 커밋에는 수치가 들어가지 않습니다.

## 시각 결정은 캡처 비교가 먼저

배치, 색, 모양처럼 말로 판단하기 어려운 결정은 코드를 고치기 전에 후보를 캡처해 비교합니다. [`capture-compare`](./capture-compare.md)가 설치되어 있으면 그 절차를 쓰고, 없으면 에이전트가 같은 조건에서 직접 캡처합니다.

보고에서 구조나 흐름을 설명해야 하면 [`archify`](./archify.md)가 설치되어 있을 때 다이어그램 파일을 만들고, 없으면 코드 블록 안에 화살표로 간단한 흐름을 그립니다.

## 자주 묻는 질문

**왜 모든 단위를 승인하지 않나요?**
이전 버전은 단위마다 멈춰 판정을 받았습니다. 승인이 잦아지면 내용을 보지 않고 넘기게 되고, 그러면 이해도 발견도 일어나지 않습니다. 그래서 사람만 할 수 있는 결정과, 직접 해볼 것이 있는 확인으로 좁혔습니다.

**AI가 결론만 보여 주고 무엇을 가정했는지 알려 주지 않으면요?**
보고는 마지막 보고 이후의 대화를 보지 않은 사용자가 읽는다고 가정하고 씁니다. 결정 보고에는 "내가 이해한 전제"가 항목마다 확인됨/추정 표시와 함께 들어갑니다. 틀린 줄만 짚어 주면 됩니다. 결론만 잘라 읽어도 판정할 수 있어야 하고, 짧게 쓰는 것보다 판단 재료가 우선합니다.

**"두괄식·개조식"을 AI마다 다르게 이해하지 않나요?**
그래서 라벨이 아니라 확인할 수 있는 규칙으로 정했습니다. 결론은 1~3개 bullet(끝난 일, 필요한 판정, 판정에 영향을 주는 전제), 줄 끝은 명사형(`~함`, `~예정`, `~필요`, `~추정`)으로 맺되 주어·대상·수치·시제는 지우지 않습니다. 판정 요청과 질문은 예외이고, 운영가이드와 최종 보고서 본문은 평서문으로 씁니다.

**자동으로 진행한 단위가 마음에 안 들면요?**
정지 보고 맨 위의 자동 진행 내역에서 그 ID를 말하면 됩니다. 단위마다 커밋이 따로 남아 있어 그 단위만 다시 열 수 있습니다.

**확인 지점에서 확인하지 않고 세션을 끄면요?**
다음 세션은 그 확인부터 요청하고, 확인 전에는 다음 기능 묶음으로 넘어가지 않습니다.

**계획에서 "Postgres를 쓴다"고 정했는데, 라이브러리를 설치할 때 또 묻나요?**
묻지 않습니다. 계획의 작업 표에는 행마다 어떤 보호 대상을 어떻게 바꿀지(`package.json`에 `pg` 추가, 기존 테스트의 기대값 변경 등)가 적혀 있고, 계획을 통과시키면 그 내용까지 판정한 것으로 봅니다. 실제 변경이 적힌 범위 안이면 에이전트가 계획 판정으로 커밋하고 다음 보고의 자동 진행 내역에 근거와 함께 알립니다. 적히지 않은 패키지가 더해지는 것처럼 범위를 넘으면 그때는 멈추고 묻습니다. 실제 내용을 직접 보고 싶은 작업은 계획에서 그 행을 "결정"으로 정하면 됩니다.

**블로그 글처럼 main에 바로 올리던 것도 PR을 거쳐야 하나요?**
아닙니다. 도입할 때 에이전트가 그런 경로가 있는지 보고, `.gated-tdd.json`의 `directPush`에 글 폴더(예: `content/posts/**`)를 넣을지 묻습니다. 넣으면 그 폴더만 바꾸는 push는 지금처럼 main으로 바로 올라갑니다. 코드나 장치 파일이 섞이면 막힙니다.

**Vercel처럼 main을 직접 가져가 배포하는 곳은 어떻게 하나요?**
배포 방식은 바꾸지 않습니다. 이 스킬이 지키려는 것은 "PR에서 테스트를 통과한 코드만 배포된다"입니다. 개발 변경은 PR로만 main에 들어가므로, 에이전트가 PR 보고에 CI 결과를 붙이고 사용자는 CI 통과를 보고 병합합니다. 추가 비용이 드는 설정은 필요 없습니다. GitHub 브랜치 보호(PR 테스트 통과를 병합 조건으로 거는 설정)는 무료로 쓸 수 있을 때(공개 저장소 등)만 선택 사항입니다. 블로그 글 예외(`directPush`)와 함께 켜면 GitHub가 main 직접 push를 거절하므로 본인을 우회 허용에 넣어야 합니다. PR마다 생기는 미리보기 주소는 확인 지점에서 직접 해볼 곳으로 씁니다.

**판정을 받은 뒤 파일을 조금 고치면 어떻게 되나요?**
보호 대상 변경이라면 훅이 커밋을 막습니다. 판정은 그 시점의 스테이징 트리에 대한 것이므로 다시 판정받아야 합니다. 계획에 적은 범위 안의 변경이면 위처럼 계획 판정으로 커밋합니다.

**`--no-verify`로 훅을 우회하면요?**
스킬이 금지합니다. 훅 비활성화, 승인 파일 조작, 사용자 대신 "통과" 작성, main 직접 push도 마찬가지입니다. 훅은 대화를 읽지 못하므로, 실제로 사용자가 판정했는지 확인하는 것은 에이전트의 책임입니다.

## 잘 되고 있다는 신호

- 멈출 때마다 사용자가 정하거나 직접 해볼 것이 있습니다. 볼 것 없는 확인 요청이 없습니다.
- 정지 보고의 자동 진행 내역만 읽어도 그사이 무엇이 왜 진행됐는지 압니다.
- 결론만 읽어도 판정할 수 있고, AI가 잘못 이해한 부분은 "내가 이해한 전제"에서 바로 보입니다.
- 새 세션이 `STATUS.md` 하나만 읽고 이어서 작업합니다. 확인 대기가 있으면 그것부터 묻습니다.
- 컨텍스트가 차기 전에 에이전트가 스스로 인계를 남기고 멈춥니다.

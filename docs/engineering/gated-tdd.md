## 무엇을 하나

`gated-tdd`는 작업을 **사람이 판정할 수 있는 작은 단위**로 나누고, 단위마다 테스트를 먼저 쓰고(Red), 통과시키고(Green), 정리한 뒤, **사용자가 직접 확인하고 "통과"라고 말해야만** 커밋하는 개발 절차입니다.

에이전트는 구현, 자동 검사, 작업 기록을 맡습니다. 사용자는 화면과 실제 동작처럼 사람이 봐야 아는 것만 판정합니다. 단위 하나가 끝날 때마다 에이전트는 수동 테스트 가이드(준비, 조작과 예상 결과, 자동 검사 결과)를 내놓고 멈춥니다.

이 규칙은 말로만 하는 약속이 아닙니다. 스킬에 들어 있는 `manual-review.mjs`와 git 훅(`pre-commit`, `pre-push`)을 저장소에 설치하면, 승인 기록 없이 커밋하거나 승인 뒤에 스테이징 내용이 바뀐 경우 git이 막습니다.

저장소에 남는 것:

- `STATUS.md`: 지금 상태(작업 브랜치, 마지막 통과, 판정 대기, 다음 할 일). 세션은 이 파일 하나로 시작합니다.
- `docs/plan/`, `docs/decision/`, `docs/log/`, `docs/guide/`: 계획, 결정 근거, 작업 이력(항목당 파일 하나), 운영 안내
- `scripts/manual-review.mjs`, `scripts/log-new.mjs`, `.githooks/`

## 언제 쓰나

에이전트가 "다 됐다"고 했는데 막상 열어 보면 안 되는 일이 반복될 때, 또는 화면과 동작이 중요한 기능을 여러 세션에 걸쳐 만들 때 씁니다.

이 스킬은 model-invoked지만 **사용자가 적용을 요청하거나 저장소 규칙이 이 절차를 채택했을 때만** 동작하도록 description을 좁혀 두었습니다. 평범한 기능 요청이나 `STATUS.md` 파일이 있다는 이유만으로는 켜지지 않습니다.

처음 쓰는 저장소에서는 "1. 도입" 절차로 위 파일들과 훅을 설치합니다. 기존 규칙과 훅이 있으면 덮어쓰지 않고 합칩니다.

맞지 않는 경우: 한 번에 끝나는 작은 수정, 사람이 볼 것이 전혀 없는 스크립트 작업. 이런 일에 저장소 전체 절차를 도입하지 마세요.

## 시각 결정은 캡처 비교가 먼저

배치, 색, 모양처럼 말로 판단하기 어려운 결정은 코드를 고치기 전에 후보를 캡처해 비교합니다. [`capture-compare`](./capture-compare.md)가 설치되어 있으면 그 절차를 씁니다. 고른 안을 반영하는 작업도 같은 Red, Green, 판정 사이클을 거칩니다.

## 자주 묻는 질문

**자동 테스트가 다 통과했는데 왜 사람이 또 확인해야 하나요?**
자동 테스트는 미리 정한 계약만 확인합니다. 배치가 어색한지, 문구가 맞는지, 실제 앱에서 눌러 보면 자연스러운지는 사람이 봐야 압니다. 대신 에이전트는 사람이 볼 것이 없는 변경이면 그렇다고 밝히고 판정만 요청합니다. `git diff` 확인이나 테스트 실행 같은 일은 사용자에게 시키지 않습니다.

**승인한 뒤에 파일을 조금 고치면 어떻게 되나요?**
훅이 커밋을 막습니다. 승인은 그 시점의 스테이징 트리에 대한 것이므로, 바뀐 내용은 다시 판정받아야 합니다.

**`--no-verify`로 훅을 우회하면요?**
스킬이 금지합니다. 훅 비활성화, 승인 파일 조작, 사용자 대신 "통과" 작성도 마찬가지입니다. 훅은 대화를 읽지 못하므로, 실제로 사용자가 판정했는지 확인하는 것은 에이전트의 책임으로 남습니다.

**병합 커밋이나 여러 커밋을 한 번에 push할 수 있나요?**
들어 있는 예제 훅은 승인받은 커밋 하나의 트리와 부모만 확인합니다. 여러 커밋을 묶어 push하려면 승인 방식을 따로 설계해야 합니다.

## 잘 되고 있다는 신호

- 에이전트가 단위 하나를 끝낼 때마다 멈추고, 다음 단위로 넘어가지 않습니다.
- 수동 테스트 가이드에 사람이 봐야 하는 것만 있습니다.
- 새 세션이 `STATUS.md` 하나만 읽고 이어서 작업합니다.
- `docs/log/INDEX.md`의 한 줄만 읽어도 무엇이 문제였고 어떻게 정했는지 알 수 있습니다.

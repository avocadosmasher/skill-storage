# 005. 전체 구성을 먼저 보여 주고 하네스의 설계 이유와 흐름을 설명

- 날짜: 2026-11-03
- 상태: 채택
- 반영: feat/writing-visual-overviews, 미배포

## 배경

블로그 회고의 협업 환경에서 코딩 AI는 표로 보여 주면서 Herdr와 Git worktree는 문단으로만 설명해 전체 구성이 한눈에 들어오지 않았다. 사용자는 먼저 표 안에 전체 구성을 표현한 뒤 설명을 이어 달라고 요청했고, 공개 범위 안에서 하네스의 폴더 구성·설계 이유·실제 운영을 더 집중해 풀어 달라고 했다. 구조·흐름도는 필요하면 archify를 사용해도 된다고 했다.

## 선택지

- 기존 문단에 설명만 추가: 근거는 늘지만 전체 구성의 가시성 문제를 해결하지 못함
- 모든 절에 표와 다이어그램을 의무화: 중복과 길이가 늘고 자연스러운 글의 흐름을 해칠 수 있음
- 읽기 목적에 맞는 요약 자료를 먼저 두고 설계 이유와 경험을 본문에서 연결: 사용자의 요구를 충족하며 다른 종류의 글에도 적용할 수 있어 채택

## 결정

- 여러 구성 요소를 소개할 때는 중요한 보조 도구와 연결 역할까지 같은 전체 구성 자료에 포함한다.
- 역할·대응은 표, 폴더 계층은 트리, 복잡한 분기·병렬 관계는 도식처럼 목적에 맞는 자료를 고른다. archify는 필요한 경우 사용하며 모든 글의 필수 의존성으로 만들지 않는다.
- 하네스 설명은 도구 목록에서 끝내지 않고 입력·보존·정리·실행·검증의 연결과 폴더를 나눈 이유를 근거로 설명한다.
- 실제 구성과 계획·미실행 개선안을 구분한다. 공개용 구조에서 생략하거나 재구성한 부분을 밝히고 비공개 원문·식별자를 옮기지 않는다.
- 상세 기준은 composition.md에 두고 SKILL의 구성안·전달 전 검토, 사용자용 설명에서 연결한다. 004의 재사용할 교정을 스킬 자체에 편입하는 원칙을 적용한다.

## 버린 것과 미룬 것

- 특정 표의 열 개수, 모든 절의 그림 수, 다이어그램의 모양을 공통 규칙으로 고정하지 않는다.
- 교정마다 새 선호 파일을 만들거나 별도 시각 강제 엔진을 추가하지 않는다.

## 다시 볼 신호

- 표에 주 도구만 있고 핵심 연결 요소는 여전히 문단에 흩어진 사례
- 요약 자료 뒤에서 같은 내용을 길게 되풀이하거나 구조를 꾸미려다 사실을 바꾼 사례
- 공개용 표·트리에 원문이나 민감한 조건이 포함된 사례

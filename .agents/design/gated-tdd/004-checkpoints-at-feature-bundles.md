# 004. 확인 지점은 직접 해볼 수 있는 기능 묶음에 둔다

- 날짜: 2026-10-14
- 상태: 채택
- 반영: skill-storage 1.5.0

## 배경

확인 게이트(④)를 단위마다 열면 볼 것이 없는 확인, 즉 도장 찍기가 생긴다. 사용자는 이것을 "가장 현실적인 문제"로 꼽았다. 처음 제안은 "자동 단위 5개 이내마다 확인 지점 하나" 같은 고정 상한이었다.

## 선택지

1. **고정 개수 상한 (자동 단위 N개마다).**
   - 단점: 단위 크기와 무관하게 끊겨, 볼 것이 없을 때도 확인을 요청한다.
2. **"단위가 많아지면 간격을 크게" (사용자 제안 중 하나).**
   - 단점: 늦게 발견했을 때의 비용은 "확인 안 된 것 위에 쌓은 양"에 비례하고 전체 단위 수와는 상관이 없다. 계획이 클수록 미확인 작업이 더 쌓여 손해가 커진다.
   - 맞는 부분: 큰 계획에는 해볼 것이 없는 내부 단위가 많다. 이것은 아래 기준 1이 처리한다.
3. **기능 묶음과 의존 토대를 경계로 삼는다 (사용자 제안 중 하나).** (채택)
   - 사용자의 말: 여러 세부 기능이라도 하나의 비즈니스 로직을 위한 것이면 결국 하나로 반영된다.

## 결정

계획 단계에서 AI가 제안하고 사용자가 확정한다([002](./002-three-gates-and-ratchet.md)).

1. **해볼 수 있나**: 사용자 흐름 하나를 처음부터 끝까지 직접 해볼 수 있게 된 행에 둔다. 그 전에는 확인할 것이 없다.
2. **토대인가**: 뒤의 여러 행이 기대는 행(예: 데이터 모델이 처음 화면에 드러나는 행)이 해볼 수 있는 상태라면 그 직후로 앞당긴다.
3. **얼마나 불확실한가**: 요구가 모호하거나 처음 다루는 영역이면 짧게, 익숙하고 스펙이 분명하면 길게.

계획의 순서가 간격을 정하므로, 계획은 **수직 슬라이스**(기능 하나를 데이터부터 화면까지 관통) 순서로 짠다. 층별 순서(DB 전부, API 전부, UI 전부)는 첫 확인 지점을 맨 끝으로 밀어낸다.

실행 중 조정:

- AI는 확인 지점을 **앞당기기만** 한다(래칫). 예: 확인에서 수정이 크게 나왔거나, 판정 질문 ②에 못 미치는 작은 해석이 쌓였을 때.
- **묶기 제안은 하지 않는다.** 사용자가 필요하면 중간중간 피드백으로 조정한다(사용자 결정).

## 버린 것과 미룬 것

- 연속 통과하면 다음 구간을 묶자고 제안하는 안(TCP 혼잡 제어처럼 천천히 넓히기)은 사용자가 원하지 않아 버렸다. 제안 자체가 또 하나의 질문이기 때문이다.
- 확인 결과(통과, 수정 n건)를 계획의 마일스톤 표에 남기는 것은 유지한다. 나중에 간격을 조정할 근거가 된다.

## 다시 볼 신호

- 확인 지점에서 수정이 자주 나오고 그 원인이 여러 묶음 전의 단위다. (간격이 너무 넓음)
- 사용자가 확인 지점 사이에 스스로 끼어드는 일이 잦다. (간격이 사용자 기대보다 넓음)

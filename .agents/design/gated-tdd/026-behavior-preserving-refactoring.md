# 026. 큰 리팩터링은 목표 구조를 계획에서 한 번 받고, 테스트의 기계적 수정은 종류로 판정한다

- 날짜: 2026-11-03
- 상태: 채택
- 반영: skill-storage 다음 배포
- 바꾼 것: [014](./014-plan-approval-covers-protected-changes.md)의 "보호 대상 변경 칸에는 무엇을 어떻게 바꾸는지까지 적는다"(현재 원칙 1)에, 테스트의 기계적 수정만 종류로 적는 예외를 둠

## 배경

[011](./011-maintenance-backlog.md) M4다. 지금까지 리팩터링은 사이클 안의 정리(Refactor 단계)와 "동작을 보존하는 유지보수는 요구를 생략하고 계획부터"라는 한 줄뿐이었다.

예시 상황: [025](./025-characterization-tests-for-untested-code.md)에서 고정 테스트를 붙인 800줄짜리 `calcOrder()`를 `pricing/`, `coupon/`, `shipping/` 세 모듈로 나눈다.
사용자 요청은 "주문 계산 코드가 너무 커서 손대기 무서워. 정리해 줘."다.

막히는 곳은 두 가지였다.

1. 파일을 옮기면 테스트의 `import` 줄도 바뀐다. 훅은 기대값이 그대로여도 기존 테스트의 줄이 바뀌면 막는다.
   임시 저장소에서 확인한 결과는 이렇다. 이름만 바꾼 테스트 파일은 통과했고, import 한 줄을 고치면 걸렸다(`manual-review.mjs`가 `-` 줄을 찾음). 그래서 파일 하나를 옮길 때마다 결정으로 멈췄다.
2. 완료 기준이 "기존 테스트가 모두 그대로 통과"뿐이었다. 테스트가 없는 곳은 동작이 바뀌어도 몰랐다. 이 부분은 025의 고정 테스트로 채워졌다.

참고: Martin Fowler의 리팩터링 정의(관찰 가능한 동작을 바꾸지 않는 구조 변경)와 "만들기 쉽게 고친 뒤 쉬운 변경을 한다"(Kent Beck),
mattpocock `improve-codebase-architecture`의 "자주 바뀌는 곳부터" 후보 찾기.

## 선택지와 결정

사용자는 다섯 가지 모두 추천대로 골랐다("추천대로 해도 될듯?").

### 1. 리팩터링을 어떻게 시작할까

| 안 | 내용 |
| --- | --- |
| **계획 보고 한 번 (채택)** | 지금 구조와 목표 구조를 나란히 보여 주고 단계 순서와 고칠 테스트 목록을 넣어 `PLAN-<이름>`으로 받음 |
| 묻지 않고 진행 | 구조를 사용자 모르게 정하게 됨 |

목표 구조는 합리적인 안이 여럿인 선택(판정 질문 ①)이라 한 번은 묻는다.

### 2. 리팩터링 때문에 테스트를 고쳐야 할 때

| 안 | 내용 |
| --- | --- |
| **기계적 수정을 종류로 계획 칸에 적어 한 번에 판정 (채택)** | import 경로, 바뀐 이름, mock 경로, 테스트 파일 이동. 커밋마다 에이전트가 바뀐 줄을 그 종류와 대조 |
| 훅이 스스로 알아봄 | 언어마다 문법이 달라 오판 위험, 스크립트 변경이 큼 |
| 고칠 때마다 결정 | 파일 하나 옮길 때마다 멈춤 |
| 옛 경로에 다시 내보내는 파일을 남김 | 임시 코드가 생기고 마지막에 한 번은 결정 |

고치기 전에 사용자에게 원칙 1과 부딪힌다고 알렸다. 원칙 1은 칸에 "무엇을 어떻게 바꾸는지까지" 적게 하는데, 이 안은 개별 변경 대신 종류를 허용한다.
그래서 종류를 기대값·단언·입력을 건드리지 않는 네 가지로 좁혔다. 대조는 줄 단위로 하고, 한 줄이라도 다르면 결정이다.
내부 구조를 직접 검사하는 테스트는 기계적으로 살릴 수 없으므로, 바깥 경계의 고정 테스트로 대신한 뒤 테스트 이름마다 지운다고 적는다.

### 3. 완료 기준

| 안 | 내용 |
| --- | --- |
| **기존 테스트 통과 + 바깥 경계 고정 테스트의 값 그대로 (채택)** | 고정 테스트 값이 바뀌면 리팩터링이 아니라 동작 변경 |
| 커버리지 기준 추가 | 커버리지 도구 설치(의존성)와 숫자 맞추기용 테스트가 생김 |
| 기존 테스트 통과만 | 테스트 없는 곳이 비어 있음 |

### 4. 사용자가 바뀐 구조를 따라가게 하는 법

설계 의도 1("결정할 재료를 사용자 머릿속에 남긴다") 때문에 따로 정했다.

| 안 | 내용 |
| --- | --- |
| **계획에 전후 구조, 완료 보고에 최종 구조와 계획 대비 달라진 점 (채택)** | 멈춤은 계획 한 번 |
| 단계마다 구조 확인 지점 | 자주 멈춤. 사람만 볼 수 있는 것(④)도 아님 |
| PR 리뷰에서만 | 큰 diff를 읽어야 함 |

### 5. 대상이 정해지지 않은 요청

| 안 | 내용 |
| --- | --- |
| **후보 3~5개를 근거와 함께 보여 주고 고르게 함 (채택)** | 근거는 최근 자주 바뀐 파일, 크기와 복잡도, 곧 할 작업과의 관련. 판정이 아닌 질문 |
| 에이전트가 하나 골라 계획 | 사용자 의도와 어긋날 수 있음 |
| 대상을 말한 것만 | "정리해 줘"에 답할 수 없음 |

## AI가 정한 세부 (사용자에게 알림, 이의 없음)

- 브랜치는 `refactor/<이름>`, 이름은 계획 ID로도 쓴다.
- 기능 개발 계획 안의 리팩터링 행은 지금처럼 허용한다. 동작을 바꾸는 행보다 앞에 두고 같은 테스트 규칙을 적용한다.
- 커밋 하나로 끝나고 기존 테스트를 고치지 않는 정리는 작은 수정이다(앞머리 `refactor:`).
- 의존성 업데이트는 M5에서 따로 다룬다. 작업 유형 표에서 리팩터링 행을 분리했다.
- 상세는 `references/refactoring.md`에 두고 SKILL.md 0절·2절·3절·7절에서 가리킨다.
- 테스트가 실패하면 기대값을 고쳐 맞추지 않고 그 행을 되돌린다. 화면 코드를 옮기면 전후 캡처를 비교한다.
- 동작 명세는 고치지 않되, 시나리오에 적힌 테스트 위치가 옮겨졌으면 새 위치로 고친다.

## 시뮬레이션과 보완

Claude Code 서브에이전트, Codex(read-only), Antigravity(Gemini 4 Argon High, plan 모드)에 같은 상황 셋을 주고 절차를 끝까지 따라가게 했다.

1. 고정 테스트가 붙은 800줄 `calcOrder()`를 세 모듈로 나눔 (mock 경로, 내부 함수 spy 테스트, 동작 명세의 테스트 참조, 세 번째 행에서 반올림 순서가 바뀌어 고정 테스트 실패, 마지막 행에 실수로 단언 한 줄을 더함)
2. "코드 좀 정리해 줘" (Django, 후보 중 views.py와 영수증 템플릿을 둘 다 고름, `timezone.now()`)
3. 기능 계획 안의 리팩터링 행, 그리고 다른 날 이름 바꾸기 요청

| 빈 곳 | 찾은 도구 | 보완 |

다섯 가지 결정을 바꾼 보완은 없다.

## 다시 볼 신호

- 기계적 수정이라고 대조한 줄에 기대값 변경이 섞여 들어간 사례가 나온다.
- 리팩터링 계획 보고가 형식적으로 통과되고, 사용자가 완료 뒤 구조를 모른다.
- 후보 고르기 질문이 매번 같은 파일을 가리켜 의미가 없어진다.

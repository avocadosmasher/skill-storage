# 025. 테스트 없는 코드는 고치기 전에 영향 경로의 지금 결과를 고정 테스트로 붙잡는다

- 날짜: 2026-11-03
- 상태: 채택
- 반영: skill-storage 다음 배포
- 바꾼 것: SKILL.md 3절 "실패 테스트를 먼저 쓴다"에 틈 만들기 예외 하나를 둠

## 배경

[011](./011-maintenance-backlog.md) M3다. 이 스킬의 모든 경로는 실패 테스트(Red)에서 시작한다. 그런데 테스트가 없는 오래된 코드에서는 세 곳에서 막혔다.

1. 새 기능의 테스트는 쓸 수 있어도, 고친 뒤 기존 계산이 그대로인지 알 기준이 없다.
2. DB 조회와 현재 시각이 함수 안에 박혀 있어 테스트에서 부를 수 없다.
3. 제품은 있는데 테스트 도구 자체가 없다. 도입 절차에는 "테스트 도구가 고의 실패 때 0이 아닌 코드로 끝나는지 확인"만 있었다.

참고: Michael Feathers의 characterization test와 seam(테스트를 넣을 틈), golden master(출력 전체 비교).

예시 상황: 테스트가 없는 800줄짜리 `calcOrder()`에 "쿠폰 두 장 같이 쓰기"를 넣는다. 함수 안에서 DB를 직접 조회하고 `new Date()`를 쓴다.

## 용어

사용자와 이야기하며 "고정 테스트"로 부르기로 했다. 맞는 값이 아니라 지금 나오는 값을 기대값으로 적는 테스트다.
사용자가 처음 물은 것: "원래 그러면 고정테스트는 문제가 없는 동작을 기준으로 해야하는거 아니야?"
답: 테스트 없는 코드에서는 무엇이 맞는지 적힌 곳이 없다. AI가 맞는 값을 짐작해 쓰면 요구를 추측으로 정하는 것(판정 질문 ①②)이고, 테스트가 처음부터 빨개져 안전망이 아니라 버그 수정이 된다.
사용자가 정리한 목적: "수정을 의도하지 않은 부분은 고정해놓고 다른 부분을 고쳤을 때 그대로 기존의 결과처럼 나와야 한다." 이 정리를 그대로 채택했다.

## 선택지와 결정

사용자는 다섯 가지 모두 추천대로 골랐다("추천대로 진행").

### 1. 어디까지 고정할까

| 안 | 내용 |
| --- | --- |
| **이번 변경이 영향을 줄 수 있는 경로만 (채택)** | 쿠폰 적용, 합계, 배송비. 포인트 적립처럼 상관없는 곳은 두지 않음 |
| 함수(모듈) 전체 | 기능 하나에 고정 테스트가 수십 개 |
| 고정하지 않고 확인 지점에서 사람이 확인 | 사람이 모든 계산을 다시 해 보기 어려움 |

[012](./012-requirements-for-every-change.md)의 "기존 시스템을 거슬러 문서화하지 않고 변경이 지나간 곳만 채운다"와 같은 원리다.

### 2. 고정하다 이상한 값이 나오면 (합계 -500원)

| 안 | 내용 |
| --- | --- |
| **`의심:` 표시와 함께 그대로 고정, 보고에 적고 고치지 않음 (채택)** | 안전망에 구멍이 없고, 정해진 동작으로 착각하지 않음 |
| 고정하지 않고 빼기 | 그 경로가 바뀌어도 모름 |
| 즉시 멈추고 묻기 | 멈추는 횟수가 늘어남 |
| 하는 김에 고치기 | 그 값에 기대는 곳(외부 정산 등)이 있으면 깨짐 |

사용자는 틀린 값을 기대값으로 굳히는 것을 걱정했다. [024](./024-bugfix-root-cause-path.md) 시뮬레이션의 1원 오차 시나리오에서 기존 테스트가 틀린 값 29,999를 기대값으로 갖고 있던 문제와 같다.
그 사례와 다른 점은 처음부터 이름에 `의심:`을 붙여 정해진 동작이 아니라고 남기는 것이다. 이번 변경과 얽히면 어느 안이든 요구 보고의 열린 질문으로 올린다.

### 3. 고정 테스트를 판정받을까

| 안 | 내용 |
| --- | --- |
| **자동 (채택)** | 고침 커밋 앞에 고정 테스트만 담은 커밋을 따로 두고, 다음 정지 보고에 한 줄로 알림 |
| 목록을 결정으로 받기 | 멈추는 횟수가 하나 늘어남 |

지금 값을 적을 뿐이라 판정 질문 ①~④ 어디에도 해당하지 않는다. 새 테스트 추가는 훅도 막지 않는다.

### 4. 테스트에서 부를 수 없는 코드

| 안 | 내용 |
| --- | --- |
| 바깥에서 고정 | 테스트 도구의 대체 기능(mock, 가짜 시계), API 호출, 테스트 DB, 출력 비교. 코드는 안 건드리지만 느릴 수 있음 |
| 틈 만들기 | 박힌 값을 인자로 받되 기본값은 그대로 두는 것 같은 기계적 수정만 테스트 없이 허용 |
| 매번 묻기 | 자주 멈춤 |
| **바깥에서 먼저, 안 되면 틈 만들기 (채택)** | |

틈 만들기는 "실패 테스트를 먼저 쓴다"보다 코드 수정이 앞선다. 고치기 전에 사용자에게 이 충돌을 알렸고, 사용자는 추천안을 골랐다.
그래서 예외의 범위를 좁게 정했다: 수정 하나에 커밋 하나, 동작 변경과 섞지 않음, 컴파일·타입 검사·기존 테스트 통과, 바로 다음 커밋이 그 틈을 쓰는 고정 테스트.
기계적 수정을 넘으면(로직을 옮기며 바꿈, 여러 파일의 구조 변경) 구조를 고르는 일이라 결정으로 올린다.

### 5. 테스트 도구 자체가 없는 저장소

| 안 | 내용 |
| --- | --- |
| **도입 보고에서 함께 받음 (채택)** | 도입 PR에 설치와 예시 테스트 하나 |
| 첫 기능의 계획 보고에서 받음 | 도입하자마자 첫 작업이 막힘 |

도입 보고는 원래 결정이라 멈추는 횟수가 늘지 않는다. 예시 테스트는 이미 있는 코드 하나의 고정 테스트로 쓴다.

## AI가 정한 세부 (사용자에게 알림, 이의 없음)

- 작은 수정에는 고정 테스트를 요구하지 않는다. 재현 테스트 하나로 지킬 수 없으면 작은 수정이 아니라고 보고 올린다.
- 고정 테스트는 동작 명세에 옮겨 적지 않고, 시나리오의 검증 테스트로도 적지 않는다.
- 고정한 값을 일부러 바꾸면 기존 테스트의 기대값 변경(②)이라 계획이나 대책의 보호 대상 변경 칸에 적는다. 요구가 바꾸는 동작은 처음부터 고정하지 않고 새 기대값으로 실패 테스트를 쓴다.
- 규칙은 새 작업 유형이 아니라 모든 유형에 걸리는 조건이라 `references/characterization.md` 한 파일에 두고 SKILL.md 3절과 각 유형 문서에서 가리킨다. M4(큰 리팩터링)의 완료 기준으로도 쓴다.
- 고정 테스트는 그것이 지키는 행 안에 따로 커밋한다. 행을 더하지 않으므로 실행 중에 필요를 알게 돼도 계획 변경이 아니다.
- 지키는지 확인하려고 고칠 곳의 값을 잠깐 바꿔 고정 테스트가 빨개지는지 본다. 스냅숏 전체 갱신 옵션은 쓰지 않는다.

## 시뮬레이션과 보완

M1처럼 Claude Code 서브에이전트, Codex(read-only), Antigravity(Gemini 4 Argon High, plan 모드)에 같은 상황 셋을 주고 절차를 끝까지 따라가게 했다.

1. 테스트 없는 800줄 `calcOrder()`에 쿠폰 두 장 기능 (DB·현재 시각이 박힘, 영수증 스냅숏 하나, -500원, 쿠폰 한 장의 계산 순서도 바꾸기로 함, 영어 테스트 이름)
2. 테스트 없는 `SettlementService.settle()`의 월말 정산 버그 (`LocalDate.now()`, `new PaymentGatewayClient()`, 부르는 곳 3개 파일)
3. 테스트 도구도 CI도 없는 Flask 도구에 도입하며 오타와 합계 오류를 함께 요청

| 빈 곳 | 찾은 도구 | 보완 |
| --- | --- | --- |
| 버그 재현 테스트를 쓰려면 틈이 먼저 필요한데, 틈 만들기가 행 ID를 전제하고 "고쳐 본 코드는 되돌린다"와 부딪힘 | 셋 다 | 기계적 틈은 버그 보고 전에도 `BUG-<이름>`으로 바로 커밋하고 되돌리지 않음 |
| 실패하는 재현 테스트가 커밋된 뒤의 고정·틈 커밋은 "기존 테스트 통과"를 지킬 수 없음 | Codex, Antigravity | 재현 테스트 하나를 빼고 모두 통과하면 됨 |
| 기계적 수정을 넘는 틈 결정의 판정 ID와 시점이 없음 | 셋 다 | 보고 전이면 결정 목록·"정할 것"에 합치고, 실행 중이나 재현이 막히면 `<행 ID>-틈`·`BUG-<이름>-틈`으로 따로 보고 |
| "바뀌는 동작은 고정하지 않는다"와 "고정한 값을 요구로 바꾼다" 예시가 부딪힘 | 셋 다 | 예시를 "이전 작업에서 고정해 둔 값"으로 좁히고, 쿠폰 한 장 예시를 더함 |
| 요구가 바꾸는 경로 안의 이상한 값을 `의심:`으로 고정할지 뺄지 모름 | 셋 다 | 고정하지 않고 맞는 값을 물음 |
| 실행 중 얽힌 이상한 값의 정지 시점과 판정 ID가 없음 | Antigravity, Claude | 얽히지 않은 고정 테스트까지 커밋하고 Red 전에 `<행 ID>-의심`으로 보고 |
| 스냅숏 보호는 `tests` 패턴에 달려 있고, 판정받은 스냅숏을 갱신하는 법이 없음 | 셋 다 | 패턴 밖이면 우려와 `도입-갱신` 제안, 갱신은 테스트 하나로 좁혀서 |
| 도입 예시 테스트를 어디에 둘지 없어 DB에 묶인 함수를 고르고 도입 PR에 제품 코드가 섞임 | 셋 다 | 바로 부를 수 있는 작은 함수에 두고 제품 코드를 고치지 않음 |
| CI가 없는 제품의 도입에서 "PR에서 테스트를 통과한 코드" 규칙을 지킬 방법이 없음 | 셋 다 | 같은 보고에서 정함. 무료 CI가 있으면 제안, 아니면 PR 보고에 로컬 결과 |
| 도입이 병합되기 전 작은 수정·버그 수정의 브랜치를 main에서 딸지 도입 브랜치에서 딸지 부딪힘 | 셋 다 | 7절의 선행 기능 규칙을 따른다고 적음 |
| 틈이 여럿 필요할 때 "수정 하나에 커밋 하나"와 "바로 다음 커밋이 고정 테스트"가 부딪힘 | Antigravity, Codex | 모두 만든 다음 제품 코드 커밋이 고정 테스트, 사이의 상태 파일 커밋은 허용 |
| mock·가짜 시계처럼 코드를 고치지 않는 길이 없고, Java처럼 기본값 인자가 없는 언어의 기준이 없음 | Claude | 테스트 도구의 대체 기능을 1순위로, 오버로드를 허용하는 수정에 넣음 |
| 결정 행에서 고정 테스트를 보고 전에 커밋해도 되는지 모호함 | Claude | 결정한 내용이 아니라서 먼저 커밋한다고 적음 |
| 고정하지 않는 안을 고른 뒤 남는 위험과 확인 방법이 없음 | Codex | 로그에 `고정 생략`, 확인 지점에서 사람이 확인, 완료 보고의 우려 |
| 이상한 값이 늘 계획 통과 뒤에 드러나 정지가 하나 더 생김 | Claude | 요구·계획을 쓸 때 고정할 경로를 한 번 돌려 봄 |
| 지키는 테스트가 있는지의 기준, 여러 행이 같은 경로를 고칠 때 어느 행에 둘지 | Claude | 갈래마다 봄, 처음 고치는 행 |
| `maintenance.md` 첫머리의 "테스트 없는 코드의 전용 절차는 아직 없다" | Claude, Codex | 고정 테스트를 가리키게 고침 |

반영하지 않은 것: 모든 커밋 메시지 형식 표, 한 요청에 여러 작업이 왔을 때의 순서(이번 변경과 무관), 금전 피해의 별도 기준(버그 수정의 피해 막기 기준으로 충분해 예시만 더함).
다섯 가지 결정을 바꾼 보완은 없다.

## 다시 볼 신호

- 고정 테스트가 너무 많아져 기능 하나보다 고정이 오래 걸린다.
- `의심:` 테스트가 쌓이는데 버그 수정으로 이어지지 않는다.
- 틈 만들기가 기계적 수정이라는 이유로 동작을 바꾼 사례가 나온다.
- 고정 테스트를 동작 명세의 근거로 착각하는 사례가 나온다.

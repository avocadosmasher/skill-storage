# 016. 제품 명세는 첫 기능 요구와 한 보고로 받고, 도입 PR은 먼저 병합한다

- 날짜: 2026-10-19
- 상태: 채택
- 반영: skill-storage 1.7.0

## 배경

두 번째 시뮬레이션에서 에이전트들이 같은 자리에서 서로 다르게 움직였다. 절차가 정하지 않은 곳이 셋 있었다.

1. 제품 명세와 첫 기능 요구를 한 보고로 받을지 두 번 나눠 받을지. 초기 개발은 `SPEC-product` 한 번이었지만, 기존 제품에 처음 제품 명세를 쓰는 경우는 정해져 있지 않았다. 나누면 만들기 전 정지가 하나 는다.
2. 도입 브랜치(`chore/gated-tdd`)를 언제 PR로 올리고 병합할지, 그리고 기능 브랜치를 어디서 딸지.
3. 계획 보고에 판정 ID가 없었다. [014](./014-plan-approval-covers-protected-changes.md) 뒤로는 계획 판정이 커밋 승인의 근거가 되므로 기록할 ID가 필요하다.

사용자는 처음에 이 문제를 "제품 명세 확인 후 기능이 원하는 대로 구현됐는지 확인하는 두 과정"으로 이해했다. 설명을 고쳐, 둘 다 만들기 전의 확인이고 만든 뒤의 확인 지점은 그대로라는 점을 표로 보였다.

## 선택지

### 제품 명세와 첫 기능 요구

1. **한 보고에 두 부분으로 넣고, 판정은 부분마다 받는다.** (채택)
   - 장점: 둘 다 "무엇을 만들지"를 정하는 일이라 같이 볼 때 판단이 쉽다. 정지가 늘지 않는다. 한쪽만 고칠 수 있다.
   - 단점: 보고가 길어진다.
2. **따로 두 번 받는다.**
   - 장점: 보고 하나가 짧다.
   - 단점: 만들기 전 정지가 하나 늘고, 기능 요구 없이 기능 지도만 보면 판단 재료가 모자란다.

부분 판정의 처리: 둘 다 통과면 함께 커밋한다. 기능 요구만 수정이면 제품 명세를 먼저 커밋한다. 제품 명세가 수정이면 기능 요구가 그 위에 서 있으므로 둘 다 고쳐 다시 보고한다.

### 도입 PR

1. **도입이 통과하면 바로 PR을 열어 먼저 병합한다.** (채택)
   - 장점: 도입은 작고 기능과 무관해 리뷰가 쉽다. 이후 기능 브랜치가 main에서 시작한다.
   - 단점: 병합 전에 기능을 시작하면 기능 브랜치가 `chore/gated-tdd`에 기댄다. 기존 규칙(선행이 미병합이면 그 브랜치에서 따고 전제에 씀)으로 처리한다.
2. **첫 기능과 함께 병합한다.**
   - 단점: 첫 PR이 커지고, 장치 변경과 기능 변경이 한 리뷰에 섞인다.

## 결정

두 묶음 모두 1을 고른다. 사용자가 AI 의견("한 보고로 받는 게 맞다", "설치 PR은 먼저 합친다")에 "진행해"로 동의했다.

- `references/requirements.md` 요구 보고: 제품 명세는 함께 시작하는 기능의 요구와 한 보고에 두 부분으로 넣고 부분마다 판정을 받는다.
- `references/init-dev.md` 2단계: `SPEC-product`와 `SPEC-skeleton` 두 부분, `feat/skeleton` 브랜치에 쓴다.
- SKILL.md 1절: 도입 통과 후 바로 push하고 PR을 연다. 7절 브랜치: 제품 명세는 함께 보고하는 기능의 브랜치에, 선행에 도입 포함.
- SKILL.md 2절과 5절: 계획 판정 ID `PLAN-<기능 ID>`.

## 다시 볼 신호

- 제품 명세와 기능 요구를 합친 보고가 길어 사용자가 한쪽을 읽지 않고 통과시킨다.
- 도입 PR이 병합되지 않은 채 기능 브랜치가 여럿 쌓인다.

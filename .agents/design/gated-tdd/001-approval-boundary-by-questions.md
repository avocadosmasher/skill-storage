# 001. 승인 경계는 책임 범주가 아니라 판정 질문 네 개로 가른다

- 날짜: 2026-10-14
- 상태: 채택
- 반영: skill-storage 1.5.0

## 배경

작업 단위마다 승인을 요청하니 피로가 쌓였다. 승인이 필요한 곳과 필요 없는 곳의 경계를 다시 정해야 했다.

사용자의 원래 제안은 책임을 두 영역으로 나누는 것이었다.

- **Responsibility (작업 진행의 책임)**: 코드가 컴파일되고 동작하는가, 스파게티 코드 같은 비효율이 없는가. AI가 잘하는 영역이므로 사용자가 관여하지 않는다.
- **Accountability (결과의 책임)**: Storey의 Triple Debt Model을 빌려 네 갈래로 나눴다.
  - 지식의 책임: 모르고 넘어가면 기술 부채, 인지 부채가 쌓이는 곳. 비즈니스 로직이 생각한 대로인지 확인할 곳.
  - 기능의 책임: 요구사항, 의도, 목적과 달라지는 의도 부채가 쌓이는 곳.
  - 보안의 책임: 개인정보 보호, 외부 공격.
  - 비용의 책임: 돈이나 자원이 드는 경우의 인프라 확인.
- Responsibility는 묻지 않고 진행하고, Accountability는 사용자가 확인·이해·결정한다.

## 선택지

1. **범주 그대로 승인 기준으로 쓴다.**
   - 장점: 직관적이고, 사람이 놓치면 안 되는 곳의 목록으로 좋다.
   - 단점: 결과의 책임은 정의상 전부 사용자에게 있다. 특히 "지식의 책임"은 거의 모든 변경에 해당해서 승인 빈도가 원래대로 돌아온다.
   - 단점: 범주가 겹친다. 스파게티 코드(R)와 기술 부채(A·지식)는 같은 것이다. 보안 안에도 AI가 지킬 위생(파라미터 바인딩)과 사용자가 정할 정책(무엇을 수집하나)이 섞여 있다. AI가 매번 범주를 해석하다 애매하면 묻게 되어 피로가 다시 생긴다.
   - 단점: R 쪽에도 멈춰야 할 곳이 있다. Green이 안 나와 기존 테스트의 기대값을 고치는 것은 동작 문제가 아니라 의도 변경이다.
2. **판정 질문으로 가르고, 범주는 체크리스트로 쓴다.** (채택)
   - 장점: "이 시점의 사용자 판단이 AI가 모르는 정보를 더하는가"를 직접 묻는다. 모든 범주에서 자동 진행과 게이트가 갈린다.
   - 단점: 질문 해석이 AI에게 남는다. 래칫([002](./002-three-gates-and-ratchet.md))과 훅의 하한선으로 보완한다.

## 결정

판정 질문 네 개로 가른다.

| 질문 | 예이면 |
| --- | --- |
| ① 선택: 합리적인 안이 둘 이상이고, 정답이 사용자의 의도·우선순위·제약에 달렸나? | 결정 게이트 |
| ② 합의 변경: 계획·스펙·테스트 기대값·범위를 바꾸거나 모호한 요구를 해석해야 하나? | 결정 게이트 |
| ③ 되돌리기 어려움: 스키마·데이터 삭제, 공개 API 계약, 인증·권한, 개인정보, 비밀값, 비용, 배포인가? | 결정 게이트 |
| ④ 사람만 확인 가능: 화면·문구·사용감, 실제 계정·기기·외부 연동인가? | 확인 게이트 |
| 전부 아니오, 완료 기준을 자동 검사로 증명함 | 자동 진행 (기록과 알림) |

사용자의 R/A 구분은 버리지 않고 두 곳에 남긴다.

- 구도: "AI는 실행(R), 사용자는 결과의 주인(A)". 자동 진행은 RACI의 I(통보)에 해당한다.
- 체크리스트: 계획을 세울 때 지식·기능·보안·비용 네 갈래를 훑어 결정이 숨은 곳을 찾는다.

근거로 삼은 것:

- Storey(2026)는 의도 부채를 "목표·제약·근거가 산출물에 기록되지 않았거나 낡은 상태"로 정의하고, 결정하는 순간에 의도를 남기라고 권한다. 단위마다 승인하는 것으로는 증상만 잡히고, 의도는 실행 가능한 테스트와 결정 기록으로 남겨야 줄어든다.
- 같은 논문은 AI 출력을 거의 검토 없이 받아들이는 상태를 위험으로 꼽는다. 인지 부채는 승인 횟수가 아니라 직접 해보는 경험의 질로 갚는다.
- Anthropic이 Claude Code auto mode를 만들며 공개한 기준(2026-03): 행동의 실제 영향과 사용자가 그 행동을 실제로 허락했는지를 본다. 사용자는 권한 요청의 93%를 승인했고, 잦은 요청은 주의를 떨어뜨렸다. ①②는 "허락", ③은 "영향"에 해당한다.

## 버린 것과 미룬 것

- R 영역을 사람 대신 기계가 확인하는 장치(복잡도·중복 검사, 비밀값·의존성 취약점 스캔)는 저장소마다 도구가 달라 스킬에 고정하지 않았다. 계획의 자동 검사 범위에서 정한다.
- 도구 수준 위험(파일 삭제, 명령 실행)은 에이전트 도구의 권한 기능(Claude Code auto mode 등)이 맡고, 이 스킬은 의미 수준(결정·의도·확인)만 맡는다.

## 다시 볼 신호

- 자동 진행으로 넘긴 단위에서 나중에 의도와 다른 점이 반복해서 발견된다. (질문이 너무 느슨함)
- 결정 게이트가 계획에 없던 사소한 선택으로 자주 멈춘다. (①의 해석이 너무 넓음)

# 012. 요구 정리는 모든 작업 유형의 공통 단계이고, 끝난 기능의 동작은 영역별 동작 명세에 쌓는다

- 날짜: 2026-10-16
- 상태: 채택
- 반영: skill-storage 1.7.0
- 대체: [010](./010-init-dev-spec-and-skeleton.md)

## 배경

[010](./010-init-dev-spec-and-skeleton.md)은 명세를 초기 개발에만 두었다. 초기 개발의 신호는 "빈 저장소, 또는 목표·사용자·성공 기준이 문서로 없는데 기능 여럿"이었다.
새 컨텍스트의 서브 에이전트 셋으로 절차를 시뮬레이션했다([013](./013-simulation-fixes.md)). 그중 "2년 된 블로그에 명세 없이 회원가입·댓글·알림을 더하는" 시나리오가 초기 개발로 분류됐다. 그런데 초기 개발의 골격(프로젝트 생성, 테스트 러너, CI)은 빈 저장소를 전제로 짜여 있어 맞지 않았다.

사용자의 말: "기능 개발이라 하더라도 요구사항 수집하고 기능 명세하고 이런 작업은 원래 개발에서 다 하는 거 아닌가? 조사해서 더 꼼꼼하게 살펴보자."

조사 결과(2026-10-16):

| 방식 | 프로젝트 단위 | 변경 단위 | 크기 조절 |
| --- | --- | --- | --- |
| [GitHub Spec Kit](https://github.github.com/spec-kit/guides/existing-projects.html) | constitution | 기능마다 `spec.md`(결과, 호환 경계) → plan → tasks | 기존 시스템 전체 문서화를 첫 기능으로 삼지 말 것 |
| [Kiro](https://kiro.dev/docs/specs/) | steering | 기능마다 `requirements.md`(사용자 스토리 + EARS 인수 기준), 버그는 `bugfix.md`(현재/기대/바뀌면 안 되는 동작) | 잘 이해된 기능은 게이트 없는 Quick Spec |
| [OpenSpec](https://github.com/Fission-AI/OpenSpec/blob/main/docs/existing-projects.md) | 영역별 `specs/`(현재 동작) | 변경마다 proposal + 델타(ADDED/MODIFIED/REMOVED), 끝나면 영역 명세에 합침 | "바꾸려는 것만 쓴다", 거슬러 채우지 않음 |
| Agile ([Example Mapping](https://xebia.com/blog/example-mapping-steering-the-conversation/)) | 제품 비전 | 스토리마다 규칙·예시·질문, 질문이 풀려야 Ready | 15~30분 대화 |
| [Shape Up](https://www.rubick.com/wiki/process/shape-up) | - | pitch: 문제, appetite, 해법, rabbit holes, no-gos | appetite가 범위를 정함 |
| [Google 디자인 문서](https://www.industrialempathy.com/posts/design-docs-at-google/) | - | 목표/비목표, 설계, 버린 대안 | 모호하지 않으면 쓰지 않음, 점진 개선은 1~3쪽 |

공통점:

1. 요구는 변경마다 정리한다.
2. 프로젝트 층(오래 가는 맥락)과 변경 층(이번에 바꿀 것)을 나눈다.
3. 기존 시스템을 거슬러 문서화하지 않는다.
4. 분량은 모호함에 비례한다.

## 선택지와 결정

사용자와 네 가지를 정했다.

1. **요구 정리의 위치.** 공통 단계(채택, 추천안) / 지금 구조 유지.
2. **기능 요구를 쓰는 곳.** 계획 파일 앞부분(AI 추천) / 별도 파일 `docs/spec/<기능>.md`(**사용자 선택**). 사용자는 요구와 계획을 나누는 쪽을 골랐다.
3. **요구 판정 시점.** 계획과 한 번에(AI 추천) / 요구를 먼저 따로(**사용자 선택**). 틀린 계획을 쓰는 일을 줄이는 대신 기능마다 정지가 하나 는다.
4. **현재 동작(행동 명세) 관리.** AI는 처음에 "테스트가 행동 명세"를 추천했다. 사용자가 영역별 누적을 자세히 설명해 달라고 해서 OpenSpec 방식을 설명했다.
   - 설명하면서 AI가 추천을 바꿨다. 이 스킬의 첫 의도가 "결정할 재료를 사용자 머릿속에 남긴다"이기 때문이다. 사용자가 읽을 수 있는 현재 동작 문서가 테스트 코드보다 이 의도에 맞는다.
   - 채택: **영역별 누적 + 테스트 연결**. 시나리오마다 검증 테스트 위치를 적어, 명세와 테스트가 어긋나면 추적할 수 있게 한다.

결과 구조(`references/requirements.md`):

| 문서 | 위치 | 역할 |
| --- | --- | --- |
| 제품 명세 | `docs/spec/product.md` | 목적, 성공 기준, 범위, 만드는 방식, 기능 지도(상태: 예정·진행·완료·있음) |
| 기능 요구 | `docs/spec/<기능 ID>.md` | 이번 기능의 델타(추가·바뀌는·없어지는 동작, 요구 + 시나리오), 하지 않을 것, 전제, 열린 질문 |
| 동작 명세 | `docs/behavior/<영역>.md` | 영역별 현재 동작. 시나리오마다 검증 테스트 |

- 흐름: 요구(판정 `SPEC-<기능 ID>`) → 계획(게이트 확정) → 사이클 → 마지막 확인 지점 통과 → 동작 명세에 합치기, 요구 파일은 `docs/archive/spec/`으로.
- 합치기는 요구 보고에서 이미 판정받은 내용이라 다시 묻지 않고 알린다.
- 작업 유형은 "제품이 있는가"로 가른다. 초기 개발은 제품이 없을 때 제품 명세를 처음 쓰고 골격을 만드는 일만 맡는다. 골격의 기능 요구는 제품 명세와 같은 보고로 받아 정지를 하나 줄인다.
- 기존 제품에 기능 여럿을 더하는데 제품 명세가 없으면, 요청받은 기능과 그것이 기대는 기존 기능(`있음`)만으로 제품 명세를 시작한다.
- 동작을 보존하는 유지보수(리팩터링, 의존성)는 요구를 생략한다. 버그 수정은 [011](./011-maintenance-backlog.md)에서 다시 정할 때까지 기능 개발과 같다.

AI가 정한 세부:

- 제품 명세 파일 이름을 `<제품>-명세.md`에서 `product.md`로 바꿨다. 기존 제품을 증축할 때 `<제품>`이 모호하다는 시뮬레이션 지적 때문이다.
- 동작 명세는 `docs/spec/` 아래가 아니라 `docs/behavior/`에 둔다. 의도(명세)와 현재 동작을 폴더로 구분하기 위해서다.
- 요구 대화 방법과 spike 규칙은 `init-dev.md`에서 `requirements.md`로 옮겼다. 모든 유형이 쓰기 때문이다.

## 버린 것과 미룬 것

- OpenSpec의 변경 폴더 구조(proposal, design, tasks, specs를 한 폴더에): 이 스킬은 이미 `docs/plan/`, `docs/decision/`, `docs/log/`가 있어 기능 요구 파일 하나만 더했다.
- Kiro의 EARS 문법(WHEN ... THE SYSTEM SHALL): 한국어 사용자에게 어색하다. "상황에서 / 조작하면 / 결과" 시나리오로 대신했다.
- 기존 시스템의 동작 명세를 도입할 때 한꺼번에 쓰는 것: 낡은 문서를 만든다(OpenSpec). 실제 변경이 지나간 영역만 채운다.

## 다시 볼 신호

- 요구 보고와 계획 보고가 연달아 와서 사용자가 내용을 보지 않고 통과시킨다. ([001](./001-approval-boundary-by-questions.md)의 승인 피로. 작고 분명한 기능은 요구와 계획을 한 번에 받는 예외를 검토한다)
- 동작 명세와 테스트가 어긋난다. 특히 버그 수정이나 리팩터링이 동작 명세를 거치지 않을 때다. ([011](./011-maintenance-backlog.md)에서 "동작이 바뀌면 동작 명세도 고친다"를 넣는다)
- 기능 요구가 계획과 같은 내용을 되풀이한다. (요구가 기술 선택까지 담고 있음)

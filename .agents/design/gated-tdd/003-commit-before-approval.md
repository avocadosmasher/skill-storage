# 003. 승인 전에 커밋하고, main 병합(PR)만 사용자가 고른다

- 날짜: 2026-10-14
- 상태: 채택
- 반영: skill-storage 1.5.0

## 배경

1.4.0까지는 "통과" 판정이 있어야만 커밋할 수 있었고, git 훅(`pre-commit`, `pre-push`)이 승인 기록과 스테이징 트리를 대조해 막았다. 자동 진행 단위를 도입하면([001](./001-approval-boundary-by-questions.md)) 이 규칙과 부딪힌다.

## 선택지

1. **"통과 후에만 커밋"을 유지한다.**
   - 단점: 확인을 기다리는 동안 자동 단위들이 스테이징에 한 덩어리로 쌓인다. 단위별 이력과 되돌리기가 깨지고, 확인에서 문제가 나왔을 때 어느 단위가 원인인지 찾기 어렵다.
2. **단위마다 커밋하고, main 병합만 사용자가 고른다.** (채택)
   - 장점: 단위별 이력이 남아 확인 간격을 넓혀도 원인 추적이 쉽다. 세션이 갑자기 끊겨도 잃는 것은 진행 중인 단위 하나다.
   - 단점: "통과해야만 커밋"이라는 스킬의 대표 문장과 git 훅의 역할이 바뀐다.

## 결정

- 단위가 끝나면 게이트 등급과 관계없이 feat 브랜치에 커밋한다. feat 브랜치 push도 자유롭다.
- 사용자의 최종 선택은 main 병합이다. PR로만 들어가고 병합은 사용자가 고른다.
- git 훅의 역할을 바꾼다.
  - `pre-commit`: 보호 대상 변경(정책 파일에 적은 경로, 기존 테스트의 줄 삭제·수정, `.skip`·`.only` 추가, 게이트 자체 파일)이 스테이징되어 있으면, 그 트리에 대한 승인 기록이 있어야 커밋된다. 그 밖의 변경은 통과한다.
  - `pre-push`: 보호 브랜치(기본 `main`, `master`)로 가는 push와 그 브랜치 삭제를 막는다.
- 결정 게이트의 판정은 지금처럼 사용자가 "통과" 또는 "수정"으로 답하고, 에이전트가 `approve`로 기록한다.

## 버린 것과 미룬 것

- 승인 기록을 여러 커밋 목록으로 쌓아 push 때 대조하는 안은 미뤘다. main 직접 push를 막는 것으로 충분하고, PR이 사용자 선택을 기록한다.
- 사람이 판정하지 않았는데 에이전트가 approve를 실행하는 것을 훅이 막을 수는 없다. 1.4.0과 같은 신뢰 모델이고, 훅은 사고를 막는 하한선이다.

## 다시 볼 신호

- PR 하나가 너무 커져서 병합 판단이 어려워진다. (PR 범위를 마일스톤 단위로 자르는 규칙이 필요)
- 보호 경로 기본값이 너무 자주 걸리거나(예: `package.json`의 scripts만 고쳐도 멈춤) 너무 자주 새어 나간다.

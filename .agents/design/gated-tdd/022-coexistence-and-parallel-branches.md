# 022. 다른 도구와 자리를 다투지 않고, 브랜치를 동시에 진행해도 깨지지 않게 한다

- 날짜: 2026-10-27
- 상태: 채택
- 반영: skill-storage 1.9.0
- 바뀐 것: [019](./019-third-simulation-fixes-and-backlog.md)의 "세션 시작에 `core.hooksPath`가 `.githooks`가 아니면 설정한다"는 실제 연결 확인으로 바뀜.
  세션 시작에 `STATUS.md`만 읽던 것은 상태 스크립트 출력만 보는 것으로 바뀜. [005](./005-unconfirmed-checkpoints-block.md)의 규칙(이 브랜치의 확인 대기가 막는다)은 그대로.

## 배경

[021](./021-full-audit.md) 전체 점검의 묶음 B 일곱 건이다. 사용자가 항목마다 질문하고 추천안을 받은 뒤 "추천대로" 정했다.
B3는 사용자가 "다른 시각에서 한 번 더"를 요청해, 새 컨텍스트 에이전트가 임시 저장소에서 공격 사례를 직접 돌려 검토했다.

## B1. 훅 자리: 도구 이름 대신 자리가 쓰이는지 본다

상황: husky를 쓰는 저장소에 도입하면 `core.hooksPath`를 `.githooks`로 바꿔 husky의 lint가 조용히 꺼진다. 다음 `npm install`에서
husky가 자리를 되찾으면 이번에는 게이트가 꺼진다. 019의 "세션 시작에 되돌린다"는 이 싸움을 매 세션 반복한다.

- 선택지: (가) husky·lefthook·pre-commit 이름을 고정해 감지 (나) 자리가 쓰이는지 일반적으로 보고, 쓰이면 이어 붙임
- 선택: (나). 사용자 제안("고정으로 넣기보다 다른 요소가 있는지 검사")을 따랐다. 이름 목록은 늘 빠지는 도구가 생긴다.
  - 자리가 쓰이는지: `core.hooksPath`가 다른 값이거나 `.git/hooks`에 sample이 아닌 파일이 있음. 도구 설정 파일은 참고.
  - 쓰이면 그 도구의 훅 맨 앞에서 `.githooks/<훅>`을 부른다. husky만 예시로 적고, 방법이 확실하지 않으면 묻는다.
  - 연결 확인은 설정이 아니라 실행이다: `manual-review.mjs hooks`가 `git hook run`으로 훅 네 개를 돌린다. 확인 중에는
    `.githooks`의 훅이 표시만 내고 멈춰, 이어진 다른 도구의 lint·테스트가 돌지 않는다. 세션 시작마다 이것으로 확인한다.
- 버린 것: 확인을 정적 검사(훅 파일에 `.githooks` 문자열이 있는지)로 하기. husky v9처럼 실제 훅이 다른 파일을 부르는 구조를 못 따라간다.

## B2. 동시 진행: 상태 파일을 브랜치마다 따로 두고 모아 보여 준다

상황: 두 브랜치가 각각 `STATUS.md`와 INDEX 같은 자리를 고치고 로그 번호 `03-`을 같이 만들어 병합 때마다 충돌했다.
브랜치 A에서는 브랜치 B의 판정 대기가 보이지 않았다.

- 선택지: (가) 로그 이름만 날짜+ID로 (나) 사용자 제안: 메인 STATUS가 전체 흐름을, 브랜치별로 따로 추적
  (다) (나)를 다듬음: 브랜치마다 자기 상태 파일만 고치고, 전체 흐름은 손으로 고치는 파일 대신 스크립트가 모아 보여 줌
- 선택: (다). 모든 브랜치가 고치는 공유 파일은 어디에 두어도 충돌하고, 병합 전에는 다른 브랜치가 볼 수 없다.
  - 상태 파일 `docs/status/<브랜치>.md`. 다른 브랜치의 파일은 고치지 않는다.
  - `status.mjs`가 로컬과 원격 브랜치(병합된 것 제외)의 상태 파일을 `git show`로 읽어 대기 칸을 모은다. 원격에만 있는 다른 PC의 작업도 보인다.
  - 로그 파일 이름은 `<날짜>-<ID>.md`, 같은 날 같은 ID면 `-2`. INDEX는 `.gitattributes`의 `merge=union`으로 양쪽 줄을 남긴다.
    GitHub의 PR 병합은 이 설정을 쓰지 않을 수 있어, PR에 INDEX 충돌이 나면 `git merge origin/main`으로 로컬에서 푼다.
- 남은 제약: 병합된 브랜치의 상태 파일은 main에 기록으로 남는다. 다른 브랜치의 확인 대기는 이 브랜치를 막지 않고 첫 보고에 적는다.

## B3. main 병합: 원격 main에서 그대로 들어온 파일만 뺀다

상황: 기능 브랜치에 main을 병합하면, 다른 PR에서 이미 판정받은 의존성·마이그레이션이 다시 막혔다.
사용자는 "병합해 들어온 쪽과 같은 내용은 빼기"에 동의하고 다른 시각의 검토를 요청했다.

- 검토에서 나온 것: 원래 안은 판정받지 않은 아무 브랜치나 병합해 보호 대상을 들여올 수 있었고, 옛 main 커밋으로 보안 패치를
  되돌리는 병합도 통과했다. 더 큰 구멍으로, 충돌 없는 병합·fast-forward·rebase·cherry-pick·revert는 지금도 `pre-commit`을 거치지 않았다.
  감사 1차에서 대안으로 적은 "rebase를 쓴다"는 가장 나쁜 안이었다.
- 선택: 고쳐서 채택.
  1. 병합해 들어오는 커밋이 모두 원격 보호 브랜치에 있을 때만 뺀다. 로컬 main은 믿지 않는다.
  2. 파일마다 "스테이징된 내용 = 들어온 쪽 내용"이고 "들어온 쪽이 실제로 바꿈(공통 조상과 다름)"일 때만 뺀다.
  3. 충돌 없는 병합을 위해 `pre-merge-commit` 훅을 더한다. 이 훅이 돌 때는 `MERGE_HEAD`가 아직 없어서 git이 넘기는
     `GITHEAD_<커밋>` 환경 변수로 들어오는 커밋을 안다(git 2.51에서 확인).
  4. `merge.ff false`로 fast-forward 병합을 끄고, `pull.ff only`로 `git pull`은 fast-forward만 하게 한다. 모두 무료 git 설정이다.
  5. 규칙: main 반영은 `git fetch` 후 `git merge origin/main`. rebase·cherry-pick·revert는 쓰지 않는다. 원격 추적 브랜치를 손으로 바꾸지 않는다.
- 같이 막은 구멍: 훅이 작업 폴더의 게이트를 돌려, 게이트를 고치다 만 채로 두면 검사가 꺼졌다. 훅은 `HEAD`의 게이트를 꺼내 돌린다.
  훅 파일 자체를 고치는 것은 여전히 막지 못하며, 금지 규칙으로 둔다.
- 버린 것: 테스트 줄 규칙을 부모마다 따로 판단하기(main에서 바뀐 테스트에 이 브랜치가 줄을 더한 경우). 드물고 복잡해서 판정으로 처리한다.

## B4. 복사 위치: `scripts/gated-tdd/`, 게이트 테스트는 복사하지 않음

상황: `scripts/manual-review.test.mjs` 등을 복사하면 vitest·jest가 `*.test.*`를 모아 돌려 아무것도 고장 나지 않았는데 `npm test`가 실패했다.
`scripts/budget.mjs`가 이미 있는 프로젝트는 덮어썼다.

- 선택: 스크립트를 `scripts/gated-tdd/`에 모으고 게이트 테스트는 스킬 안에만 둔다. 설치 검증은 테스트 대신 `hooks` 확인으로 한다.
  게이트 파일 패턴은 `scripts/gated-tdd/**`가 되어 `log-new.mjs`, `status.mjs`도 보호한다.
- 이미 도입한 저장소: `approval-gate.md`의 "예전 배치에서 옮기기"로 한 번 옮긴다(판정 ID `도입-갱신`).

## B5. 다른 스킬과의 겹침

- grill-me-plus: 불리면 저장소 맨 위에 `DECISIONS.md`를 만들고 미룬 결정을 "spike"라 부른다. 두 호출 자리에 "결정은 계획의 결정 목록·
  기능 요구·`docs/decision/`에 쓰고, 미룬 결정은 결정 목록의 `미정`이나 요구 보고의 열린 질문으로"를 적었다. spike는 뜻이 다르다고 밝혔다.
- capture-compare: 시안 개수(2~8 대 3~4)를 그 스킬에 맡기고, 없을 때만 3~4개로 한다. 비교 결과는 `docs/decision/`.
- 채택 선언: 새 문구(clone 줄, main 반영 줄)를 도입 절차, 문서 페이지, CHANGELOG에 같이 적었다.
- superpowers 같은 다른 계획 스킬과 계획 문서가 두 벌 생기는 문제는 그 스킬을 호출하지 않으므로 이번에 다루지 않았다.

## B6. 작업 보류: 지우지 않고, 매번 보이게

상황: 급한 일이 끼어들거나 정식 절차로 올릴 때 커밋하지 않은 변경이 다음 판정(approve)을 막았다. 사용자 조건은
"미뤄 둔 일이 잊히거나 지워지면 안 된다".

- 선택: 이름 붙인 stash + 원격 `park/<ID>` 브랜치 + 상태 파일 "미뤄 둔 작업" + 세션 시작 출력.
  - stash는 이 PC에만 있어, 원격이 있으면 바로 `stash@{0}`을 `park/<ID>`로 올린다. stash 커밋은 `git stash apply <커밋>`으로 그대로 꺼낼 수 있다.
  - `stash pop`·`stash clear`는 쓰지 않는다. 꺼낸 작업이 커밋된 뒤에만 그 하나를 지운다.
  - `status.mjs`가 stash 목록과 `park/` 브랜치를 지울 때까지 매번 보여 준다.
- 버린 것: 보류용 WIP 커밋. 보호 대상 변경이 섞이면 훅에 막히고, `--no-verify`는 금지다.

## B7. 동작을 보존하는 작업은 요구를 생략한다

상황: "결제 모듈 구조만 정리"처럼 사용자가 보는 동작이 그대로인 요청에서, SKILL.md와 [012](./012-requirements-for-every-change.md) 이후
표는 요구를 생략한다고 하고 `requirements.md` 첫 줄은 모든 작업이 거친다고 했다.

- 선택: 생략으로 통일. `requirements.md` 첫 줄과 현재 원칙 10을 고쳤다. 계획부터 하고, 기능 ID는 계획을 쓸 때 정하며,
  끝의 정의는 "기존 테스트가 모두 그대로 통과"와 작업 목적으로 쓴다.

## 함께 고친 것

- 훅 파일이 Windows에서 CRLF로 풀리면 `exec node ... check-commit\r`가 되어 깨진다. 도입 저장소의 `.gitattributes`에
  `.githooks/* text eol=lf`를 넣고, 이 저장소에도 스킬의 훅 파일에 같은 설정을 두었다.
- spike 기록은 병합하지 않는 spike 브랜치가 아니라 작업 브랜치에 남긴다.
- 예산 정지 문구가 `STATUS.md`를 가리키던 것을 "상태 파일"로.

## 다시 볼 신호

- 이어 붙인 훅 도구(lefthook, pre-commit 등)에서 `hooks` 확인이 통과하는데 실제 커밋에서 게이트가 돌지 않는 사례.
- 원격 main 병합에서 정당한 변경이 계속 판정을 요구하거나(테스트 줄 규칙), 반대로 판정 없이 들어오는 사례.
- `GITHEAD_` 환경 변수가 없는 git 버전이나 병합 전략.
- `docs/status/`의 끝난 브랜치 파일이 많아져 읽기 불편해짐.
- stash나 `park/` 브랜치가 쌓여 정리되지 않음.

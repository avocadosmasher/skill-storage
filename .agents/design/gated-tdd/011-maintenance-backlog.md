# 011. 유지보수 개발 절차(버그 수정, 레거시, 리팩터링, 의존성)는 다음 개선으로 미룬다

- 날짜: 2026-10-16
- 상태: 보류 (M2는 [020](./020-small-fix-path.md)에서 채택)
- 반영: M2만 skill-storage 1.8.0. 나머지는 없음 (작업 유형 표의 유지보수 행은 "기능 개발과 같음. 동작을 보존하는 작업은 요구를 생략함", [012](./012-requirements-for-every-change.md))

## 배경

[009](./009-lifecycle-audit-and-structure.md) 점검의 M1~M5다. 사용자는 이번 개선 범위를 초기 개발로 정하고, 유지보수 항목은 "다른 항목들도 좋은 것 같아서 나중에 고도화하기 위해 기록해 두는 작업"으로 남기라고 했다.
이 파일은 다음 개선을 시작할 때 출발점이다.

## 과제

### M1. 버그 수정 흐름

- 지금: 3절 Red가 "기대 동작을 테스트로 먼저 쓴다"뿐이다. 7절의 "추측하지 말고 잰다" 한 줄이 원인 조사의 전부다.
- 참고: mattpocock `diagnosing-bugs`
  1. 재현 루프(빠르고 결정적이며 이 버그에서 빨개지는 명령 하나)를 먼저 만든다.
  2. 재현을 최소화한다.
  3. 검증 가능한 가설 3~5개를 순위를 매겨 사용자에게 보인다.
  4. 맞는 seam에 회귀 테스트를 둔다. 맞는 seam이 없으면 그 자체가 발견이다.
  5. 진단용 로그에 태그를 붙여 정리한다.
- 참고: superpowers `systematic-debugging`의 "원인 조사 전 수정 금지".
- 참고: Kiro의 `bugfix.md`는 현재 동작, 기대 동작, 바뀌면 안 되는 동작으로 버그를 적는다. [012](./012-requirements-for-every-change.md)의 기능 요구(바뀌는 동작)와 동작 명세에 잇기 좋다.
- 이 스킬과의 접점: 재현 테스트가 Red가 된다. 기존 테스트가 버그를 기대값으로 굳혀 두었으면 그 수정은 판정 질문 ②(결정)다.

### M2. 작업 크기별 강도와 "작은 수정"의 정의

- 지금: docs 페이지는 "한 번에 끝나는 작은 수정은 맞지 않는다"고 하는데, 저장소 규칙으로 채택하면 모든 작업이 이 절차를 탄다. 계획 문서 없이 도는 경로가 없다.
- 사용자 의견: "작은 수정까지 계획 문서를 만들면 번거롭긴 할 것 같다. 하지만 작은 수정이라는 단위를 잘 정의하는 게 중요할 것 같다."
- AI가 처음 낸 추천: 크기별 차등. 작은 수정은 계획 파일 없이 "재현 테스트 → 수정 → 로그 1건 → 커밋"으로 하고, 판정 질문과 훅은 그대로 적용한다. 여러 단위가 필요하면 계획을 세우고, 커지면 멈추고 한 단계 올린다.
- 정의 후보 (아직 고르지 않음):
  1. 판정 질문 기준: 작업 표 한 행으로 표현되고, 완료 기준을 자동 검사로 증명하며, ①②③④ 어디에도 해당하지 않음. 이 스킬의 기존 언어를 쓰고 훅과 맞는다.
  2. 크기 기준: 바뀌는 파일 수나 줄 수. 재기 쉽지만 의미와 어긋난다(한 줄짜리 권한 변경도 있다).
  3. superpowers의 3단계(바로 할 일, 대화로 정하는 작은 변경, 문서가 필요한 프로젝트). 사용자에게 크기를 말하고 사용자가 바꿀 수 있다.
- 열린 질문: 작은 수정의 로그를 남길지, 커밋 메시지로 대신할지. 확인 지점(④)이 걸리는 작은 화면 수정은 어떻게 할지.

### M3. 테스트 없는 기존 코드

- 지금: Red를 쓸 기준점이 없는 코드에서 막힌다.
- 방향 후보: 고치기 전에 지금 동작을 그대로 고정하는 특성화 테스트를 먼저 둔다. 새 테스트 추가는 훅에서 자유다. 특성화 테스트가 드러낸 "이상하지만 지금 그런" 동작을 고칠지는 판정 질문 ②다.

### M4. 동작을 바꾸지 않는 큰 리팩터링

- 지금: Refactor가 사이클 안의 정리로만 있다.
- 방향 후보: 새 실패 테스트 없이 "기존 테스트 녹색 유지 + 특성화 테스트"를 완료 기준으로 하는 작업 유형. 후보 탐색은 최근 자주 바뀐 곳부터 본다(mattpocock `improve-codebase-architecture`).
- 주의: 기존 테스트가 내부 구조에 묶여 있으면 리팩터링이 테스트 수정을 부르고, 그 수정은 보호 대상이다. 기대값을 바꾸지 않는 이동·이름 변경을 어떻게 구분할지 정해야 한다.

### M5. 일상적 의존성 업데이트

- 지금: `package.json` 등이 기본 `decide` 경로라 패치 버전 하나도 결정이다. [003](./003-commit-before-approval.md)의 다시 볼 신호에 적혀 있던 항목이다.
- 방향 후보: 패치·마이너 업데이트를 자동으로 내릴 수 있게 할지, 계획에서 "의존성 업데이트" 행을 결정으로 한 번 확정하면 그 범위의 업데이트를 덮게 할지. 훅이 파일 단위로 판단하므로 버전 범위를 읽는 검사가 필요할 수 있다. 보안 판단이 따르므로 기본값은 보수적으로 둔다.

## 결정

보류. 다음 개선에서 M2(작은 수정의 정의)부터 정한다. M1, M3, M4는 M2의 경로 위에 얹히기 때문이다.
M2는 2026-10-20 [020](./020-small-fix-path.md)에서 정했다. 다음은 M1(버그 수정의 원인 조사)이다. 작은 수정의 "재현 먼저"와 "가설 3번 실패 시 올림"이 그 출발점이다.
M1에서 함께 정할 것(020 시뮬레이션에서 나옴): 작은 수정에서 올라온 버그를 기능 지도에 넣는지, 커밋하지 않은 재현 테스트를 요구·계획 커밋 동안 어떻게 두는지.
만들 때 상세는 `references/maintenance.md`에 두고, SKILL.md 작업 유형 표의 유지보수 행이 그 파일을 가리키게 한다([009](./009-lifecycle-audit-and-structure.md)).

## 다시 볼 신호

- 버그 수정이나 리팩터링이 동작 명세(`docs/behavior/`)를 거치지 않아 명세와 테스트가 어긋난다.

- 실제 버그 수정에 이 스킬을 쓰다가 계획 문서 부담이나, 재현 없이 수정하는 일이 생긴다.
- 의존성 업데이트 때문에 결정 정지가 반복된다.

# 023. 두 번째 전체 점검: 1.9.0의 빈 곳을 막는다

- 날짜: 2026-10-28
- 상태: 채택 (묶음 C 보류)
- 반영: skill-storage 1.10.0
- 바뀐 것: [022](./022-coexistence-and-parallel-branches.md)의 로그 이름(`<날짜>-<ID>`)은 `<날짜>-<작업>-<ID>`로, `park/<ID>`는 `park/<브랜치>-<ID>`로 바뀜.
  [018](./018-small-gaps-and-scope-view-idea.md)·[013](./013-simulation-fixes.md)의 "결정은 보고 전에 커밋하지 않는다"에 상태 파일만 예외를 둠.
  원칙 12에 우선순위 선언 예외, 원칙 16에 `directPush` rebase 예외를 둠.

## 배경

1.9.0(022)을 PR #9로 올린 뒤 사용자가 "한 번 더 점검"을 요청했다. 021과 같은 세 관점(상황별 문제, 지시문 충돌, 다른 스킬·도구와의 겹침)으로
새 컨텍스트 에이전트 셋을 돌렸고, 상황별 문제 쪽은 임시 저장소에서 git 2.51로 재현했다. 겹친 것을 합쳐 24건이었다.
사용자는 방향이 분명한 것(묶음 A)은 바로 고치고, 선택이 필요한 것(묶음 B)은 추천대로 가자고 했다.

## 묶음 A: 방향이 분명한 버그

보호가 뚫리는 것:

- **A1 설정을 작업 폴더에서 읽음** (재현함): 게이트는 커밋된 것을 돌리는데 `.gated-tdd.json`은 디스크에서 읽어, 스테이징하지 않은
  `{"decide":[],"protectedBranches":[]}`만으로 의존성 커밋과 main push가 통과했다. 커밋 검사는 스테이징된 설정, push 검사와 연결 확인은
  HEAD의 설정을 읽게 했다. 스테이징된 설정 변경은 그 자체가 게이트 파일 변경이라 판정이 필요하다.
- **A2 연결 확인이 실패 전달을 보지 않음** (재현함): 이어 붙인 줄에 `|| exit $?`가 없으면 표시는 나오지만 게이트가 막아도 커밋된다.
  확인 모드의 종료 코드 3이 `git hook run`까지 돌아오는지 본다.
- **A3 pre-push 표준 입력**: pre-commit(Python)과 기본 설정의 lefthook은 push 정보를 훅에 넘기지 않아, 게이트가 빈 입력을 받고 main push를 통과시킨다.
  확인 때 `git hook run --to-stdin`으로 push 한 줄을 넣고, 확인 모드의 pre-push는 입력이 없으면 `no-stdin` 표시를 낸다. 도구별 방법을 `approval-gate.md`에 적었다.
- **A4 아무 원격의 main이나 믿음** (재현함): fork를 원격으로 더하고 그 `main`을 병합하면 리뷰받지 않은 의존성이 들어왔다.
  믿는 원격을 설정 `trustedRemote`(기본 `origin`) 하나로 줄였다. 설정 파일은 게이트 파일이라 바꾸려면 판정이 필요하다.
  - 버린 안: `branch.main.remote`를 따르기. 그 값은 `git branch -u` 한 번으로 바뀌고 훅이 막지 못한다.

절차가 막히거나 꼬이는 것:

- **A5** 보류할 때 상태 파일까지 stash에 들어가 나중에 꺼낼 수 없었다. `":(exclude)docs/status"`로 빼고, 적은 뒤 상태 파일만 커밋한다.
- **A6** `stash@{0}`이 PowerShell에서 깨진다(재현함). `refs/stash`로 쓰고, 번호가 필요한 `drop`은 따옴표를 붙인다.
- **A7** `status.mjs`가 개인 stash와 lint-staged 백업까지 "미뤄 둔 작업"으로 보였다. `gated-tdd 보류:` 이름만 본다.
- **A8** 브랜치 이름을 바꾸면 상태 파일과 연결이 끊겼다. 이름을 바꾸는 세 곳에 상태 파일도 바꾸게 하고, 이미 push한 옛 원격 브랜치는 지우게 했다.
- **A9** 작은 수정을 올릴 때 "커밋 안 한 작업은 그대로 둔다"를 따르면 다음 approve가 실패했다. 작업 보류로 미룬다.
- **A10** 예전 배치 판별 순서가 거꾸로였고, 옮긴 `STATUS.md`가 chore 브랜치 이름으로 저장됐으며, `도입-갱신`이 ID 목록에 없었다.
  판별을 먼저 하고, main의 `STATUS.md`는 지우며, 진행 중인 기능 브랜치는 옮기기 PR이 병합된 뒤 `git merge origin/main`을 하며 옮긴다.
- **A11** 도입 뒤에 husky가 들어오면 세션 시작 지침이 `core.hooksPath`를 되찾게 해 B1의 자리 싸움이 다시 열렸다. 이때는 이어 붙이는 안을 `도입-갱신`으로 보고한다.
- **A12** 이미 자기 `.githooks/`를 쓰는 저장소는 빈 자리로 보고 덮어썼다. 스킬의 훅이 아닌 파일이 있으면 쓰이는 자리로 본다.
  Git LFS처럼 같은 pre-push 입력이 필요한 훅과 한 파일에 이을 때는 입력을 변수에 담아 두 번 넘긴다.
- **A13** monorepo 하위 폴더에서 세션을 열면 스크립트가 없다고 보고 두 번째 도입을 시작했다. 명령과 판단을 저장소 맨 위에서 한다.
- **A14** Prettier·ESLint·tsc가 복사한 게이트 스크립트에 걸려 도입 PR의 CI가 실패하고, 포맷터가 INDEX 표를 다시 정렬하면 `merge=union`이 줄을 두 벌로 남겼다.
  설치 5단계로 제외 목록에 넣는다.
- **A15** `park/` push가 추적되지 않은 파일(실수로 둔 키 파일 등)까지 올렸고, `park/A01`은 기능끼리 겹쳤다. 올리기 전 목록을 보고, 이름에 브랜치를 넣는다.
- **A16** 기능 ID `product`는 제품 명세 파일을 덮는다. 쓰지 않는 ID로 정했다(`skeleton`은 골격 전용).
- **A17** 오래된 표현: description의 `STATUS.md`, 원칙 6의 범위, 원칙 9의 작업 유형 수, 브랜치 규칙에 빠진 `fix/`·`chore/gated-tdd-update`·`park/`.

## 묶음 B: 선택이 있었던 것 (모두 추천안)

1. **로그 이름 충돌**: 행 ID는 계획마다 A01부터 다시 시작해, 같은 날 두 기능이 같은 파일 이름을 만들었다.
   - 선택지: (가) 이름에 작업 이름을 넣음 (나) 행 ID를 저장소 전체에서 유일하게
   - 선택: (가). 작업 이름은 브랜치의 첫 마디를 뺀 것이고(`feat/login` → `login`), ID에 이미 들어 있으면 붙이지 않는다. INDEX 항목 칸도 같다.
     (나)는 계획을 쓸 때마다 다른 브랜치를 살펴야 한다.
2. **다른 브랜치의 판정 대기가 안 보임**: 결정은 보고 전에 커밋하지 않고 `status.mjs`는 커밋된 것만 읽어서, 다른 브랜치의 판정 대기가 거의 보이지 않았다.
   - 선택지: (가) 문서 표현을 "커밋된 대기만"으로 낮춤 (나) 정지 보고 전에 상태 파일만 커밋·push
   - 선택: (나), 세션 시작에 `git fetch --prune`. 결정 문서와 로그는 그대로 판정 뒤에 커밋한다. 승인은 스테이징 트리에 붙으므로 상태 파일을 먼저 커밋해도 판정 범위는 바뀌지 않는다.
3. **squash 병합 뒤 끝난 브랜치가 계속 대기로 보임** (재현함): squash·rebase 병합은 main의 조상이 되지 않는다.
   - 선택지: (가) 내용 비교(`git cherry` 등)로 병합 판단 (나) 원격 브랜치가 지워진 로컬 브랜치를 표시하고, 에이전트가 PR 병합을 확인한 뒤 지움
   - 선택: (나). squash는 내용 비교로도 맞추기 어렵다. 병합 없이 닫힌 PR일 수 있어 확인할 수 없으면 묻는다.
4. **양쪽이 고친 보호 대상 파일의 병합** (재현함): 결과가 어느 쪽과도 달라 막히는데 다음 할 일이 없었다.
   - 선택지: (가) 판정 ID `MERGE-main-<날짜>`로 양쪽 변경과 합친 결과를 결정 보고 (나) 게이트가 "main 쪽 변경과 이 브랜치의 커밋된 변경을 뺀 나머지"만 검사
   - 선택: (가). 합친 결과는 실제로 아무도 판정하지 않은 내용이고, (나)는 줄 단위 비교가 필요해 게이트가 복잡해진다.
5. **directPush 중 원격 main이 앞서면 막다른 길**: `pull.ff only`라 pull이 안 되고 rebase는 금지였다.
   - 선택지: (가) 원격 main에서 새로 따서 다시 커밋 (나) `directPush` 경로만 `git pull --rebase` 허용
   - 선택: (나). push 훅이 올리는 커밋 전체가 `directPush` 경로만 바꾸는 fast-forward인지 다시 검사하므로, rebase가 훅을 건너뛰어도 빈 곳이 없다.
     먼저 pull하는 습관도 같이 적었다.
6. **다른 계획 스킬**: superpowers는 계획을 `docs/plans/`에 따로 쓰고 로컬 main 병합을 권하며, spec-kit은 `specs/`와 자기 브랜치 이름을 전제한다.
   - 선택: 채택 선언에 "계획·요구·TDD는 gated-tdd가 맡는다" 한 줄. 원칙 12(AGENTS.md에 절차를 옮겨 적지 않음)에 "다른 도구와 부딪히는 지점의 우선순위 선언은 예외"를 더했다.
     main 반영 줄(022)도 같은 이유로 이 예외에 든다.
7. **기존 문서 폴더**: `docs/adr/`, `docs/decisions/`가 있으면 비슷한 `docs/decision/`이 하나 더 생겼다.
   - 선택: 기존 폴더를 쓰고 `AGENTS.md` "상태와 문서" 줄에 대응을 적는다. 스크립트가 쓰는 `docs/log/`, `docs/status/`는 바꾸지 않는다.
8. **캡처 위치**: capture-compare(임시 폴더), SKILL.md(`docs/decision/`), maintenance.md(저장소 밖)가 달랐다.
   - 선택: 비교 시트는 임시 폴더에 만들고 고른 시트 하나와 이유만 `docs/decision/`에 남긴다. 작은 수정의 전후 캡처(maintenance.md)는 목적이 달라 그대로 둔다.
     캡처 도구 설치는 의존성 추가(판정 질문 ③)로 본다.

## 묶음 C: 기록만 하고 미룸

- 정당한 병합에서 테스트 줄 규칙이 판정을 요구하는 경우(022에서 미룸). 이제 `MERGE-main` 결정으로 처리할 길은 생겼다.
- main에 병합된 옆 브랜치의 옛 커밋을 `-X theirs`로 병합해 보안 수정을 되돌리는 경우. 원격 main이 아닌 대상 병합이라는 규칙 위반이 먼저 필요하다.
- 021 묶음 C의 "docs가 문서 사이트" 건은 브랜치마다 `docs/status/`가 쌓이며 커졌다. Docusaurus는 `<ID>` 같은 글자에서 빌드가 깨질 수 있다. 실제 사례가 나오면 다시 본다.
- 끝난 브랜치가 150개쯤 쌓이면 `status.mjs`가 10초 가까이 걸린다(재현함). 병합된 로컬 브랜치를 지우는 규칙(B3)으로 먼저 줄인다.
- `merge.ff false` 때문에 로컬 `git merge --squash`가 실패한다. 이 절차는 squash를 쓰지 않으므로 기록만 한다.

## 다시 볼 신호

- 상태 파일만 먼저 커밋하는 규칙 때문에 기능 브랜치의 커밋 기록이 상태 커밋으로 어지러워짐.
- `trustedRemote`를 바꿔야 하는 fork 흐름에서 설정을 잊어 정당한 병합이 계속 막힘.
- `directPush` rebase 예외가 다른 rebase의 핑계로 쓰임.
- 기존 문서 폴더 대응을 다른 스킬(capture-compare 등)이 모르고 `docs/decision/`에 씀.

# 027. 의존성 업데이트는 패키지와 목표 버전을 늘 사용자가 보고 정하고, lock 파일도 보호하며, 막 나온 버전은 7일 기다린다

- 날짜: 2026-11-05
- 상태: 채택
- 반영: skill-storage 1.12.0
- 바꾼 것: 현재 원칙 10("동작을 보존하는 유지보수는 계획부터")에 패키지 하나의 예외, 현재 원칙 1의 "테스트의 기계적 수정을 종류로"를 의존성 업데이트로 넓힘, 게이트 기본 보호 목록에 lock 파일

## 배경

[011](./011-maintenance-backlog.md) M5다. 작업 유형 표에는 "유지보수 (의존성): 요구를 생략하고 계획부터" 한 줄만 있었다.
[003](./003-commit-before-approval.md)의 다시 볼 신호("보호 경로 기본값이 너무 자주 걸리거나 너무 자주 새어 나간다")에 걸린 항목이기도 하다.

예시 상황: Node 저장소에서 사용자가 "의존성 업데이트 좀 해 줘"라고 한다. `npm outdated`에 patch 15개, minor 6개, major 2개(vitest 2→3, react-router 6→7), `npm audit`에 high 취약점 1건이 있다.

임시 저장소에서 게이트를 직접 돌려 본 결과, 같은 patch 업데이트가 명령에 따라 다르게 처리됐다.
`npm install a@1.2.9`는 `package.json`이 바뀌어 결정으로 멈췄고, `npm update a`는 `package-lock.json`만 바뀌어 기록 없이 통과했다. `Cargo.lock`, `go.sum`도 보호 대상이 아니었다.
그 밖에 계획에 무엇을 적는지, 완료 기준, 급한 보안 패치, 테스트 도구를 올릴 때의 테스트 수정에 지시가 없었다.

## 선택지와 결정

사용자는 다섯 가지 모두 추천대로 골랐다("추천대로진행하자.").

### 1. 업데이트를 어떻게 판정받나

| 안 | 내용 |
| --- | --- |
| **계획 보고 한 번, 패키지마다 현재→목표 버전 (채택)** | 업데이트 표에 패키지, 버전, 공개일, 이유, 변경 기록 요약을 적음. patch·minor는 한 행에 묶어 표를 줄임 |
| 종류로 판정 ("patch·minor 전부") | 실제 버전은 설치하는 순간 정해져, 판정 뒤에 나온 악성 버전도 범위 안이 됨 |
| patch는 판정 없이 자동 (훅이 버전 범위를 읽음) | 생태계마다 파서가 필요하고 보안 판단을 사용자가 못 함 |

원칙 1("무엇을 어떻게 바꾸는지까지")을 그대로 지키는 안이다.

### 2. lock 파일

| 안 | 내용 |
| --- | --- |
| **기본 보호 대상에 더함 (채택)** | 명령과 관계없이 같은 판정. 범위 안 업데이트로 들어오는 하위 의존성도 보임 |
| 지금처럼 두고 절차 문서에서만 다룸 | 기능 작업 중 `npm update`가 그대로 통과 |

게이트 스크립트가 바뀌므로 이미 도입한 저장소는 다시 복사해야 적용된다. 이번 유지보수 묶음에서 처음 생긴 이런 변경이라, 복사하는 절차("스크립트를 새 버전으로 바꾸기")를 함께 두었다.
기능 작업 중 패키지 관리자 버전 차이로 lock 파일이 다시 쓰이면 걸리는 비용이 있어, 의도하지 않은 lock 변경은 되돌리게 했다.

### 3. 막 나온 버전을 기다리는 기간

| 안 | 내용 |
| --- | --- |
| **7일, 알려진 취약점을 고치는 버전은 예외 (채택)** | 일상 업데이트는 급하지 않아 비용이 작음 |
| 3일 | 늦게 발견된 악성 버전을 놓칠 수 있음 |
| 기다리지 않음 | 공급망 공격에 그대로 노출 |

### 4. 패키지 하나만 바꾸는 업데이트

| 안 | 내용 |
| --- | --- |
| **계획 파일 없이 결정 보고 한 번, `DEP-<패키지>-<버전>` (채택)** | 급한 보안 패치가 빠름. 버그 보고처럼 한 번 |
| 항상 계획 | 패키지 하나에도 계획 파일 |

고치기 전에 원칙 10과 부딪힌다고 사용자에게 알렸다. 그래서 조건을 좁혔다. 매니페스트와 lock 파일 말고 고칠 것이 없고, 고정 테스트가 필요 없고, 화면 라이브러리면 전후 캡처가 같아야 한다.
하나라도 아니면 계획으로 간다.

### 5. 테스트가 덮지 않는 사용처

| 안 | 내용 |
| --- | --- |
| **major이거나 변경 기록에 동작 변경이 적힌 업데이트만, 바뀐 API를 쓰는 곳을 고정 (채택)** | patch·minor는 기존 테스트·빌드·타입 검사로 끝내고 덮지 않는 사용처는 위험으로 적음 |
| 모든 업데이트의 사용처를 고정 | 고정 테스트 작업이 업데이트보다 커짐 |
| 고정 없이 위험만 표시 | 원칙 17(고치기 전에 고정)과 어긋남 |

## AI가 정한 세부 (사용자에게 알림, 이의 없음)

- 상세는 `references/dependencies.md`에 두고 SKILL.md 0절·2절·5절·7절에서 가리킨다. 작업 유형 표의 "유지보수 (의존성)" 행을 "의존성 업데이트"로 바꿨다.
- 브랜치는 `deps/<이름>`이다. 패키지 하나는 이름에 목표 버전을 넣어(`DEP-lodash-4.17.21`) 같은 패키지를 다시 올려도 ID가 겹치지 않게 했다. 계획은 범위와 연월(`PLAN-2026-11-routine`)이다.
- 범위가 없는 요청은 패키지 관리자 명령으로 목록을 만들어 모두 표에 넣고, 사용자가 계획 보고에서 뺄 행을 고른다. 리팩터링과 달리 후보 고르는 질문을 따로 하지 않는다. 업데이트는 목록이 명령으로 정해지기 때문이다.
- major는 패키지마다 한 행으로 두어 하나씩 되돌릴 수 있게 했다. 받아들이려면 사용자가 보는 동작이 바뀌어야 하는 업데이트는 기능 개발로 분리한다.
- 실행 중 테스트가 실패하면 기대값을 고쳐 맞추지 않는다. patch·minor 묶음의 원인 패키지는 빼고 진행하며 완료 보고에서 따로 할지 묻는다(범위를 줄이는 것이라 판정 없이). major 행과 취약점 행은 빼면 작업의 목적을 잃으므로 그 행 ID로 결정을 올린다(시뮬레이션에서 바꿈).
- 화면 라이브러리의 minor·major 행과 사용자 흐름을 다루는 라이브러리(라우터, 폼)의 major 행에는 확인 지점을 둔다. 화면 라이브러리의 patch는 전후 캡처를 비교해 다르면 확인 지점을 더한다(등급은 올리기만 함).
- 하위 의존성은 설치 명령의 날짜 제한(npm `--before`, uv `--exclude-newer`)으로 7일 규칙을 적용한다. 날짜 제한이 없는 패키지 관리자면 확인하지 않은 범위로 보고한다.
- 업데이트로 생기는 테스트의 기계적 수정은 [026](./026-behavior-preserving-refactoring.md)의 종류 방식으로 받는다. 패키지 이름이 바뀐 major는 import 경로·이름 변경을 쓰고, 테스트 도구는 두 종류(이름만 바뀐 도구 API, 스냅숏 형식)를 더 쓴다. 원칙 1의 예외를 넓히는 것이라 사용자에게 알렸다. 처음에는 테스트 도구에만 두었다가 시뮬레이션에서 일반 패키지의 import 변경으로 넓혔다.
- Dependabot 같은 봇 PR은 도입에서 권하지 않는다. 이미 있으면 사용자가 병합하고, 처리를 맡으면 이 절차의 계획에 묶는다.
- 7일 규칙은 기능 계획에서 패키지를 더할 때도 적용한다. 같은 공급망 위험이 있기 때문이다.
- 게이트 기본 목록에 빠져 있던 매니페스트(`Pipfile`, `composer.json`, `libs.versions.toml`)도 lock 파일과 함께 더했다.

## 다시 볼 신호

- lock 파일 보호 때문에 기능 작업 중 의도하지 않은 lock 변경으로 막히는 일이 잦다.
- 계획의 업데이트 표가 길어 사용자가 읽지 않고 통과시킨다.
- 7일 규칙 때문에 필요한 수정이 늦어진 사례가 나온다.
- 패키지 하나 경로로 시작했다가 계획으로 올라가는 일이 대부분이다.

# gated-tdd 설계 기록

## 의도

이 스킬은 개발을 AI에게 통째로 맡기지 않고 사용자가 흐름을 따라가게 하려고 만들었다. 목적은 둘이다.

1. **결정할 재료를 사용자 머릿속에 남긴다.** 개발 중인 서비스를 사용자가 이해하고 있어야 결정이 필요할 때 스스로 판단할 수 있다.
2. **잘못 만들어진 기능을 빨리 발견한다.** 사용자가 직접 해볼 수 있는 부분은 직접 해보게 해서, 의도와 다른 기능을 일찍 잡는다.

승인 절차는 이 두 목적을 위한 수단이다. 승인 횟수 자체는 목적이 아니다. 승인이 잦아 도장 찍기가 되면 두 목적 모두 망가진다([001](./001-approval-boundary-by-questions.md)).

## 현재 원칙

1. AI는 실행하고, 사용자는 AI가 대신 정할 수 없는 것만 정한다. 계획에서 이미 정한 것은 다시 묻지 않는다. 계획 작업 표의 보호 대상 변경 칸에 적어 판정받은 변경은 그 범위 안이면 계획 판정으로 커밋한다([014](./014-plan-approval-covers-protected-changes.md)).
2. 승인 여부는 책임 범주가 아니라 판정 질문 네 개로 가른다. 범주는 계획할 때 결정이 숨는 곳을 훑는 체크리스트로 쓴다([001](./001-approval-boundary-by-questions.md)).
3. 작업 행마다 게이트 등급(결정·확인·자동)을 계획에서 AI가 제안하고 사용자가 확정한다. 실행 중 AI는 등급을 올리기만 한다([002](./002-three-gates-and-ratchet.md)).
4. 단위마다 커밋한다. 사용자의 최종 선택은 main 병합(PR)이다([003](./003-commit-before-approval.md)). 블로그 글처럼 개발 절차 밖의 콘텐츠 경로는 `directPush`로 main에 바로 올릴 수 있다. 배포되는 코드는 PR에서 테스트를 통과한 코드여야 하고, 방법은 기존 배포 방식에 맞춘다([017](./017-direct-push-paths-and-deploy-rule.md)).
5. 확인 지점은 사용자가 직접 해볼 수 있는 기능 묶음이 완성되는 곳에 둔다. 고정 개수로 정하지 않는다([004](./004-checkpoints-at-feature-bundles.md)).
6. 확인 지점은 확인받기 전에는 넘어가지 않는다. 그 브랜치에서는 세션이 바뀌어도 확인부터 한다. 다른 브랜치의 확인 대기는 막지 않고 알린다([005](./005-unconfirmed-checkpoints-block.md), [022](./022-coexistence-and-parallel-branches.md)).
7. 컨텍스트와 사용 한도는 단위 경계에서만 보고, 임계치를 넘었을 때만 알린다. 특정 에이전트 도구에 묶지 않고, 정확한 수치는 도구별 어댑터가 공급한다([006](./006-budget-signal-harness-neutral.md), [007](./007-claude-code-budget-adapter.md)).
8. 보고는 마지막 보고 이후 대화를 보지 않은 사용자가 읽는다. 결론만 잘라 읽어도 판정할 수 있어야 하고, AI의 가정은 "내가 이해한 전제"로 드러낸다. 짧음보다 판단 재료가 우선이다([008](./008-report-reader-and-style.md)).
9. 작업 유형(초기 개발, 기능 개발, 작은 수정, 유지보수)은 "제품이 있는가"와 요청의 크기로 가르고 세션 시작에서 고른다. 고른 유형은 첫 보고의 전제에 밝힌다. 유형별 상세는 SKILL.md가 아니라 `references/`에 둔다([009](./009-lifecycle-audit-and-structure.md), [013](./013-simulation-fixes.md)).
10. 요구 정리는 사용자가 보는 동작을 더하거나 바꾸는 작업의 공통 단계다. 기능마다 요구(델타, 시나리오)를 먼저 판정받고 계획을 세운다. 동작을 보존하는 유지보수(리팩터링, 의존성)는 요구를 생략하고 계획부터 한다([022](./022-coexistence-and-parallel-branches.md)). 끝난 기능의 동작은 영역별 동작 명세에 쌓고 시나리오마다 검증 테스트를 잇는다. 기존 시스템을 거슬러 문서화하지 않는다([012](./012-requirements-for-every-change.md)).
11. 초기 개발은 제품이 없을 때 제품 명세를 처음 쓰고 골격을 만드는 일만 맡는다. 제품 명세가 통과하기 전에는 짓지 않는다([012](./012-requirements-for-every-change.md)). 보호 대상과 테스트·빌드 명령은 스택이 정해지는 골격 계획에서 맞춘다([015](./015-init-dev-gate-config-at-skeleton.md)).
12. 도입한 저장소의 `AGENTS.md`에는 절차를 옮겨 적지 않고 채택 선언만 둔다. 절차는 스킬이 로드되며 따라온다([013](./013-simulation-fixes.md)). 다른 도구·스킬이 같은 저장소에서 다른 방법을 권하는 지점(main 반영, 계획 문서)의 우선순위 선언은 예외로 둔다([023](./023-second-audit.md)).
13. 작은 수정은 요구·계획 없이 커밋 하나로 처리한다. 진입 조건은 판정 질문과 훅으로 정하고, 커지면 멈추고 알린 뒤 기능 개발로 올린다([020](./020-small-fix-path.md)). 그 밖의 유지보수 전용 절차(버그 원인 조사, 레거시, 리팩터링, 의존성)는 아직 없다. 과제와 후보는 [011](./011-maintenance-backlog.md)에 보류로 있다.
14. 게이트 장치는 저장소의 다른 도구와 자리를 다투지 않는다. 스크립트는 `scripts/gated-tdd/`에 모으고 게이트 자체 테스트는 복사하지 않는다. 다른 훅 도구가 쓰는 훅 자리는 빼앗지 않고 이어 붙이며, 연결은 설정이 아니라 실제 실행으로 확인한다([022](./022-coexistence-and-parallel-branches.md)).
15. 여러 브랜치를 동시에 진행할 수 있어야 한다. 상태 파일은 브랜치마다 따로 두고, 정지 보고 전에 상태 파일만 먼저 커밋·push한다. 세션 시작에는 스크립트가 모든 브랜치의 대기 항목과 미뤄 둔 작업을 모아 보여 준다. 미뤄 둔 작업은 그 작업이 커밋되기 전에는 지우지 않는다([022](./022-coexistence-and-parallel-branches.md), [023](./023-second-audit.md)).
16. main 반영은 믿는 원격(`trustedRemote`) main의 병합으로만 한다. 거기에 이미 들어간 보호 대상 변경은 다시 묻지 않고, 양쪽이 고친 파일은 합친 결과를 묻는다. 훅을 거치지 않는 rebase·cherry-pick·revert·fast-forward 병합은 쓰지 않는다. push 훅이 다시 검사하는 `directPush` 경로의 rebase만 예외다([022](./022-coexistence-and-parallel-branches.md), [023](./023-second-audit.md)).

## 출발점 (1.4.0까지의 설계)

001~006 이전의 스킬은 작은 작업 단위 하나마다 Red, Green, 기록 후 멈추고, 사용자가 "통과"라고 해야 `manual-review.mjs approve`로 커밋할 수 있었다. 사람이 볼 것이 없는 변경도 판정을 요청했다. 이 방식이 승인 피로를 만들어 2026-10-14 개편을 시작했다.

# 017. 콘텐츠 경로는 main으로 바로 올리게 두고, 배포 규칙은 목적으로 정한다

- 날짜: 2026-10-19
- 상태: 채택
- 반영: skill-storage 1.7.0

## 배경

두 번째 시뮬레이션의 기존 제품 시나리오(Vercel에 배포하는 블로그에 기능 추가)에서 두 가지가 나왔다.

1. 이 블로그는 글(Markdown)을 main에 바로 올리면 Vercel이 게시하는 방식이었다. 도입하면 `pre-push`가 main으로의 push를 전부 막아, 글 하나도 PR을 거쳐야 한다. 이 훅은 사용자가 직접 하는 push에도 걸린다. 스킬은 이 영향을 도입 보고에서 알리라고 하지 않았다.
2. "CI는 재사용 워크플로 하나를 PR과 배포가 같이 쓴다"는 규칙이 Vercel처럼 플랫폼이 main을 직접 가져가 배포하는 경우와 맞지 않았다.

사용자 의견:
- 글: "글 올리기는 편했으면 한다."
- 배포: "기존 방식을 해치지 않으면서 진행하고 싶다."

## 선택지

### 글 올리기

1. **훅에 `directPush` 경로를 두고, 그 경로만 바꾸는 fast-forward push는 통과시킨다.** (채택)
   - 장점: 사용자가 직접 올리는 글은 지금과 똑같다.
   - 단점: 훅 코드가 늘어난다. MDX처럼 코드를 품을 수 있는 파일을 경로에 넣으면 테스트 없이 빌드에 들어간다.
2. **글은 저장소 밖(CMS, 다른 저장소)으로 옮긴다.**
   - 단점: 기존 방식을 크게 바꾼다.

`directPush` 검사의 경계:
- 게이트 파일은 경로와 무관하게 막는다. `directPush`에 `.gated-tdd.json`을 넣어 우회하지 못하게 하기 위해서다.
- 새 브랜치, 브랜치 삭제, 강제 push(fast-forward 아님), 병합 커밋은 막는다. 올리는 커밋마다 바뀐 파일을 보고, 그 사이 다른 파일을 고쳤다 되돌린 것도 잡는다.
- 원격 커밋이 로컬에 없으면(fetch 전) 막는다.
- 한글 파일 이름이 이스케이프되어 경로가 어긋나지 않도록 `core.quotePath=false`로 읽는다.

### 배포 규칙

1. **규칙을 목적으로 바꾼다: "배포되는 코드는 PR에서 테스트를 통과한 코드여야 한다". 방법은 기존 배포 방식에 맞춘다.** (채택)
   - CI가 배포하면 재사용 워크플로를 같이 쓴다(기존 규칙).
   - 플랫폼이 main을 직접 배포하면 배포 방식은 그대로 두고, PR 보고에 CI 결과를 붙여 사용자가 통과를 보고 병합한다.
   - 처음에는 GitHub 브랜치 보호(PR 테스트 통과를 병합 조건으로)를 기본 안내로 넣었다. 세 번째 시뮬레이션에서 두 문제가 드러났다. 이 설정은 GitHub 서버에서 main 직접 push를 거절해 `directPush`가 소용없어진다. 또 비공개 저장소에서는 유료다. 사용자는 "비용이 드는 형상관리 작업은 안 된다"고 했다. 그래서 기본 경로는 무료(PR 보고의 CI 결과)로 두고, 브랜치 보호는 무료일 때만 선택 사항으로 안내하며, `directPush`와 함께 켜면 본인을 우회 허용에 넣으라고 쓴다.
   - 플랫폼의 PR 미리보기 주소를 확인 지점의 해볼 곳으로 쓴다.
2. **배포를 GitHub Actions로 옮긴다.**
   - 단점: 사용자가 원하지 않은 기존 방식 변경이다.

## 결정

두 묶음 모두 1을 고른다. 사용자가 AI 제안에 "이어서 진행해 줘"로 동의했다.

- `assets/manual-review.mjs`: `directPush` 설정(기본 빈 목록)과 `check-push`의 예외. 테스트 두 개를 더했다.
- SKILL.md 1절: 배포 규칙을 목적으로 바꿈. main으로 바로 올리던 경로가 있으면 도입 보고에 영향을 쓰고 `directPush`를 묻는다.
- SKILL.md 5절 금지 규칙의 "main 직접 push"에 `directPush` 예외.
- `references/approval-gate.md`: 검사 경계와 넣지 말아야 할 파일(MDX, 설정, 스크립트).

처음에는 "AI가 쓴 글은 초안(`draft: true`)으로 올리고 공개 전환은 사용자가 판정한다"는 규칙도 넣었다. 사용자가 다른 작업과 헷갈려 draft를 말한 것을 AI가 이 스킬의 규칙으로 넘겨짚은 것이었다. 사용자 확인 후 뺐다. 이 스킬은 개발 절차라 AI가 콘텐츠를 쓰는 경우를 다루지 않는다.

원칙 4("사용자의 최종 선택은 main 병합(PR)")에 예외가 생긴다. 개발 절차 밖의 콘텐츠만 해당하므로 원칙은 유지하고 README에 예외를 적는다.

## 다시 볼 신호

- `directPush` 경로로 올린 파일이 빌드를 깨거나 동작을 바꾼다. (경로 선정 기준을 좁히거나 빌드 검사를 붙임)
- 브랜치 보호를 걸 수 없는 저장소에서 테스트를 통과하지 않은 PR이 병합된다.

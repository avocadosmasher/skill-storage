# 024. 버그 수정은 요구 없이 원인·영향도·대책을 조사해 대책만 한 번 판정받는다

- 날짜: 2026-11-02
- 상태: 채택
- 반영: skill-storage 1.11.0
- 바꾼 것: [012](./012-requirements-for-every-change.md)의 "버그 수정은 기능 개발과 같다"(현재 원칙 10)

## 배경

[011](./011-maintenance-backlog.md) M1이다. 지금까지 작은 수정이 아닌 버그는 기능 개발과 같은 절차를 탔다. 요구 보고(`SPEC-`)와 계획 보고(`PLAN-`)로 두 번 멈추고, 원인 조사는 7절의 "추측하지 말고 잰다" 한 줄이 전부였다.

참고한 것(011에 정리):

- mattpocock `diagnosing-bugs`: 재현 루프를 먼저 만들고, 재현을 최소화하고, 가설 3~5개에 순위를 매기고, 맞는 경계에 회귀 테스트를 두고, 진단 로그에 태그를 붙인다.
- superpowers `systematic-debugging`: 원인 조사 전에는 고치지 않는다.
- Kiro `bugfix.md`: 현재 동작, 기대 동작, 바뀌면 안 되는 동작으로 버그를 적는다.

## 선택지와 결정

### 1. 몇 번 멈추나

- **요구와 계획 두 번(지금).** 기능 개발과 같다.
- **버그 보고 한 번.** (채택, AI 추천)

사용자의 말: "버그는 이미 명확하게 맞는 동작이 있는데 그 동작을 안 하는 게 문제니까, 요구 파악보다는 원인 분석(어디를 어떻게 고쳐야 한다)과 고친 부분이 다른 부분에 끼칠 영향도 파악, 대책(계획) 세우기로 가서 대책에 대해서만 사용자에게 묻는 게 맞겠지?"

- 버그 문서 하나에 원인, 영향도, 대책을 쓰고 `BUG-<이름>`으로 한 번 판정받는다. 대책의 작업 표가 계획을 대신한다. 작업 표의 보호 대상 변경 칸은 계획의 칸처럼 판정받은 범위가 된다([014](./014-plan-approval-covers-protected-changes.md)).
- AI가 더한 것:
  - 이미 생긴 피해(틀린 값으로 저장된 데이터 등)도 영향도에 넣는다. 바로잡을지는 ③이라 같은 보고에서 묻는다.
  - 맞는 동작이 둘로 갈리는 버그(반올림을 상품마다 할지 합계에서 할지)는 그 선택도 같은 보고에서 묻는다. 따로 멈추지 않는다.
- 원칙 10을 바꿨다. 012는 "요구 정리는 사용자가 보는 동작을 더하거나 바꾸는 작업의 공통 단계"라고 했다. 버그는 맞는 동작의 근거(동작 명세, 문서, 누구나 틀렸다고 보는 결과)가 이미 있으므로 요구를 새로 합의하지 않는다. 근거가 없어 원하는 동작을 새로 정해야 하면 버그가 아니라 기능 개발이다.

### 2. 가설 확인 순서

- **조직마다 설정으로 고른다**(가능성 순, 위험도 순, 속도 순). 사용자가 처음 낸 안이다.
- **고정 규칙: 싸고 가능성 높은 것부터, 지금도 피해가 쌓이는 근거가 보이면 순서와 관계없이 즉시 멈춤.** (채택, AI 추천, 사용자 동의)

사용자는 "조직의 성격에 따라 나뉜다"며 설정을 제안하고 냉정한 판단을 요청했다. AI는 반대했다.

- 세 기준은 고르는 축이 아니라 한 번에 같이 따지는 값이다. 하나만 고르게 하면 나빠진다. "가능성 순"은 5초면 지울 가설을 두고 하루 걸리는 1순위부터 붙잡고, "위험도 순"은 가능성이 거의 없는 보안 가설을 매번 먼저 본다.
- 위험도가 중요한 곳은 순서가 아니라 피해 막기다. 그래서 "지금도 피해가 나고 있을 때"를 따로 두었다(판정 ID `CONTAIN-<이름>`).
- 조직의 성격이 실제로 갈리는 곳은 대책 쪽(먼저 막고 나중에 고칠지, 데이터를 보정할지)이고, 그것은 버그 보고에서 사용자가 정한다.
- 고른 순서와 이유는 버그 문서의 원인 표에 남아 사용자가 볼 수 있다.

가설 결과를 보여 주려고 따로 멈추지는 않는다. 측정하며 진행하고 버그 보고에서 보인다. 가설을 두 번 세워 모두 틀리면 멈추고 정보를 묻는다. 작은 수정의 "가설 3번 틀림"은 작은 수정을 버그 수정으로 올리는 조건으로 그대로 둔다.

### 3. 재현이 안 되면

- **멈추고 묻는다.** (채택)
- 사용자가 더한 것: "재현이 되는 순간을 나중에 포착할 수 있는 방법을 알려 주는 것도 좋아. 예를 들어 JVM 같은 경우 Full GC가 계속 나면 그 순간 thread dump를 뜨도록 하는 스크립트나 옵션값을 준다든지." 그리고 이런 장치가 부하를 주거나 동시다발로 큰 파일을 만들 수 있으니 주의 사항도 같이 알려 달라고 했다.
- 결정:
  - 재현 대기 보고에 다음에 생길 때 그 순간을 잡는 방법을 넣는다.
  - 방법마다 주의 다섯 가지를 쓴다: 크기·개수 상한, 성능 부하, 개인정보·비밀값, 끄는 시점, 판정.
  - AI가 바로잡은 사실: 힙 크기에 비례해 커지는 것은 힙 덤프이고, 스레드 덤프는 보통 작지만 반복해 뜨면 개수가 쌓인다. 힙 덤프에는 메모리의 비밀번호·토큰·개인정보가 그대로 들어간다.
  - 운영 설정이나 배포를 바꾸는 장치는 ③이라 결정(`CAPTURE-<이름>`)으로 받는다. 저장소를 고쳐야 하면 버그 브랜치가 아니라 main에서 딴 `chore/capture-<이름>`에서 PR로 올린다. 장치는 고침보다 먼저 병합되어야 하기 때문이다.
  - 기다리는 동안 상태 파일 "다음 할 일"에 `재현 대기: <잡는 방법>, <끄는 날짜>`를 둔다. `status.mjs`가 이미 "다음 할 일" 줄을 모아 보여 주므로 스크립트는 바꾸지 않았다.

### 4. 재현 테스트를 언제 커밋하나

- 재현하자마자 커밋한다. 브랜치 CI가 빨개지고, 대책이 수정되면 버려질 수 있다.
- **버그 보고가 통과하면 버그 문서와 함께 커밋한다.** (채택, AI 추천)

이 커밋은 실패 테스트를 담고 있어 첫 고침 커밋까지 push하지 않는다. 새 테스트를 덧붙이는 것이라 훅에는 걸리지 않는다.
020 시뮬레이션에서 나온 "커밋하지 않은 재현 테스트를 요구·계획 커밋 동안 어떻게 두나"는 이것으로 풀린다. 작은 수정에서 버그 수정으로 올릴 때는 멈추지 않고 재현 테스트를 그대로 둔 채 이어 가며, 보류(stash)는 기능 개발로 올릴 때만 한다.

### 5. 이름

- 사용자: "bug-fix/<이름>이나 fix/bug-<이름> 같은 식으로 bug인지 알 수 있고, 이름만으로 특정할 수 있어야 하지 않을까?"
- AI 추천, 사용자 동의: `bugfix/<이름>`. 다른 브랜치처럼 첫 마디가 종류를 말하고, 로그 이름에 쓰는 작업 이름(브랜치의 첫 마디를 뺀 것)이 `bug-` 없이 남는다. `fix/`는 작은 수정에 그대로 쓴다.
- 이름은 `<영역>-<증상>`. 영역은 동작 명세의 영역 이름이다.
- 사용자가 더한 것: "비슷한 곳에서 나중에 다시 문제가 생겼다면 판정 ID를 다르게 지어야 할 텐데, 비슷한 버그임을 이름만 보고도 알 수 있으면 좋겠다."
  - 영역을 앞에 두어 같은 영역의 버그가 파일 목록에서 모인다.
  - 같은 증상이 다시 나면 `-2`, `-3`을 붙인다. 날짜는 로그 이름에 이미 있고, 번호는 몇 번째 재발인지 바로 보인다.
  - 이전 ID를 다시 쓰는 안은 버렸다. 판정 기록과 로그가 ID로 구분되어 두 번의 기록이 섞인다.
  - 재발이면 버그 문서에 이전 버그, 그때 원인, 그때 회귀 테스트가 이번에 못 잡은 이유를 쓴다. 이름보다 이 항목이 재발 방지에 더 중요하다.

| 쓰는 곳 | 형식 |
| --- | --- |
| 브랜치 | `bugfix/<영역>-<증상>` |
| 판정 ID | `BUG-<영역>-<증상>` (대책을 다시 받으면 `-대책2`) |
| 버그 문서 | `docs/spec/bug-<영역>-<증상>.md`, 끝나면 `docs/archive/spec/` |

`log-new.mjs`는 ID에 작업 이름이 들어 있으면 붙이지 않으므로 `bugfix/cart-total-mismatch`의 `BUG-cart-total-mismatch` 로그는 `<날짜>-BUG-cart-total-mismatch.md`가 된다. 스크립트는 바꾸지 않았다.
대화에서 든 예시 `cart-total-rounding`은 시뮬레이션에서 "증상이 아니라 원인"이라는 지적을 받아 문서에서는 `cart-total-mismatch`로 바꿨다(아래).

## 시뮬레이션과 보완

새 컨텍스트의 에이전트 셋(Claude Code 서브 에이전트, Codex, Antigravity의 Gemini 4 Argon)에 같은 시나리오 셋을 읽기 전용으로 돌렸다. 사용자가 세 도구를 골랐다.

1. 1원 오차 재발: 작은 수정으로 시작해 가설 3번 틀림, 틀린 값을 기대값으로 굳힌 기존 테스트, 이미 1원 적게 결제된 주문 120건
2. 운영에서만 나는 JVM 멈춤: 재현 안 됨, JVM 옵션이 보호 경로, 에이전트는 운영 접근 권한 없음
3. 다른 사람 이름의 알림 메일: 조사 중 캐시 키 누락 근거, 지금도 발송 중

세 도구가 공통으로 찾은 빈 곳과 고친 것:

| 빈 곳 | 고친 것 |
| --- | --- |
| 맞는 동작이 갈리는 버그는 재현 테스트의 기대값을 버그 보고 전에 정할 수 없음 | 추천 쪽 값으로 쓰고 보고에 밝힘. 다른 쪽을 고르면 커밋 전에 고침 |
| CAPTURE·CONTAIN으로 멈출 때 커밋하지 않은 재현 테스트·진단 로그가 남아 approve가 실패하거나 다른 브랜치로 딸려 감 | 공통 규칙: 고쳐 본 코드는 되돌리고 나머지는 작업 보류(ID `BUG-<이름>`) |
| 막는 방법이 저장소 안·밖 둘 다 후보면 보고 전에 로그를 쓸 브랜치를 정할 수 없음 | 보고와 로그는 늘 버그 브랜치. 저장소 변경은 통과 뒤 별도 브랜치에서 같은 ID로 approve |
| 켠 장치·막은 조치를 푸는 단계와 ID가 없음. 같은 ID 재사용은 금지라 막힘 | `-off` ID와 브랜치, 또는 대책 표의 마지막 행. 막은 뒤 막혔는지 확인 |
| 통과 커밋을 push하지 말라는 지시와 정지 전 상태 파일 push가 부딪힘 | 첫 고침 전에 멈춰야 하면 push하고, 브랜치 CI 실패가 예상된 것이라고 보고에 씀. SKILL.md 5절에도 예외를 적음 |
| CONTAIN 기준에 정도가 없어 1원 오차에도 멈출 수 있고, 반대로 신고 자체가 개인정보 노출인데도 재현을 먼저 함 | 원인 확인 전이고 쌓일 피해가 막는 부작용보다 클 때만. 원인을 확인했으면 버그 보고로. 신고된 증상 자체가 피해면 1단계에서 봄 |
| 작은 수정에서 틀린 가설을 버그 수정의 가설 묶음으로 세는지 없음 | 첫 묶음으로 셈 |

한두 도구만 찾은 것도 고쳤다: 재현 조건을 모르면 가설로 좁혀 재현을 만든 뒤에야 "재현이 안 될 때"로 감(간헐적 버그가 바로 CAPTURE로 빠지던 문제), 잡힌 자료의 전달과 개인정보 거르기, 끄는 날짜까지 안 잡히면 끄고 연장을 물음, 기존 테스트가 바로 그 경우면 새 테스트 대신 기대값을 고친 것을 재현으로 삼음, 피해 정리 행은 바로잡지 않기로 하면 다시 보고하지 않고 지움, 피해 정리 결정이 늦어지면 고침 PR을 먼저 엶, 보안·개인정보 피해면 통지 여부를 CONTAIN에서 물음, 막는 코드 변경도 테스트를 통과해야 배포됨, 이름은 증상으로 30자 이내(긴 이름은 `log-new.mjs`의 40자 자르기에 걸림), 동작 명세가 없는 영역, 마감 커밋과 커밋 메시지 규칙, SKILL.md 작은 수정 행의 "버그면 원인도 분명함", 7절 브랜치 목록, 보고 단계 이름.

## AI가 정한 세부

- 버그는 제품 명세의 기능 지도에 넣지 않는다(011에서 미룬 질문). 기능 지도는 기능의 목록이고, 버그 이력은 `bug-<영역>-` 파일로 찾는다.
- 기능 ID에 `bug-`로 시작하는 이름을 쓰지 않는다. 버그 문서와 파일 이름이 겹친다.
- 버그 문서의 기대 동작은 마감 때 동작 명세에 합친다. 012의 다시 볼 신호("버그 수정이 동작 명세를 거치지 않아 명세와 테스트가 어긋난다")에 대한 답이다.
- 진단 로그 태그는 `[bug:<이름>]`이고, 커밋 전에 `git grep`으로 남은 것이 없는지 본다.
- 원인을 확인하려고 잠깐 고쳐 볼 수는 있지만 버그 보고 전에 되돌린다. "원인 조사 전 수정 금지"를 지키면서 실험은 막지 않는다.
- 이미 생긴 피해를 바로잡는 운영 데이터 실행은 대책의 별도 행이고, 바꿀 건수를 본 뒤 그 행의 결정 보고로 한 번 더 받는다.

## 다시 볼 신호

- 가설 확인 순서에 대한 불만이 반복된다(설정 안을 다시 본다).
- 버그 보고가 너무 커서 사용자가 대책을 읽지 않고 통과시킨다.
- `bugfix/`와 `fix/`의 경계가 자주 틀린다(작은 수정으로 시작해 매번 올라옴, 또는 그 반대).
- 재현 대기 상태의 버그 브랜치가 쌓여 세션 시작 출력이 길어진다.

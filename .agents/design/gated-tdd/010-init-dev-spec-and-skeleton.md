# 010. 초기 개발은 명세와 기능 지도를 결정 게이트로 먼저 합의하고, 첫 기능은 골격으로 만든다

- 날짜: 2026-10-16
- 상태: 대체됨 (012)
- 반영: skill-storage 1.7.0

## 배경

[009](./009-lifecycle-audit-and-structure.md) 점검의 G1~G4다. 사용자의 질문은 "개발 계획을 세우기 전에 필요한 단계(요구사항 수집, 기능 명세 추출)는 다루지 않는가, 초기 프로젝트 시작부터 이 스킬을 쓰면 안 되는가"였다.
막는 규칙은 없었지만 다음이 비어 있었다. 명세 문서와 그 승인 시점, 기능 여럿을 묶는 상위 층, 테스트 도구가 없는 저장소의 부트스트랩 순서, 버리는 실험의 규칙이다.

## 선택지

명세 단계의 형태:

1. **`docs/spec/` 문서와 결정 게이트.** (채택)
   - 장점: 기능 지도(기능 ID, 선행, 사용자가 해볼 흐름, 만들 순서)가 기능별 계획들의 목차가 되어 G2까지 함께 메운다.
   - 장점: 명세 승인은 판정 질문 ②(합의 변경, 모호한 요구 해석)를 계획보다 앞으로 당긴 것이다. "결정은 앞에서 한 번에 받는다"는 [002](./002-three-gates-and-ratchet.md)와 같은 방향이다.
   - 단점: 승인 지점이 하나 늘어난다.
2. **계획 문서 앞부분에 요구 절을 통합한다.**
   - 장점: 파일이 늘지 않는다.
   - 단점: 기능 여럿을 묶는 상위 층(G2)이 여전히 없다.
3. **`grill-me-plus`에 위임한다.**
   - 장점: 이미 있는 스킬을 쓴다.
   - 단점: `DECISIONS.md`는 결정 기록이지 명세가 아니다. 목적, 성공 기준, 범위, 기능 지도를 담을 자리가 없다.

## 결정

1을 고른다. 사용자가 추천안을 그대로 골랐다. 상세는 `skills/engineering/gated-tdd/references/init-dev.md`에 있다.

- 순서: 최소 도입 → 명세(결정 보고 후 멈춤) → 골격 계획 → 골격 사이클과 첫 확인 지점 → 기능 지도 순서대로 기능별 계획.
- 명세가 통과하기 전에는 짓지 않는다(제품 코드, 프로젝트 생성, 의존성 설치, 계획 작성). 읽기, 조사, 동의받은 spike는 된다.
- 명세 대화는 열린 질문 하나로 시작하고, 되읽어 주며, 추측을 표시한다. 사용자가 건너뛰면 AI가 정한 기본값을 "누가 정했나"에 모두 적고 같은 명세 보고로 받는다.
- 명세 보고는 결정 보고의 한 종류이고, "AI가 정한 것"을 판단 재료에 반드시 넣는다.
- 명세는 살아 있는 문서다. 기능 추가·삭제, 성공 기준·범위 변경, 기능 지도 순서 변경은 판정 질문 ②로 결정이다.
- 첫 기능은 가장 얇은 흐름 하나를 끝에서 끝까지 통과시키는 골격이다. 행은 프로젝트 생성, 테스트 러너, 첫 흐름, CI, 합의했을 때만 배포다. 첫 흐름 직후에 첫 확인 지점을 둔다([004](./004-checkpoints-at-feature-bundles.md)의 토대 규칙).
- spike는 사용자 동의 후 `spike/<주제>` 브랜치에서 테스트·계획·게이트 없이 하고, 배운 것만 로그로 남기며 코드는 병합하지 않는다.

AI가 정한 세부(사용자와 따로 논의하지 않음):

- 기능 ID는 영문 소문자와 하이픈으로 한 번 정하면 바꾸지 않고, 계획 파일 이름에 쓴다. addyosmani의 capability map 규칙을 따랐다.
- 테스트 러너의 고의 실패 테스트는 확인만 하고 커밋하지 않는다. 커밋 후 지우면 테스트 파일 삭제라 `pre-commit`의 보호 대상에 걸린다.
- spike에서 의존성 추가처럼 훅에 걸리는 변경이 필요하면 저장소 밖 임시 폴더에서 한다. spike 브랜치도 같은 훅을 쓰고, `--no-verify`는 금지이기 때문이다.
- 원격에 main이 없으면 훅을 설치하기 전에 빈 첫 커밋을 main으로 push할지 묻는다. 설치 뒤에는 `pre-push`가 main push를 막아 PR 대상이 생기지 않는다.

## 버린 것과 미룬 것

- addyosmani의 단계별 사람 검토(명세, 계획, 작업, 구현마다 승인): 승인 피로를 다시 만든다([001](./001-approval-boundary-by-questions.md)). 계획의 게이트 확정과 명세 승인으로 충분하다고 봤다.
- addyosmani 명세의 Commands, Code Style, Boundaries(Always/Ask/Never) 절: 명령과 코드 스타일은 저장소 `AGENTS.md`의 몫이고, Boundaries는 판정 질문과 `.gated-tdd.json`의 `decide`가 이미 맡는다.
- superpowers의 builder check(새 서브에이전트가 명세만 읽고 계획을 세울 수 있는지 점검): 서브에이전트가 있는 도구에 묶여 미뤘다. 명세 품질 문제가 반복되면 다시 본다.
- 골격 단계의 결정 보고를 하나로 묶는 안: 판정 기록은 스테이징된 트리마다 필요해, 커밋이 다르면 판정도 따로 받아야 한다. 묶는 규칙을 만들지 않았다.

## 다시 볼 신호

- 골격 단계에서 결정 정지가 연달아 생겨 사용자가 내용을 보지 않고 통과시킨다.
- 명세가 기능 개발 중에 자주 바뀐다. (명세 대화가 얕았거나, 명세가 너무 상세함)
- 사용자가 명세 대화를 자주 건너뛴다. (대화가 무거움)
- 기능 하나짜리 요청에도 에이전트가 명세부터 시작한다. (작업 유형 판별이 넓음)

# 020. 작은 수정은 요구·계획 없이 커밋 하나로 처리하고, 커지면 올린다

- 날짜: 2026-10-20
- 상태: 채택
- 반영: skill-storage 1.8.0

## 배경

[011](./011-maintenance-backlog.md) M2다. 저장소가 이 절차를 채택하면 오타 하나도 요구 보고와 계획 보고를 거쳐야 했다. 사용자가 처음 낸 의견은 이랬다. "작은 수정까지 계획 문서를 만들면 번거롭긴 할 것 같다. 하지만 작은 수정이라는 단위를 잘 정의하는 게 중요할 것 같다."

정의 기준을 고를 때 사용자는 "솔직히 뭐가 좋을지 판단이 잘 안 선다"며 다른 스킬 모음 조사를 요청했다. 네 곳을 서브 에이전트로 같은 질문에 답하게 했다.

| | superpowers (obra, v7.0.0) | Matt Pocock skills | pstack (cursor/plugins, gstack 포크 보조) | Addy Osmani agent-skills |
| --- | --- | --- | --- | --- |
| 크기 기준 | 필요한 것이 요청에 다 있나 | 한 세션에 끝나나 | 따로 없음. 작으면 절차를 안 씀 | 30분, 여러 파일·모듈, 수용 기준 3줄 이하, 제목의 "그리고" |
| 누가 정하나 | AI가 알리고 사용자가 뒤집음 | 사용자가 명령으로 고름 | AI | AI |
| 작을 때 생략 | 설계·계획 문서 | 명세·티켓 | 거의 전부. 절차 안에서는 `skip: 이유`를 남김 | 명세·계획. 수용 기준 두 줄은 남김 |
| 커지면 | 멈추고 말하고 올림(기준 없음) | 규칙 없음 | gstack 포크: 파일 5개 초과, 가설 3번 실패면 멈춤 | 범위 밖 발견은 고치지 않고 적어 두고 물음 |
| 버그 | 원인 조사 후 재현 테스트 | 증상을 재현하는 실패 명령 하나 먼저 | 재현은 항상 먼저, 테스트는 쌀 때만 | 재현 테스트 먼저, 예외 없음 |
| 문구·화면 | 사람이 읽는 문구에는 테스트 안 씀 | 규칙 없음(제외 제안은 거절됨) | 화면은 전후 캡처 | 동작 영향 없는 문구·설정은 TDD 제외, 화면은 전후 스크린샷 |

공통점은 네 가지다. 버그는 작아도 재현부터 한다. 커지면 멈추고 올린다. 문구·화면에는 억지 테스트를 쓰지 않는다. 크기는 AI가 판단하되 사용자가 바꿀 수 있다. 공통으로 약한 곳은 "얼마나 커지면 올리나"다. 이 스킬은 판정 질문과 훅으로 그 기준을 분명하게 만들 수 있다.

## 선택지

### 정의 기준

1. **판정 질문 기준에 조사 결과를 합친 정의.** (채택)
   - 진입 조건: ①요청이 분명하고 수용 기준을 한두 줄로 쓸 수 있음 ②커밋 하나로 끝남 ③판정 질문 ②③·보호 대상에 걸리지 않음 ④사람이 봐야 하면 확인 한 번
   - 올리는 조건: 커밋 둘 이상 필요, ①②③이 새로 생김, 훅이 막음, 가설 3번 실패
   - 장점: 이 스킬의 기존 언어(판정 질문, 훅)를 그대로 쓴다. 보호 대상은 기계적으로 걸러진다.
2. **1에 숫자 상한(바뀌는 파일 N개)을 더한다.**
   - 장점: AI 판단에 기대지 않는다.
   - 단점: 파일 수는 위험과 맞지 않는다. 한 줄 권한 변경은 못 잡고(조건 3이 잡음), 여러 언어 파일의 문구 수정은 정당한데도 걸린다. 사용자: "숫자 상한은 굳이?" 커밋 하나 조건이 이미 상한 역할을 한다.
3. **사용자가 직접 고른다(Matt Pocock 방식).**
   - 단점: 사용자가 매번 경로를 말해야 한다. 이 스킬은 AI가 판단하고 근거를 드러내는 구조다.
4. **크기 기준(파일·줄 수)만 쓴다.**
   - 단점: 2와 같은 이유로 의미와 어긋난다.

### 문구·화면·설정의 테스트

- **테스트 대신 확인 방법을 기록한다.** (채택, 사용자 선택) 동작을 바꾸는 수정만 실패 테스트를 먼저 쓴다. 네 곳 모두 이 방향이다. 동작 영향이 애매한 설정은 테스트 쪽으로 보낸다(Addy Osmani 조사에서 나온 주의점).
- 항상 테스트 먼저: 문구 일치만 보는 형식적인 테스트가 생긴다.

### 기록

- 사용자: "로그 및 커밋 메시지 둘 다 해야 하지 않을까. 로그로 남기고 로그를 기반으로 커밋 메시지를 작성하면 어때?" 그대로 채택한다. `log-new.mjs`로 항목을 만들고, 커밋 제목은 INDEX 결론 한 줄, 본문은 수용 기준·원인·확인 방법이다.

### 사람이 봐야 하는 작은 수정(④)

- **작은 수정 + 확인 한 번.** (채택, 사용자가 추천안 선택) 고치고 커밋한 뒤 전후 캡처와 함께 확인을 받는다. 처음에는 "확인이 통과하면 PR을 연다"였으나 시뮬레이션 뒤 순서를 바꿨다(아래 "시뮬레이션 뒤 보완").
- 기능 개발 절차로 보냄: 버튼 색 하나에 요구와 계획은 과하다.

### 시뮬레이션 뒤 보완

새 컨텍스트 에이전트 셋에게 도입된 쇼핑몰 저장소를 가정하고 요청 하나씩을 줬다. 오타("비밀번호가 틀렸습니디"), 결제하기 버튼 색(#2563eb), 해외 상품 합계 1원 오차(조사하면 반올림 위치 결정과 라이브러리 설치가 드러남)다. 셋 모두 기대한 경로를 탔다. 오타와 색은 작은 수정과 확인 한 번으로, 1원 오차는 고치기 전에 올렸다. 지시가 모자라 짐작한 곳 10개를 고쳤다. 사용자는 항목별 설명을 보고 모두 받아들였고, 다시 시뮬레이션하지 않고 반영하기로 했다.

- **확인 전에 PR을 연다.** 선택지는 둘이었다. "확인 통과 후 PR"은 PR 미리보기 주소(Vercel 등)를 확인에 쓸 수 없다. "PR 먼저"는 병합을 사용자가 고르므로 위험이 늘지 않고, PR 본문에 "확인 대기"를 적는다. 후자를 채택했다.
- **확인 결과 기록 커밋은 "커밋 하나"에 세지 않는다.** 확인 결과를 적으려면 커밋이 하나 더 생겨 조건과 부딪혔다. 기록 파일만 바꾸는 커밋으로 한정하고, 코드를 다시 고치면 커밋 둘 이상으로 본다.
- 조건은 조사하면서 다시 본다. 재현 테스트의 기대값이 정하지 않은 선택에 기대면 ①이다.
- 채택 선언 문구를 "코드를 바꾸는 작업(작은 수정 포함) 전에"로 넓혔다. 색 변경이 "기능 개발, 버그 수정, 리팩터링" 어디에 드는지 애매했다.
- 재현의 범위(오타는 틀린 곳, 새로 바꾸는 요청은 수정 전 캡처), 커밋 앞머리(`fix:`/`chore:`, 저장소 규칙 우선).
- 캡처는 있는 브라우저 도구로 하고 설치하지 않는다(설치하면 보호 대상 변경으로 올라감). 파일은 저장소 밖에 둔다.
- 사용자가 값을 정해 준 시각 변경은 시안을 만들지 않는다(SKILL.md 7절).
- 로그 템플릿 칸과의 대응, STATUS는 ④면 "확인 대기"에 쓴다.
- 올린 뒤에는 올림 알림과 요구 첫 질문을 한 메시지로 보내고, 기능 ID가 정해지면 브랜치를 `feat/<기능 ID>`로 바꾼다.
- 고치지 않은 것: STATUS "마지막 커밋"에 그 커밋 자신의 해시를 쓸 수 없는 문제 등, 작은 수정 전부터 있던 작은 불편.

### 두 번째 시뮬레이션 뒤 보완

보완한 곳을 겨냥해 셋을 다시 돌렸다. 오타 확인이 거절되는 경우("끝에 마침표가 빠졌어"), 옛 채택 문구 저장소에서 버튼 색을 Vercel 미리보기로 확인하다 세션이 끊기는 경우, 1원 오차에서 올린 뒤 답을 받는 경우다. PR 먼저 열기, 새 세션의 확인 대기 재요청, 시안 생략, 올림 메시지 한 번, 브랜치 이름 변경은 의도대로 됐다. 고친 것은 이렇다(사용자가 항목별 설명을 보고 받아들임).

- **확인에서 나온 고침 커밋도 세지 않는다.** 첫 보완이 만든 충돌이다. 조건 2의 "코드를 다시 고쳐야 하면 커밋 둘 이상"과 9단계의 "한 커밋으로 끝나는지 다시 본다"가 부딪혔다. 선택지는 "확인 거절이면 항상 올림"과 "사용자가 값을 정해 준 한 커밋이면 남음"이었다. 앞의 것은 마침표 하나로 요구와 계획을 다시 하게 되어 후자를 채택했다. 반복 횟수 상한은 두지 않는다(숫자 상한을 쓰지 않는다는 앞의 결정과 같은 이유).
- **PR을 연 뒤 올리면 브랜치와 PR을 그대로 두고 본문에 "올림, 병합하지 말 것"을 적는다.** 초안(draft) PR로 돌리는 방법은 무료 플랜의 비공개 저장소에서 쓸 수 없어 택하지 않았다.
- **올린 이유가 조사로 드러난 선택이면 첫 질문에서 바로 묻는다.** requirements.md의 "선택지를 먼저 내밀지 않는다"에 예외를 하나 둔다. 에이전트가 규칙을 지키려 돌려 묻자, 사용자가 결국 선택지로 답할 수밖에 없었다. 이 선택지는 AI의 제안이 아니라 조사한 사실이다.
- 재수정과 통과 기록 커밋의 형식, 통과 상태 이름(`통과 (수정 N건)`).
- 유형과 근거는 첫 정지 보고의 전제에, 계획 대비 위치는 `작은 수정 (요구·계획 생략)`.
- 보호 대상이 필요하다는 것을 알면 훅을 기다리지 않고 올린다.
- 캡처는 세션이 바뀌어도 남는 곳에 두고 경로를 로그에 적는다.
- SKILL.md 유형 표의 작은 수정 행에 ①과 "기능 개발 신호와 겹쳐도"를 더했다.
- 미룬 것: 올린 버그를 기능 지도에 넣을지, 커밋하지 않은 재현 테스트를 요구·계획 커밋 동안 어떻게 둘지는 M1([011](./011-maintenance-backlog.md))에서 정한다.

### 세 번째 시뮬레이션 뒤 보완

확인을 두 번 거절하는 경우로 다시 돌렸다. "마침표 빠졌어"는 작은 수정으로 남고, "더 부드럽게, 다른 문구도"는 PR을 연 채 올라가 위 보완이 풀린 것을 확인했다. 새로 보인 빈 곳을 고쳤다.

- **PR을 연 뒤 올릴 때, 이미 고친 것이 그 자체로 맞으면 그 PR을 마무리하고 커진 일은 새 `feat/` 브랜치에서 한다.** 두 번째 보완의 "같은 브랜치에서 잇는다"를 한 경우로 줄였다(방향 변경, 사용자 승인). 그대로 두면 맞게 고친 오타가 말투 작업이 끝날 때까지 main에 못 들어가고, `fix/` 브랜치에서 기능을 개발하게 되어 "기능은 `feat/<기능 ID>`에서"와도 어긋났다. 고친 것이 커진 일에 휩쓸리는 경우(색 하나가 색 체계 전체로)는 같은 브랜치에서 잇는다. 어느 쪽으로 봤는지는 전제에 써서 사용자가 뒤집을 수 있게 했다.
- 재수정 때 INDEX 결론을 최종 값으로 고치고 커밋 제목도 거기서 쓴다.
- 올릴 때 로그·INDEX 상태 `올림`, STATUS "확인 대기" 비움, `사용자 답 대기`, 다음 판정 커밋에 함께 넣음.
- ④면 "발견했지만 안 건드린 것"을 첫 확인 보고에 넣는다. 시뮬레이션에서 사용자가 첫 확인 때 바로 그 점(마침표)을 지적했다.

### 네 번째 시뮬레이션 뒤 보완

오타(마침표 뒤 "더 부드럽게, 다른 문구도")와 버튼 색("결제 화면 색을 통째로 다시")으로 두 경우를 돌렸다. 둘 다 의도대로 갈렸고, 나눈 뒤의 처리에서 빈 곳이 나왔다.

- **이미 고친 것이 맞아 보여도 AI가 통과로 적지 않는다.** 세 번째 보완은 AI가 "맞다"고 판단하면 `통과`를 기록하게 해서, 무응답을 통과로 해석하지 않는다는 SKILL.md 5절과 부딪혔다. 올림 메시지에서 통과 여부를 첫 질문과 함께 묻고, 답이 올 때까지 `확인 대기`로 둔다. 멈춤은 늘지 않는다.
- **커진 일의 `feat/` 브랜치는 7절 선행 기능 규칙대로 딴다.** 세 번째 보완은 "main에서 새로 딴다"였는데, 마무리한 PR이 병합 전이면 같은 줄을 두 브랜치가 고쳐 충돌한다.
- **휩쓸린 경우도 `fix/` 브랜치에서 기능을 개발하지 않는다.** 기능 ID가 정해지면 그 `fix/` 브랜치에서 `feat/<기능 ID>`를 따고 옛 PR은 댓글을 달고 닫는다. push한 브랜치 이름을 바꾸면 PR이 끊기고, 그대로 두면 브랜치 이름과 PR 제목이 내용과 어긋난다. 선택지는 `fix/` 브랜치 예외 허용, PR 제목만 고치기, 새 브랜치로 옮기기였고, 규칙에 예외를 만들지 않는 마지막을 골랐다.
- 커밋 앞머리의 "저장소 규칙"은 `AGENTS.md`나 기여 안내 문서에 적힌 것만이다. 기존 커밋 모양까지 규칙인지 세 회차 연속 망설였다.

## 결정

- `references/maintenance.md`를 새로 만들고 "작은 수정" 절차를 둔다([009](./009-lifecycle-audit-and-structure.md)에서 정한 파일 이름).
- SKILL.md 0절 작업 유형 표에 "작은 수정" 행을 더하고, 2절 첫머리에 "작은 수정은 이 절을 거치지 않는다"를 쓴다.
- 조사에서 가져온 것: 시작할 때 한 줄로 알리기(superpowers), 수용 기준 한두 줄과 범위 밖 발견을 고치지 않고 적기, 완료 보고 세 칸(Addy Osmani), 생략한 단계를 기록에 남기기(pstack), 가설 3번 실패 시 올리기(superpowers·gstack), 재현 먼저(네 곳 공통).
- 가져오지 않은 것: 작은 수정도 채팅 승인을 받는 하드 게이트(superpowers), "의심되면 명세부터"(Addy Osmani), 작으면 절차 밖으로 나가기(pstack), 테스트마다 seam을 사용자에게 확인(Matt Pocock). 모두 판정 질문으로 사용자 판정을 좁힌 이 스킬의 구조나, 훅과 기록을 유지하려는 목적과 맞지 않는다.

## 다시 볼 신호

- 작은 수정으로 처리한 변경을 사용자가 자동 진행 내역에서 다시 연다. (진입 조건이 느슨함)
- 작은 수정이 올리는 조건에 자주 걸려 헛걸음이 잦다. (진입 조건이 너무 넓거나, 시작 전 판단이 약함)
- 사용자가 작은 수정마다 PR을 여는 것을 번거로워한다. (여러 작은 수정을 한 브랜치에 묶는 규칙 검토)

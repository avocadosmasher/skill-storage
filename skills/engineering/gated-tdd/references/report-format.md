# 보고 형식

보고의 목적은 사용자가 "맞는 방향으로 가고 있나", "무엇을 정해야 하나"를 스스로 판단할 재료를 갖게 하는 것이다.
결론만 잘라 보여 주면 사용자는 AI가 무엇을 가정했는지 모른 채 판정하게 된다.

## 읽는 사람

보고는 **마지막 정지 보고 이후의 대화를 보지 않은 사용자**가 읽는다고 가정한다.

| AI가 아는 것 | 사용자가 아는 것 |
| --- | --- |
| 읽은 파일, 도구 출력, 오류 메시지, 버린 시도 | 보고에 쓰인 것 |
| 왜 이 방향이 낫다고 봤는지에 대한 추론 | 결론 |
| "사용자는 아마 이걸 원할 것"이라는 가정 | AI가 그렇게 가정했다는 사실 자체를 모름 |

- 도구 결과·파일 내용으로만 알게 된 사실은 사용자가 모른다고 본다. 판정에 쓰이면 보고에 적는다.
- 보고 안에 대상이 없는 지시어를 쓰지 않는다: "그 문제", "기존 방식", "예상대로", "앞서 말한".
- ID는 항상 이름과 함께 쓴다(`A02 가입 API`). 처음 나오는 함수·파일·용어에는 한 줄 설명을 붙인다.

## 두괄식

첫 블록 **결론**만 잘라 읽어도 판정할 수 있어야 한다. 1~3개 bullet로 쓰고, 한 줄로 억지로 줄이지 않는다.

1. 끝난 일과 현재 상태
2. 지금 필요한 판정 (없으면 "판정 필요 없음"과 이유)
3. 판정에 영향을 주는 전제나 주의 (있을 때만)

## 개조식 (한국어)

- 한 줄에 한 사실. "및"으로 셋 이상 잇지 않는다.
- 끝은 명사형으로 맺는다. "~합니다", "~입니다", "~다"로 끝내지 않는다.
- 어미만 바꾼다. 주어·대상·수치·조건은 지우지 않는다("검증 필요"가 아니라 "가입 API의 중복 이메일 처리 검증 필요").
- 시제와 확신도를 어미로 구분한다. 했는지, 할 것인지, 해야 하는지, 추측인지가 섞이면 보고가 사실과 달라진다.

  | 서술형 | 개조식 | 뜻 |
  | --- | --- | --- |
  | 테스트를 추가했습니다 | 테스트 추가함 | 완료 |
  | 캐시가 갱신됩니다 | 캐시 갱신됨 | 상태 |
  | 다음 세션에서 진행할 예정입니다 | 다음 세션에서 진행 예정 | 계획 |
  | 사용자 확인이 필요합니다 | 사용자 확인 필요 | 요구 |
  | 원인은 캐시 만료로 보입니다 | 원인은 캐시 만료로 추정됨 (재현 전) | 추측 |
  | 이 방식이 더 빠릅니다 | 이 방식이 더 빠름 (측정: 320ms → 180ms) | 비교 |

- 예외: 판정 요청, 사용자에게 묻는 질문, 코드·명령·인용, 스크립트가 출력한 줄.
- 적용 범위: 정지 보고, 진행 중 알림, STATUS.md, 로그 항목. 운영가이드와 최종 보고서 본문은 처음 읽는 사람을 위한 문서라 평서문으로 쓴다.

## 목록과 기호

항목이 둘 이상이면 한 문장에 늘어놓지 않고 번호 목록(1. 2. 3. ...)으로 쓴다.
"판정 필요: A, B"처럼 라벨 뒤에 쉼표로 잇는 것도 한 줄 나열이다.
그 아래 하위 목록이 필요하면 번호 대신 bullet(•)을 쓴다. 줄 안에서 구분이 필요해도
em dash(긴 줄표)로 잇지 않는다: 쟁점과 설명은 "선택:", "버린 대안:"처럼 이름 붙은 하위 항목으로
나누고, 화살표(→)는 조작과 그 결과처럼 방향이 있는 짝에만 쓴다.
"이 규칙에 따라 멈춥니다" 같이 스킬 규칙을 인용하는 메타 설명은 쓰지 않는다.

## 우선순위

판단 재료 > 짧음 > 중복 금지.

- 결론은 무엇·얼마나, 아래 블록은 왜·어떻게를 맡는다. 결론의 문장과 수치를 아래에서 그대로 되풀이하지 않는다.
- 줄이다가 판정에 필요한 사실이 빠질 것 같으면 줄이지 않는다.

## 정지 보고의 순서

1. **결론**: 위 "두괄식" 세 가지.
2. **자동 진행 내역**: 마지막 정지 보고 이후 묻지 않고 진행한 단위. 없으면 뺀다.
   ```
   자동 진행 4건
   1. A01 pg 설치: package.json에 pg 추가 (사유: 계획 판정 D1, 보호 대상 변경 칸 범위 안 / 커밋 0f1e2d3)
   2. A02 가입 API: 요청 검증과 저장 (사유: 계획대로, 자동 검사로 증명 / 커밋 1a2b3c4)
   3. A04 로그인 API: 비밀번호 대조 (사유: 계획대로 / 커밋 5d6e7f8)
   4. A04a 오류 응답 형식 통일 (사유: 동작 동일한 리팩터링 / 커밋 9a0b1c2)
   ```
   계획 판정으로 커밋한 보호 대상 변경은 근거(결정 목록 항목, 요구의 바뀌는 동작)를 사유에 쓴다.
   이의가 있으면 사용자는 ID만 말하면 된다. 그 단위를 다시 연다.
3. **계획 대비 위치**: 한 줄. 끝난 확인 지점, 남은 확인 지점, 계획에서 벗어난 것(없으면 "계획 이탈 없음").
   계획이 아직 없으면(도입, 제품 명세, 요구 보고) 절차상 위치와 제품 명세 기능 지도에서의 위치를 쓴다.
4. **내가 이해한 전제**: 결정 보고에는 반드시, 확인 보고에는 전제가 바뀌었을 때 쓴다.
   - 목표·범위를 어떻게 해석했는지, 시스템 상태를 어떻게 가정했는지, 사용자 선호를 어떻게 추측했는지.
   - 항목마다 `확인됨 (근거)` 또는 `추정 (근거, 없으면 "근거 없음")`을 붙인다. 사용자는 틀린 줄만 짚으면 된다.
5. **판단 재료** (결정 보고) 또는 **확인 방법** (확인 보고). 둘 다 필요하면 둘 다 쓴다.
6. **자동 검사**: 돌린 검사마다 통과·실패, 돌리지 않은 범위와 이유.
7. **판정 후**: 통과하면 무엇을 하고, 수정이면 어디부터 다시 하는지 한 줄.
8. **판정 요청**: "직접 확인 후 '통과' 또는 '수정: [문제와 원하는 변경]'으로 알려주세요."

## 결정 보고: 판단 재료

쟁점마다 하위 항목으로 나눈다. 코드가 어떻게 짜였는지가 아니라 왜 이 방향을 골랐는지를 쓴다.

- 지금 정하는 이유: 이 결정이 무엇을 막고 있는지
- 선택: 추천하는 안과 확신도(높음·중간·낮음), 확신도가 무엇에 달렸는지
- 버린 대안: 검토했지만 버린 안과 이유
- trade-off: 이 선택으로 가능해지는 것, 안 되는 것, 미룬 것
- 모르는 것: 판정에 필요한데 확인하지 못한 것 (없으면 뺀다)
- 잘못 정하면: 나중에 되돌리는 비용

pre-commit이 보호 대상 변경으로 막은 경우, 걸린 파일과 이유(보호 경로, 기존 테스트 변경 등)를 결론에 쓴다.

## 확인 보고: 확인 방법

- 해볼 흐름을 번호별로 "조작 → 기대 결과" 짝으로 쓴다.
- **이번 묶음에서 바뀐 구조**: 새로 생긴 모듈·데이터·흐름을 세 줄 이내로. 사용자가 시스템을 계속 이해하게 하려는 것이다.
- 사용자가 직접 실행할 수 없는 환경이면 이유와 확인 시점·장소를 명시한다.

## 예시: 결정 보고

```markdown
**결론**
1. A01 사용자 테이블 마이그레이션 작성 완료, 커밋 전 판정 대기 중임
2. 이메일 중복 허용 여부 결정 필요: 소셜 로그인 도입 시 같은 이메일로 계정 2개가 생길 수 있음
3. 판정 전까지 A02(가입 API) 시작하지 않음

**계획 대비 위치**: 확인 지점 M1(가입 흐름) 전, 남은 행 2개. 계획 이탈 없음

**내가 이해한 전제**
1. 소셜 로그인은 이번 범위 밖, 다음 단계에서 도입 (추정: 계획 제외 범위에 "소셜 로그인"이 있음)
2. 운영 DB에 기존 사용자 없음, 마이그레이션은 빈 테이블 대상 (확인됨: 운영 DB 없음, 개발 DB만 존재)
3. 같은 사람이 계정 여러 개 갖는 것을 원하지 않음 (추정: 근거 없음, 확인 필요)

**판단 재료**
1. 이메일 유일 제약
   • 지금 정하는 이유: A02 가입 API의 중복 처리 방식이 이 결정에 달림
   • 선택(추천, 확신도 중간): `users.email`에 유일 인덱스 추가함. 확신도는 전제 3에 달림
   • 버린 대안: 앱 코드에서만 중복 검사함. 동시 가입 시 중복 생성 가능해 버림
   • trade-off: 중복 가입 원천 차단됨. 소셜 계정 연결은 별도 테이블 필요
   • 잘못 정하면: 데이터가 쌓인 뒤 제약 추가 시 중복 계정 정리 작업 필요

**자동 검사**
1. 마이그레이션 적용·롤백 테스트: 통과
2. 단위 테스트 42개: 통과

**판정 후**: 통과 시 A02 시작, 수정 시 마이그레이션부터 다시 작성함

직접 확인 후 '통과' 또는 '수정: [문제와 원하는 변경]'으로 알려주세요.
```

## 진행 중 한 줄 알림

자동 단위를 마칠 때는 멈추지 않고 한 줄만 남긴다.

```
A02 자동 진행: 가입 API 요청 검증 추가함 (커밋 1a2b3c4)
```

예산 때문에 멈출 때도 묻지 않고 알린다.

```
[예산] 이번 세션 단위 10개 (대리 지표: 단위 수) → STATUS.md 인계 후 정지 (새 세션 권장)
인계: 다음 할 일 A07, 확인 대기 없음
```

## 보내기 전 점검

1. 결론만 잘라 읽어도 판정할 수 있나.
2. 줄 끝이 명사형인가 (판정 요청·질문·코드·인용은 예외).
3. 줄이다가 주어·대상·수치·조건이나 시제(함·예정·필요·추정)가 흐려지지 않았나.
4. 사용자가 "왜?", "그게 뭔데?"라고 물을 만한 곳이 있나. 있으면 그 답을 넣는다.
5. 내 가정 중 사용자가 모를 만한 것이 "내가 이해한 전제"에 들어 있나.

## 시각 정보

글보다 빨리 읽히는 경우에만 쓴다.

| 상황 | 표현 |
| --- | --- |
| 대안 2개 이상을 기준 2개 이상으로 비교 | 표 (행: 대안, 열: 기준). 아니면 bullet 하위 항목 |
| 하위 작업 여럿 중 일부만 끝남 | bullet 뒤에 `[x]`(완료)·`[ ]`(남음). dash로 시작하는 마크다운 체크리스트(`- [x]`)는 쓰지 않는다 |
| 수치 전후 비교 | `응답 시간: 320ms → 180ms` 한 줄. 지표가 여럿이면 표 |
| 배치·색·크기 같은 시각 결정 | 캡처 이미지 경로 (아래 1) |
| 구조·흐름 설명 | 다이어그램 (아래 2) |

다른 스킬은 사용 가능한 스킬 목록에 있을 때만 연계한다. 없으면 자체 형식으로 쓴다.

1. 시각 결정
   • 있으면: Skill 도구로 `capture-compare`를 호출해 비교 시트를 만들고 그 경로를 적는다.
   • 없으면: 같은 조건(창 크기·데이터·상태)에서 후보를 직접 캡처해 경로를 나열한다.
     캡처할 수 없는 환경이면 후보별 차이를 표로 쓰고, 실제 화면에서 볼 위치를 적는다.
2. 구조·흐름
   • 있으면: Skill 도구로 `archify`를 호출해 다이어그램 파일을 만들고 그 경로를 적는다.
   • 없으면: 코드 블록 안에 화살표로 흐름을 그린다. 노드가 10개를 넘으면 그리지 않고
     번호 목록으로 단계를 쓴다.

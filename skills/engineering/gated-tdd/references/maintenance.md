# 유지보수: 작은 수정과 버그 수정

판정 질문과 훅은 두 경로 모두 그대로 적용한다. 고칠 코드에 테스트가 없으면 `references/characterization.md`의 고정 테스트를 함께 따른다.
큰 리팩터링은 `references/refactoring.md`를 따른다. 의존성 업데이트의 전용 절차는 아직 없다. 기능 개발과 같은 절차를 타되 요구를 생략한다(SKILL.md 2절).

## 작은 수정

오타, 원인이 분명한 작은 버그, 문구 변경처럼 요구 문서와 계획 없이 커밋 하나로 끝나는 수정의 경로다.

### 작은 수정이 되는 조건

세 가지가 모두 맞아야 한다. 하나라도 아니면 버그는 아래 "버그 수정"으로, 동작을 바꾸지 않는 정리는 리팩터링(`references/refactoring.md`)으로, 그 밖에는 기능 개발 절차(요구 → 계획 → 사이클)로 간다.
시작할 때는 요청만 보고 판단하고, 조사와 재현을 하면서 다시 본다. 도중에 맞지 않게 되면 "올리는 조건"을 따른다.

1. **요청만으로 무엇을 할지 분명하다.** 인수 기준("이렇게 되면 완료")을 한두 줄로 쓸 수 있고, 선택이 사용자 의도에 달리지 않는다(판정 질문 ①).
   "보기 좋게 바꿔 줘"처럼 기준을 문장으로 쓸 수 없거나 "A로 할까 B로 할까"가 생기면 아니다.
   재현 테스트의 기대값이 아직 정하지 않은 선택에 기대도 ①이다. 예: 1원 오차의 기대값이 반올림을 상품마다 하느냐 합계에서 하느냐에 따라 달라짐.
2. **커밋 하나로 끝난다.** 처음 수정이 작업 표의 한 행이다. 순서나 중간 상태가 생기면 계획이 필요하다.
   다음 커밋은 세지 않는다. ④의 확인 결과만 적는 기록 커밋, 그리고 확인에서 사용자가 고칠 값을 정해 준 고침 한 커밋이다.
   고칠 점이 새 선택을 부르거나 커밋 여러 개가 필요하면 올린다.
3. **판정 질문 ②③에 해당하지 않고 보호 대상을 건드리지 않는다.** 기존 테스트의 기대값 변경, 권한, 데이터, 의존성은 작아도 아니다.
   보호 대상은 훅이 커밋 때 기계적으로 막는다.

고칠 코드에 테스트가 없어도 재현 테스트 하나로 수정이 닿는 결과를 지킬 수 있으면 작은 수정이다. 고정 테스트(`references/characterization.md`)는 요구하지 않는다.

사람이 봐야 하는 변경(판정 질문 ④)은 조건에 걸리지 않는다. 화면·문구 수정은 작은 수정으로 하되 확인을 한 번 받는다.

### 흐름

1. **알림**: 시작할 때 한 줄로 알리고 기다리지 않고 진행한다. `작은 수정으로 처리함: <인수 기준>`. 사용자가 정식 절차를 원하면 기능 개발로 간다.
   고른 유형과 근거(조건을 어떻게 확인했는지)는 첫 정지 보고(확인 보고, 완료 보고, 올림 메시지)의 "내가 이해한 전제"에 쓴다.
2. **브랜치**: 진행 중인 기능과 관련 없으면 main에서 `fix/<짧은 이름>`을 딴다. 도입이 아직 main에 병합되지 않았으면 SKILL.md 7절의 선행 기능 규칙대로 도입 브랜치에서 딴다.
3. **재현**: 고치기 전에 지금 상태를 그대로 보인다. 원인을 추측으로 고치지 않는다.
   - 버그는 증상을 재현한다.
   - 오타처럼 지금 잘못 보이는 것은 틀린 곳(파일과 화면 위치)을 보인다.
   - 색 변경처럼 새로 바꾸는 요청은 수정 전 캡처가 재현을 대신한다.
4. **테스트 또는 확인 방법**
   - 동작을 바꾸는 수정은 실패 테스트를 먼저 쓴다(SKILL.md 3절 Red). 버그는 그 증상을 재현하는 테스트다.
   - 동작을 바꾸지 않는 정리(이름 하나 바꾸기, 함수 하나 추출)는 새 테스트 대신 고칠 코드를 지키는 기존 테스트가 그대로 통과하는 것으로 확인한다.
     지키는 테스트가 없거나 기존 테스트를 고쳐야 하면 작은 수정이 아니다(`references/refactoring.md`).
   - 동작이 없는 문구·화면·설정 변경은 테스트 대신 확인 방법을 정한다. 화면은 전후 캡처, 문구는 바뀐 문장 인용이다.
     문구가 같은지만 보는 테스트는 쓰지 않는다. 동작에 영향이 있는지 애매한 설정은 테스트 쪽으로 간다.
   - 캡처는 이미 쓸 수 있는 브라우저 도구로 한다. 캡처 도구를 새로 설치하지 않는다(의존성은 보호 대상이다).
     캡처 파일은 세션이 바뀌어도 남는 저장소 밖 폴더에 두어 커밋에 섞이지 않게 하고, 경로를 로그 Red 칸에 적는다.
     캡처할 수 없으면 바뀐 문장과 화면 위치를 글로 적는다.
   - 사용자가 값을 정해 준 시각 변경("#2563eb로")은 고를 것이 없으므로 시안을 만들지 않는다(SKILL.md 7절).
5. **고침**: 통과시키는 최소 수정. 하는 김에 다른 곳을 고치지 않는다.
6. **자동 검사**: 영향 범위의 테스트와 저장소 필수 게이트.
7. **기록**: `node scripts/gated-tdd/log-new.mjs "FIX-<짧은 이름>: <제목>" --gate 자동`(④면 `--gate 확인`). 템플릿 칸은 그대로 채운다.
   - 게이트: `자동` 또는 `확인`, 사유는 "작은 수정" (④면 "작은 수정, 사람이 봐야 함")
   - 시작 기준: 브랜치를 딴 main 커밋
   - 문제·요청: 사용자 요청과 인수 기준
   - Red: 재현과 실패 테스트. 테스트가 없으면 확인 방법과 수정 전 상태
   - 수정, 자동 검사, 남은 제약: 기능 개발과 같다

   템플릿 아래에 두 줄을 덧붙인다.
   - `생략: 요구·계획 (작은 수정)`
   - `발견했지만 안 건드림: <무엇, 어디>` (없으면 "없음", 아래 절)

   INDEX 결론 한 줄과 상태 파일의 "최근 3건"을 고친다. 상태 파일에는 확인이 필요 없는 수정은 "자동 진행 내역"에, ④는 "확인 대기"에 적는다.
8. **커밋**: 로그를 바탕으로 커밋 메시지를 쓴다. 제목은 `<앞머리>: <INDEX 결론 한 줄>`, 본문은 인수 기준, 원인(버그면), 확인 방법이다.
   앞머리는 버그·오타면 `fix:`, 동작을 바꾸지 않는 정리는 `refactor:`, 그 밖의 변경(색, 문구 다듬기, 설정)은 `chore:`다. `AGENTS.md`나 기여 안내 문서에 커밋 규칙이 적혀 있으면 그것을 따른다.
   기존 커밋의 모양은 규칙으로 보지 않는다.
   그 영역의 동작 명세(`docs/behavior/`)에 해당 시나리오가 있으면 테스트 위치를 같은 커밋에서 적는다.
9. **마무리**: push하고 PR을 연다.
   - ④가 아니면 완료 보고를 한다.
   - ④면 PR 주소와 전후 캡처로 확인 보고를 하고 **멈춘다.** PR에 미리보기 주소가 생기면 그것으로 확인받는다. PR 본문에 "확인 대기"를 적는다.
   - 확인에서 고칠 점이 나오면 조건 2로 다시 본다. 사용자가 값을 정해 줬고 한 커밋이면 같은 PR에 고침 커밋을 더하고 다시 확인받는다.
     로그는 새로 만들지 않고 같은 항목의 수정 칸에 덧붙이고, INDEX 결론을 최종 값으로 고친다.
     커밋 제목은 8단계와 같은 규칙으로, 고친 INDEX 결론에서 쓴다. 그렇지 않으면 올린다.
   - 확인이 통과하면 로그 머리줄과 INDEX 상태를 `통과`로(고친 적이 있으면 `통과 (수정 N건)`), 상태 파일의 "확인 대기"를 비운다.
     이 기록 커밋의 제목은 `chore: <ID> 확인 통과 기록`이다. 같은 PR에 더하고 완료 보고를 한다.

완료 보고는 세 칸으로 쓴다: 바꾼 것 / 일부러 안 건드린 것 / 우려되는 점. 보고 형식(SKILL.md 4절)을 따르되,
판정할 것이 없으면 결론과 이 세 칸, 자동 검사, PR 주소만 쓴다.

### 올리는 조건

작업 중 하나라도 생기면 정식 절차로 올린다. 버그면 아래 "버그 수정"으로, 동작을 바꾸지 않는 정리면 리팩터링으로, 그 밖에는 기능 개발로 올린다.

| 조건 | 예 |
| --- | --- |
| 커밋이 둘 이상 필요해짐 | 같은 문구가 여러 화면에 흩어져 있어 문구 관리 구조를 바꿔야 함 |
| 판정 질문 ①②③이 새로 생김 | 버그 원인을 보니 "탈퇴한 회원의 댓글을 보여 줄지"를 정해야 함 |
| 보호 대상을 바꿔야 함 (알게 된 때 올린다. 훅은 놓친 경우를 막는 장치다) | 고치려면 라이브러리를 설치하거나 기존 테스트의 기대값을 바꿔야 함 |
| 고정 테스트가 필요해짐 | 테스트 없는 800줄 함수 안의 한 줄이라, 고치면 같은 함수의 다른 계산이 함께 바뀔 수 있음 |
| 원인 가설이 3번 틀림 | 반올림, 타임존, 캐시를 차례로 의심했지만 모두 아님. 구조 문제일 수 있음 |

**버그 수정으로 올릴 때**는 멈추지 않는다. `작은 수정으로 시작했으나 <조건>이 생겨 버그 수정으로 올림`을 한 줄 알리고
버그 수정의 흐름을 이어 간다. 정할 것은 버그 보고에서 함께 받는다.

- 재현 테스트는 그대로 두었다가 버그 보고가 통과할 때 버그 문서와 함께 커밋한다. 미뤄 두지 않는다.
- 원인을 확인하기 전에 고쳐 본 코드는 되돌린다.
- 브랜치는 `bugfix/<버그 이름>`으로 바꾼다. 방법은 아래 기능 개발로 올릴 때의 브랜치 규칙과 같고, `feat/<기능 ID>` 자리에 `bugfix/<버그 이름>`을 쓴다.
- 로그를 이미 만들었으면 머리줄과 INDEX 상태를 `올림`으로 바꾸고, 버그 보고의 판정 커밋에 함께 넣는다.
- 올린 이유가 맞는 동작이 둘로 갈리는 선택(①)이면 버그 보고의 "정할 것"에 넣는다. 맞는 동작의 근거가 없어 새로 정해야 하면 버그가 아니므로 기능 개발로 올린다.

**리팩터링으로 올릴 때**는 아래 기능 개발로 올릴 때와 같이 멈추고 커밋하지 않은 작업을 보류한다. 다른 점은 셋이다.
요구 질문 대신 `references/refactoring.md`대로 계획을 써서 올림 메시지와 함께 계획 보고(`PLAN-<이름>`)를 한다. 브랜치는 `refactor/<이름>`으로 바꾼다(아래 브랜치 규칙에서 `feat/<기능 ID>` 자리).
보류한 작업은 계획이 통과한 뒤 꺼내 그 계획의 행으로 이어 간다.

**기능 개발로 올릴 때**는 멈춘다. 아직 커밋하지 않은 작업은 커밋하지 않고 SKILL.md 7절의 "작업 보류"로 미뤄 두고 보고에 쓴다.
그대로 두면 다음 판정(요구 보고)의 approve가 스테이징되지 않은 변경 때문에 실패한다.
올림 알림과 요구 정리(SKILL.md 2절)의 첫 질문을 한 메시지로 보내고 멈춘다. 따로 정지를 하나 더 만들지 않는다.
조사로 드러난 선택이 올린 이유면, 첫 질문은 그 선택을 근거와 함께 바로 묻는다. 이 선택지는 AI의 제안이 아니라 조사한 사실이다.

```
작은 수정으로 시작했으나 <조건>이 생겨 정식 절차로 올림. 지금까지 한 것: <…>
내가 이해한 전제: <…>
첫 질문: <요구를 정하는 데 필요한 질문>
```

기록: 로그 머리줄과 INDEX 상태를 `올림`으로 바꾸고, 상태 파일의 "확인 대기"에 이 항목이 있으면 비운다.
"다음 할 일"에는 `사용자 답 대기: <첫 질문 요약>`을 쓴다. 상태 파일은 정지 보고 규칙대로 먼저 커밋하고(SKILL.md 1절),
로그와 INDEX는 따로 커밋하지 않고 다음 판정 커밋(요구 보고)에 함께 넣는다.

브랜치는 PR을 열기 전인지 뒤인지에 따라 다르다.

- **PR을 열기 전**: 기능 ID가 정해지면 브랜치 이름을 `feat/<기능 ID>`로 바꾸고(`git branch -m`) 상태 파일 이름도 새 브랜치에 맞춘다.
  원격에 이미 올린 상태 파일 커밋이 있으면 옛 원격 브랜치는 지운다(`git push origin --delete fix/<이름>`). PR이 없으므로 잃는 것이 없다.
- **PR을 연 뒤**(확인에서 고칠 점이 커진 경우): 이미 고친 것이 그 자체로 맞는지 본다. 어느 쪽으로 봤는지는 올림 메시지의
  "내가 이해한 전제"에 쓴다. 사용자가 뒤집으면 그에 따른다.
  - **맞아 보이면**(예: 오타와 마침표는 맞고, 말투를 새로 정하고 싶음): 지금 PR은 작은 수정으로 마무리한다.
    사용자가 통과라고 하지 않았으면 통과로 적지 않는다(SKILL.md 5절). 올림 메시지에 "<ID>는 이대로 통과인가요?"를 첫 질문과 함께 묻고,
    그때까지 이 항목은 `확인 대기`로 둔다. 위의 `올림` 기록은 이 항목에 쓰지 않는다.
    통과라고 하면 로그 머리줄과 INDEX 상태를 `통과`(고친 적이 있으면 `통과 (수정 N건)`)로 바꾸고, 남은 제약에 "<커진 일>은 정식 절차로 올림"을 적어
    `chore: <ID> 확인 통과 기록` 커밋을 그 PR에 더한다. 병합은 사용자가 고른다. 통과가 아니면 아래 휩쓸린 경우로 간다.
  - **커진 일에 휩쓸리면**(예: 버튼 색을 바꿨는데 화면 색 전체를 다시 정하게 됨): 그 PR은 병합하지 않는다.
    기능 ID가 정해질 때까지는 PR을 닫지 않고 본문 맨 위에 "정식 절차로 올림, 병합하지 말 것"을 적어 둔다.
  - 커진 일의 `feat/<기능 ID>` 브랜치는 요구 파일을 처음 쓸 때 딴다(`references/requirements.md`). 어디서 딸지는 SKILL.md 7절의 선행 기능 규칙을 따른다.
    마무리한 PR이 이미 병합됐으면 main에서, 아직이면 그 `fix/` 브랜치에서 딴다. 휩쓸린 경우는 늘 그 `fix/` 브랜치에서 딴다.
    휩쓸린 경우 새 브랜치를 push한 뒤 옛 PR은 "`feat/<기능 ID>`로 옮김" 댓글을 달고 닫는다. 이미 push한 브랜치는 이름을 바꾸면 PR이 끊기기 때문이다.

### 발견했지만 안 건드린 것

작은 수정 중 발견한 다른 문제는 고치지 않는다. 로그에 `발견했지만 안 건드림: <무엇, 어디>`로 적고, 완료 보고의
"일부러 안 건드린 것"에 넣어 따로 할지 묻는다. ④면 첫 확인 보고의 결론에 넣는다. 사용자가 확인하면서 함께 정할 수 있다.
하는 김에 고치면 작은 수정이 조용히 커진다.

## 버그 수정

원인을 찾아야 하는 버그의 경로다. 버그는 맞는 동작이 이미 있으므로 요구 정리(SKILL.md 2절)를 거치지 않는다.
원인, 영향도, 대책을 조사해 버그 문서에 쓰고, 버그 보고 한 번으로 대책만 판정받는다. 계획 파일도 따로 쓰지 않는다. 대책이 계획을 대신한다.

### 버그 수정이 되는 조건

- **버그다.** 지금 동작이 맞는 동작과 다르고, 맞는 동작의 근거가 있다. 근거는 동작 명세나 기능 요구의 시나리오, 문서,
  또는 누구나 틀렸다고 보는 결과(오류 화면, 데이터 손실, 계산 오류)다. 근거가 없어 원하는 동작을 새로 정해야 하면 기능 개발이다.
- **작은 수정이 아니다.** 원인이 분명하지 않거나, 커밋이 둘 이상 들거나, 판정 질문 ②③·보호 대상에 걸린다.
  원인이 분명하고 작은 수정의 조건에 맞으면 작은 수정으로 한다.
- 작은 수정으로 시작했다가 올리는 조건이 생긴 버그도 여기로 온다.

### 이름

이름은 `<영역>-<증상>`이다. 증상은 원인이 아니라 사용자가 보는 것으로 짓는다(`cart-total-mismatch`, `notify-wrong-recipient`).
시작할 때는 원인을 모르고, 원인이 드러나도 이름은 바꾸지 않는다. 영역은 동작 명세(`docs/behavior/<영역>.md`)의 영역 이름을 쓴다.
그 영역의 동작 명세가 아직 없으면 사용자가 알아듣는 영역 이름을 새로 짓고 마감 때 그 파일을 만든다.
영문 소문자와 하이픈으로 30자 이내로 짓는다. 길면 `log-new.mjs`가 제목을 잘라 로그 이름이 겹쳐 길어진다.
영역이 앞에 있어 같은 영역의 버그가 파일 목록에서 한데 모인다.

| 쓰는 곳 | 형식 | 예 |
| --- | --- | --- |
| 브랜치 | `bugfix/<이름>` | `bugfix/cart-total-mismatch` |
| 판정 ID | `BUG-<이름>` | `BUG-cart-total-mismatch` |
| 버그 문서 | `docs/spec/bug-<이름>.md` (끝나면 `docs/archive/spec/`) | `docs/spec/bug-cart-total-mismatch.md` |

- 시작할 때 `docs/spec/`과 `docs/archive/spec/`에서 `bug-<영역>-*`를 찾는다. 사용자가 보는 증상이 같으면 원인이 달라도 재발이다.
  이름 뒤에 `-2`, `-3`을 붙이고(`cart-total-mismatch-2`) 버그 문서의 "이전 버그"를 채운다. 같은 영역의 다른 증상은 새 증상 이름을 쓴다(`cart-coupon-twice`).
- 이전 ID를 다시 쓰지 않는다. 판정 기록과 로그가 ID로 구분되어, 같은 ID를 쓰면 두 번의 기록이 섞인다.
- 버그는 제품 명세의 기능 지도에 넣지 않는다. 기능 지도는 기능의 목록이다. 버그 이력은 `bug-<영역>-` 파일로 찾는다.

### 흐름

1. **알림과 브랜치**: 시작할 때 `버그 수정으로 처리함: <증상 한 줄>`을 알리고 기다리지 않고 진행한다. main에서 `bugfix/<이름>`을 딴다(도입이 아직 병합되지 않았으면 작은 수정의 브랜치 규칙과 같다).
   고른 유형과 근거는 첫 정지 보고의 "내가 이해한 전제"에 쓴다.
   신고된 증상 자체가 지금도 쌓이는 피해(다른 사람의 개인정보가 보임, 데이터가 망가짐)면 재현보다 먼저 아래 "지금도 피해가 나고 있을 때"를 본다.
2. **재현**: 고치기 전에 이 버그에서 빨개지는 빠르고 결정적인 명령 하나를 만든다. 보통 실패 테스트다(SKILL.md 3절 Red).
   - 재현 조건을 모르면(가끔만 남) 코드와 기록을 읽고 3단계의 가설로 조건을 좁혀 가며 만든다. 그래도 만들 수 없을 때만 "재현이 안 될 때"로 간다.
   - 재현 조건을 하나씩 빼 보며 최소로 줄인다. 줄이는 과정이 원인을 좁힌다.
   - 테스트는 사용자가 보는 결과나 데이터 계약을 검증하되, 원인에 가장 가까운 경계(함수, API, 모듈)에 둔다.
     그런 경계가 없어 화면 전체를 돌려야만 재현되면 그 사실을 버그 보고의 우려에 적는다.
   - 고칠 코드를 테스트에서 부를 수 없으면 `references/characterization.md`의 "테스트에서 부를 수 없을 때"대로 한다. 기계적인 틈 만들기는 버그 보고를 기다리지 않고
     `refactor: BUG-<이름> 틈 만들기: <무엇>`으로 바로 커밋하고, 버그 문서의 재현 칸에 적는다. 동작을 바꾸지 않으므로 아래의 "고쳐 본 코드"가 아니다.
   - 기존 테스트가 바로 그 경우를 틀린 값으로 기대하고 있으면 새 테스트를 만들지 않고, 그 기대값을 고친 것을 재현 테스트로 삼는다.
     기존 테스트의 기대값 변경이므로 대책 표 첫 행의 보호 대상 변경 칸에 적는다.
   - 맞는 동작이 둘로 갈려 기대값이 사용자의 선택에 달리면, 추천하는 쪽의 값으로 쓰고 버그 보고의 "정할 것"에 그렇게 썼다고 밝힌다.
     사용자가 다른 쪽을 고르면 기대값을 고친 뒤 커밋한다.
   - 재현 테스트는 버그 보고가 통과할 때까지 커밋하지 않는다.
3. **가설과 측정**: 원인을 측정으로 확인하기 전에는 고치지 않는다(SKILL.md 7절 "추측하지 말고 잰다").
   - 확인할 수 있는 가설을 3~5개 세우고, 가설마다 가능성(높음·중간·낮음)과 확인 비용(명령 하나, 몇 분, 반나절 이상)을 적는다.
   - **싸고 가능성 높은 것부터** 확인한다. 가능성이 낮아도 몇 초면 배제할 수 있으면 먼저 지운다. 고른 순서와 이유는 버그 문서의 원인 표에 남긴다.
   - 확인하다 지금도 피해가 쌓이고 있는 근거가 보이면 순서와 관계없이 아래 "지금도 피해가 나고 있을 때"로 간다.
   - 진단용 로그에는 `[bug:<이름>]` 태그를 붙인다. 커밋 전에 `git grep -F "[bug:<이름>]"`로 남은 것이 없는지 본다.
   - 원인을 확인하려고 코드를 잠깐 고쳐 볼 수는 있다. 버그 보고 전에 되돌린다. 커밋한 틈 만들기는 되돌리지 않는다.
   - 재발이면 이전 버그의 회귀 테스트가 이번에는 왜 못 잡았는지부터 본다. 지난 수정이 원인을 덜 잡았다는 신호다.
   - 가설이 모두 틀리면 배운 것으로 한 번 더 세운다. 두 번째도 모두 틀리면 멈추고, 지운 가설과 남은 의심을 보고하고
     더 알려 줄 정보(언제, 어떤 계정, 어떤 환경)를 묻는다. 판정이 아닌 질문이므로 상태 파일의 "다음 할 일"에 `사용자 답 대기: <질문 요약>`을 쓴다.
     작은 수정에서 올라왔으면 그때 틀린 가설들을 첫 묶음으로 센다.
4. **영향도**: 고칠 곳이 정해지면 그 변경이 닿는 곳을 본다.
   - 고칠 함수·모듈을 부르는 곳(Graft가 있으면 `graft callers <식별자> --depth all`)과 그 영역 동작 명세의 시나리오
   - 지금의 틀린 동작을 기대값으로 굳힌 기존 테스트. 기대값을 바꾸는 것은 판정 질문 ②라 대책 표의 보호 대상 변경 칸에 적는다.
   - 고칠 곳 근처에 그 결과를 지키는 테스트가 없으면 대책 표의 그 행 작업 칸에 고정할 경로를 적는다(`references/characterization.md`).
   - 이미 생긴 피해: 틀린 값으로 저장된 데이터, 잘못 나간 알림·결제. 바로잡을지는 판정 질문 ③이라 버그 보고에서 묻는다.
     원인을 이미 확인했으면 피해가 남아 있어도 따로 멈추지 않는다. 고침이 곧 막는 일이기 때문이다.
5. **대책**: 고칠 곳과 방법, 작업 표, 회귀 테스트를 버그 문서에 쓴다. 작업 표는 계획(SKILL.md 2절)과 같은 열이고, 행이 하나여도 쓴다.
   - 첫 행의 실패 테스트는 재현 테스트다. 사람이 봐야 하는 변경(④)이면 확인 지점을 둔다.
   - 이미 생긴 피해를 바로잡는 일은 따로 행으로 두고 게이트를 결정으로 한다. 버그 보고에서 바로잡지 않기로 하면 다시 보고하지 않고 그 행을 지운다.
     운영 데이터를 실제로 바꾸는 실행은 바꿀 건수를 본 뒤 그 행의 결정 보고로 한 번 더 받는다.
     그 결정이 늦어지면 고침 PR을 먼저 열고, 그 행은 상태 파일의 "다음 할 일"에 남긴다.
   - 앞서 켠 재현 장치나 피해를 막은 조치가 있으면 그것을 푸는 행을 마지막에 둔다(아래 두 절).
6. **버그 보고**: 아래 "버그 보고"대로 보고하고 멈춘다.
7. **통과하면**: SKILL.md 5절대로 버그 문서, 재현 테스트, 로그를 `approve --for BUG-<이름>`으로 함께 커밋한다.
   이 커밋은 실패하는 테스트를 담고 있으므로 첫 고침 커밋까지 push하지 않는다. 브랜치 CI가 빨개지지 않게 하기 위해서다.
   그 전에 다시 멈춰야 하면(대책 수정, 예산) 정지 보고 규칙대로 push하고, 브랜치 CI가 재현 테스트 하나로 실패하는 것은 예상된 것이라고 보고의 자동 검사 칸에 쓴다.
8. **고침**: 작업 표대로 SKILL.md 3절 사이클을 돈다. 기록 ID는 행 ID다. 보호 대상 변경 칸 범위 안의 커밋은 버그 판정으로 커밋한다
   (`approve --for <행 ID>`, 사유 `버그 판정: <근거>`). 커밋 메시지는 작은 수정의 8단계와 같은 규칙이다.
   하는 김에 다른 곳을 고치지 않고, 발견한 것은 작은 수정의 "발견했지만 안 건드린 것"처럼 적는다.
   고칠 코드에 테스트가 없으면 고침 커밋 앞에 고정 테스트 커밋을 따로 둔다(`references/characterization.md`).
   고치다 대책이 틀린 것이 드러나면(원인이 달랐음, 행이 더 필요함) 멈추고, 버그 문서를 고쳐 다시 버그 보고를 한다(판정 ID `BUG-<이름>-대책<n>`, n은 2부터).
9. **마감**: 마지막 확인 지점을 통과하면(없으면 마지막 행을 커밋하면) 마감한다.
   - 버그 문서의 기대 동작을 `docs/behavior/<영역>.md`에 반영한다(`references/requirements.md`의 "동작 명세에 합치기"). 그 시나리오가 이미 있으면
     회귀 테스트 위치를 더하고, 버그 보고에서 정한 것(반올림 위치 등)이 시나리오에 없으면 그것도 적는다. 시나리오가 없으면 새로 더한다.
     버그 보고에서 판정받은 내용이므로 다시 묻지 않는다.
   - 버그 문서를 `docs/archive/spec/bug-<이름>.md`로 옮기고 상태 파일의 "다음 할 일"을 비운다. 새 로그 항목은 만들지 않고 `chore: BUG-<이름> 마감`으로 커밋한다.
   - push하고 PR을 연다. 완료 보고는 작은 수정과 같은 세 칸(바꾼 것 / 일부러 안 건드린 것 / 우려되는 점)에 회귀 테스트 위치를 더한다.

### 재현 장치와 피해 막기의 공통 규칙

아래 두 절의 결정(`CAPTURE-`, `CONTAIN-`)은 조사 도중에 멈추는 것이라 같은 순서를 따른다.

1. 고쳐 본 코드는 되돌리고, 커밋하지 않은 재현 테스트와 진단 로그는 SKILL.md 7절의 "작업 보류"로 미뤄 둔다(보류 ID는 `BUG-<이름>`).
   남겨 두면 approve가 스테이징되지 않은 변경 때문에 실패하거나, 다른 브랜치로 옮길 때 딸려 간다.
2. 보고와 로그는 늘 버그 브랜치에서 쓴다. 저장소 안에서 할지 밖에서 할지는 보고에서 고르므로, 고르기 전에 기록할 곳이 정해져 있어야 한다.
3. 통과하면 로그를 버그 브랜치에 커밋한다. 저장소를 고쳐야 하는 방법을 골랐으면 main에서 별도 브랜치를 따서 바꾸고,
   보호 대상이면 같은 ID로 `approve --for <ID>` 한 뒤 커밋하고 PR로 올린다. 이 변경도 PR에서 테스트를 통과해야 배포된다(SKILL.md 1절 배포 규칙).
   버그 브랜치와 따로 두는 것은 고침보다 먼저 병합되어야 하기 때문이다.
4. 저장소 밖(호스팅 콘솔의 환경 변수, 관리자 화면의 기능 플래그)에서 하는 방법을 골랐으면 켜는 방법과 푸는 방법을 단계로 쓰고 사용자가 한다.
5. 켠 것을 푸는 변경은 새 ID로 받는다: `CAPTURE-<이름>-off`, `CONTAIN-<이름>-off`, 브랜치는 `chore/capture-<이름>-off` 같은 식이다.
   고침과 함께 풀어도 되면 따로 받지 않고 버그 대책 표의 마지막 행으로 둔다.

### 재현이 안 될 때

코드 조사와 가설로 조건을 좁히고, 테스트 환경과 운영에 가까운 데이터·설정으로 시도해도 증상이 나지 않으면 추측으로 고치지 않고 멈춘다.
결정 보고(판정 ID `CAPTURE-<이름>`)에 시도한 재현과 결과, 그래서 지운 가설, 사용자에게 받을 정보(언제, 어떤 계정, 화면 녹화, 로그 시각), 그리고
**다음에 생길 때 그 순간을 잡는 방법**을 쓴다. 운영 설정을 바꾸지 않고 정보만 받으면 되는 경우는 판정이 아닌 질문으로 묻는다.

| 증상 | 잡는 방법의 예 |
| --- | --- |
| JVM 앱이 멈추거나 Full GC가 반복됨 | GC 로그(`-Xlog:gc*`), GC 시간이 기준을 넘으면 스레드 덤프(`jcmd <pid> Thread.print`)를 뜨는 감시 스크립트, 메모리 부족 때 힙 덤프(`-XX:+HeapDumpOnOutOfMemoryError`) |
| 가끔 틀린 값이 저장됨 | 그 값을 쓰는 자리에 입력과 결과를 남기는 태그 로그 |
| 특정 사용자에게만 오류 | 오류 추적 도구에 사용자·요청 ID를 붙임 |

잡는 방법마다 아래를 함께 쓴다. 잡는 장치가 또 다른 장애를 만들 수 있어서다.

| 쓸 것 | 내용 |
| --- | --- |
| 크기·개수 상한 | 파일 하나의 크기, 최대 개수, 넘으면 어떻게 되는지. 힙 덤프는 힙 크기만큼 커서 여러 번 뜨면 디스크를 채운다 |
| 성능 부하 | 잡는 동안 앱이 멈추거나 느려지는 정도 |
| 개인정보·비밀값 | 덤프와 로그에 담길 수 있는 것(힙 덤프에는 메모리의 비밀번호·토큰·개인정보가 그대로 있음), 보관 위치, 공유 범위 |
| 자료 전달 | 잡힌 자료를 누가 어디서 꺼내 어떤 형태로 넘기는지, 넘기기 전에 개인정보를 어떻게 거르는지. 에이전트가 운영에 접근할 수 없으면 사용자가 한다 |
| 끄는 시점 | 언제(날짜, 몇 번 잡으면) 누가 끄는지 |
| 판정 | 운영 설정을 바꾸거나 배포가 필요하면 결정 |

- 저장소를 고쳐야 하면 공통 규칙 3대로 `chore/capture-<이름>`에서 올린다.
- 기다리는 동안 버그 브랜치 상태 파일의 "다음 할 일"에 `재현 대기: <잡는 방법>, <끄는 날짜>`를 쓰고 상태 파일만 커밋한다.
  다른 기다림이 함께 있으면 같은 줄에 `; `로 잇는다. 세션 시작마다 다른 브랜치의 대기로 보인다.
- 끄는 날짜까지 잡히지 않으면 끄고, 연장할지 사용자에게 묻는다.
- 잡히면 잡은 자료로 보류해 둔 작업을 꺼내 2단계부터 이어 간다.

### 지금도 피해가 나고 있을 때

원인을 확인하기 전에 보안 노출, 개인정보 노출, 데이터 손상, 큰 금액의 잘못된 결제처럼 지금도 쌓이는 피해의 근거가 보이고,
고칠 때까지 쌓일 피해가 막는 부작용(기능 중단 등)보다 크면 원인 확인을 기다리지 않고 바로 멈춘다.
피해가 작거나 원인을 이미 확인했으면 멈추지 않고 버그 보고의 "정할 것"에 넣는다.
결정 보고(판정 ID `CONTAIN-<이름>`)에 다음을 쓴다.

- 보이는 근거와 아직 모르는 것. 추정이면 추정이라고 쓴다.
- 피해를 막는 방법(기능 끄기, 이전 배포로 되돌리기, 그 요청 막기)과 각각의 부작용, 막혔는지 확인하는 방법. 추천과 확신도.
- 보안·개인정보 피해면 대상자에게 알리거나 신고해야 하는지도 이 보고에서 묻는다. 기한이 있을 수 있어서다.
- 막는 일은 배포라서 사용자가 고른다. 저장소를 고쳐야 하면 공통 규칙 3대로 `chore/contain-<이름>`에서 올린다.
  이 변경은 작업 표 없이 한 커밋으로 하되, 완료 기준은 "막혔는지 확인하는 방법"이고 저장소의 테스트를 통과해야 한다.

막은 뒤에는 막혔는지 확인한다. 사용자가 저장소 밖에서 막았으면 확인 방법을 주고 결과를 받는다. 확인되면 원인 조사를 이어 간다.
막은 조치를 푸는 일은 대책 표의 마지막 행으로 두고, 고침이 배포된 뒤에 한다. 이미 생긴 피해의 정리는 버그 보고에서 묻는다.

### 버그 문서

`docs/spec/bug-<이름>.md`. 비어 있는 절은 지운다.

```markdown
# BUG-<이름>: <증상 한 줄>

최종 갱신: YYYY-MM-DD
영역: cart
이전 버그: 없음 (재발이면 이전 버그 문서, 그때 원인, 그때 회귀 테스트가 이번에 못 잡은 이유)
앞선 판정: 없음 (CAPTURE·CONTAIN을 받았으면 ID와 지금 상태)

## 동작
- 지금 동작: <조작> → <지금 나오는 결과>
- 기대 동작: <조작> → <나와야 할 결과> (근거: 동작 명세 "<시나리오>", 문서, 또는 누구나 틀렸다고 보는 결과)
- 바뀌면 안 되는 동작: <고치면서 그대로 둘 것. 회귀 테스트로 지킴>

## 재현
- 명령: `<이 버그에서 빨개지는 명령>`
- 최소 조건:

## 원인
| 순서 | 가설 | 가능성 | 확인 비용 | 확인 방법 | 결과 |
| --- | --- | --- | --- | --- | --- |

확인된 원인: <어디가 왜 틀렸나>. 근거: <측정 결과>

## 영향도
- 고칠 곳을 쓰는 곳:
- 틀린 동작을 기대값으로 굳힌 기존 테스트:
- 이미 생긴 피해:

## 대책
<고칠 곳과 방법>

| ID | 작업 | 선행 | 먼저 작성할 실패 테스트 / 완료 기준 | 게이트 | 보호 대상 변경 |
| --- | --- | --- | --- | --- | --- |

- 회귀 테스트: <파일> "<테스트 이름>"
- 확인 지점: <사람이 봐야 하면 해볼 흐름>

## 정할 것
<맞는 동작이 둘로 갈리는 선택(재현 테스트는 추천 쪽으로 씀), 이미 생긴 피해를 바로잡을지>

## 내가 이해한 전제
항목마다 확인됨(근거) 또는 추정(근거).
```

### 버그 보고

결정 보고(SKILL.md 4절, `references/report-format.md`)의 한 종류다. 판정 ID는 `BUG-<이름>`,
기록은 `node scripts/gated-tdd/log-new.mjs "BUG-<이름>: <증상 한 줄>" --gate 결정`. 판단 재료 자리에는 다음을 쓴다.

1. 원인: 지금 동작과 기대 동작, 확인된 원인과 측정 근거, 지운 가설의 수
2. 영향도: 고칠 곳을 쓰는 곳, 기대값을 바꿀 기존 테스트, 이미 생긴 피해
3. 대책: 고칠 곳과 방법, 작업 표 요약(게이트, 보호 대상 변경), 회귀 테스트 위치
4. 정할 것: 맞는 동작이 둘로 갈리면 그 선택(선택지마다 결과, 추천과 근거), 이미 생긴 피해를 바로잡을지.
   따로 멈추지 않고 이 보고에서 함께 묻는다.

보고 전에 버그 문서, 로그 항목, 상태 파일("판정 대기"에 `BUG-<이름>`, "다음 할 일")을 쓴다. "다음 할 일"에는 커밋하지 않은
재현 테스트의 경로도 적어 다음 세션이 찾게 한다. 보고 전에는 상태 파일만 커밋하고 push한다(SKILL.md 1절).
보고하고 멈추며, 같은 턴에 고침으로 넘어가지 않는다. 수정이 오면 버그 문서를 고쳐 다시 보고한다.

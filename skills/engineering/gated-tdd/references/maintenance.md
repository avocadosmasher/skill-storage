# 유지보수: 작은 수정

오타, 작은 버그, 문구 변경처럼 요구 문서와 계획 없이 커밋 하나로 끝나는 수정의 경로다. 판정 질문과 훅은 그대로 적용한다.
버그 수정의 원인 조사, 테스트 없는 코드, 큰 리팩터링, 의존성 업데이트의 전용 절차는 아직 없다. 작은 수정이 아니면 기능 개발과 같은 절차를 탄다.

## 작은 수정이 되는 조건

세 가지가 모두 맞아야 한다. 하나라도 아니면 기능 개발 절차(요구 → 계획 → 사이클)로 간다.
시작할 때는 요청만 보고 판단하고, 조사와 재현을 하면서 다시 본다. 도중에 맞지 않게 되면 "올리는 조건"을 따른다.

1. **요청만으로 무엇을 할지 분명하다.** 인수 기준("이렇게 되면 완료")을 한두 줄로 쓸 수 있고, 선택이 사용자 의도에 달리지 않는다(판정 질문 ①).
   "보기 좋게 바꿔 줘"처럼 기준을 문장으로 쓸 수 없거나 "A로 할까 B로 할까"가 생기면 아니다.
   재현 테스트의 기대값이 아직 정하지 않은 선택에 기대도 ①이다. 예: 1원 오차의 기대값이 반올림을 상품마다 하느냐 합계에서 하느냐에 따라 달라짐.
2. **커밋 하나로 끝난다.** 처음 수정이 작업 표의 한 행이다. 순서나 중간 상태가 생기면 계획이 필요하다.
   다음 커밋은 세지 않는다. ④의 확인 결과만 적는 기록 커밋, 그리고 확인에서 사용자가 고칠 값을 정해 준 고침 한 커밋이다.
   고칠 점이 새 선택을 부르거나 커밋 여러 개가 필요하면 올린다.
3. **판정 질문 ②③에 해당하지 않고 보호 대상을 건드리지 않는다.** 기존 테스트의 기대값 변경, 권한, 데이터, 의존성은 작아도 아니다.
   보호 대상은 훅이 커밋 때 기계적으로 막는다.

사람이 봐야 하는 변경(판정 질문 ④)은 조건에 걸리지 않는다. 화면·문구 수정은 작은 수정으로 하되 확인을 한 번 받는다.

## 흐름

1. **알림**: 시작할 때 한 줄로 알리고 기다리지 않고 진행한다. `작은 수정으로 처리함: <인수 기준>`. 사용자가 정식 절차를 원하면 기능 개발로 간다.
   고른 유형과 근거(조건을 어떻게 확인했는지)는 첫 정지 보고(확인 보고, 완료 보고, 올림 메시지)의 "내가 이해한 전제"에 쓴다.
2. **브랜치**: 진행 중인 기능과 관련 없으면 main에서 `fix/<짧은 이름>`을 딴다.
3. **재현**: 고치기 전에 지금 상태를 그대로 보인다. 원인을 추측으로 고치지 않는다.
   - 버그는 증상을 재현한다.
   - 오타처럼 지금 잘못 보이는 것은 틀린 곳(파일과 화면 위치)을 보인다.
   - 색 변경처럼 새로 바꾸는 요청은 수정 전 캡처가 재현을 대신한다.
4. **테스트 또는 확인 방법**
   - 동작을 바꾸는 수정은 실패 테스트를 먼저 쓴다(SKILL.md 3절 Red). 버그는 그 증상을 재현하는 테스트다.
   - 동작이 없는 문구·화면·설정 변경은 테스트 대신 확인 방법을 정한다. 화면은 전후 캡처, 문구는 바뀐 문장 인용이다.
     문구가 같은지만 보는 테스트는 쓰지 않는다. 동작에 영향이 있는지 애매한 설정은 테스트 쪽으로 간다.
   - 캡처는 이미 쓸 수 있는 브라우저 도구로 한다. 캡처 도구를 새로 설치하지 않는다(의존성은 보호 대상이다).
     캡처 파일은 세션이 바뀌어도 남는 저장소 밖 폴더에 두어 커밋에 섞이지 않게 하고, 경로를 로그 Red 칸에 적는다.
     캡처할 수 없으면 바뀐 문장과 화면 위치를 글로 적는다.
   - 사용자가 값을 정해 준 시각 변경("#2563eb로")은 고를 것이 없으므로 시안을 만들지 않는다(SKILL.md 7절).
5. **고침**: 통과시키는 최소 수정. 하는 김에 다른 곳을 고치지 않는다.
6. **자동 검사**: 영향 범위의 테스트와 저장소 필수 게이트.
7. **기록**: `node scripts/log-new.mjs "FIX-<짧은 이름>: <제목>" --gate 자동`(④면 `--gate 확인`). 템플릿 칸은 그대로 채운다.
   - 게이트: `자동` 또는 `확인`, 사유는 "작은 수정" (④면 "작은 수정, 사람이 봐야 함")
   - 시작 기준: 브랜치를 딴 main 커밋
   - 문제·요청: 사용자 요청과 인수 기준
   - Red: 재현과 실패 테스트. 테스트가 없으면 확인 방법과 수정 전 상태
   - 수정, 자동 검사, 남은 제약: 기능 개발과 같다

   템플릿 아래에 두 줄을 덧붙인다.
   - `생략: 요구·계획 (작은 수정)`
   - `발견했지만 안 건드림: <무엇, 어디>` (없으면 "없음", 아래 절)

   INDEX 결론 한 줄과 STATUS "최근 3건"을 고친다. STATUS에는 확인이 필요 없는 수정은 "자동 진행 내역"에, ④는 "확인 대기"에 적는다.
8. **커밋**: 로그를 바탕으로 커밋 메시지를 쓴다. 제목은 `<앞머리>: <INDEX 결론 한 줄>`, 본문은 인수 기준, 원인(버그면), 확인 방법이다.
   앞머리는 버그·오타면 `fix:`, 그 밖의 변경(색, 문구 다듬기, 설정)은 `chore:`다. `AGENTS.md`나 기여 안내 문서에 커밋 규칙이 적혀 있으면 그것을 따른다.
   기존 커밋의 모양은 규칙으로 보지 않는다.
   그 영역의 동작 명세(`docs/behavior/`)에 해당 시나리오가 있으면 테스트 위치를 같은 커밋에서 적는다.
9. **마무리**: push하고 PR을 연다.
   - ④가 아니면 완료 보고를 한다.
   - ④면 PR 주소와 전후 캡처로 확인 보고를 하고 **멈춘다.** PR에 미리보기 주소가 생기면 그것으로 확인받는다. PR 본문에 "확인 대기"를 적는다.
   - 확인에서 고칠 점이 나오면 조건 2로 다시 본다. 사용자가 값을 정해 줬고 한 커밋이면 같은 PR에 고침 커밋을 더하고 다시 확인받는다.
     로그는 새로 만들지 않고 같은 항목의 수정 칸에 덧붙이고, INDEX 결론을 최종 값으로 고친다.
     커밋 제목은 8단계와 같은 규칙으로, 고친 INDEX 결론에서 쓴다. 그렇지 않으면 올린다.
   - 확인이 통과하면 로그 머리줄과 INDEX 상태를 `통과`로(고친 적이 있으면 `통과 (수정 N건)`), STATUS "확인 대기"를 비운다.
     이 기록 커밋의 제목은 `chore: <ID> 확인 통과 기록`이다. 같은 PR에 더하고 완료 보고를 한다.

완료 보고는 세 칸으로 쓴다: 바꾼 것 / 일부러 안 건드린 것 / 우려되는 점. 보고 형식(SKILL.md 4절)을 따르되,
판정할 것이 없으면 결론과 이 세 칸, 자동 검사, PR 주소만 쓴다.

## 올리는 조건

작업 중 하나라도 생기면 멈추고, 알리고, 기능 개발 절차로 올린다. 아직 커밋하지 않은 작업은 커밋하지 않고 그대로 두고 보고에 쓴다.

| 조건 | 예 |
| --- | --- |
| 커밋이 둘 이상 필요해짐 | 같은 문구가 여러 화면에 흩어져 있어 문구 관리 구조를 바꿔야 함 |
| 판정 질문 ①②③이 새로 생김 | 버그 원인을 보니 "탈퇴한 회원의 댓글을 보여 줄지"를 정해야 함 |
| 보호 대상을 바꿔야 함 (알게 된 때 올린다. 훅은 놓친 경우를 막는 장치다) | 고치려면 라이브러리를 설치하거나 기존 테스트의 기대값을 바꿔야 함 |
| 원인 가설이 3번 틀림 | 반올림, 타임존, 캐시를 차례로 의심했지만 모두 아님. 구조 문제일 수 있음 |

올림 알림과 요구 정리(SKILL.md 2절)의 첫 질문을 한 메시지로 보내고 멈춘다. 따로 정지를 하나 더 만들지 않는다.
조사로 드러난 선택이 올린 이유면, 첫 질문은 그 선택을 근거와 함께 바로 묻는다. 이 선택지는 AI의 제안이 아니라 조사한 사실이다.

```
작은 수정으로 시작했으나 <조건>이 생겨 정식 절차로 올림. 지금까지 한 것: <…>
내가 이해한 전제: <…>
첫 질문: <요구를 정하는 데 필요한 질문>
```

기록: 로그 머리줄과 INDEX 상태를 `올림`으로 바꾸고, STATUS "확인 대기"에 이 항목이 있으면 비운다.
"다음 할 일"에는 `사용자 답 대기: <첫 질문 요약>`을 쓴다. 이 기록은 따로 커밋하지 않고 다음 판정 커밋(요구 보고)에 함께 넣는다.

브랜치는 PR을 열기 전인지 뒤인지에 따라 다르다.

- **PR을 열기 전**: 기능 ID가 정해지면 브랜치 이름을 `feat/<기능 ID>`로 바꾼다(`git branch -m`). 아직 push하지 않은 브랜치이므로 바꿔도 잃는 것이 없다.
- **PR을 연 뒤**(확인에서 고칠 점이 커진 경우): 이미 고친 것이 그 자체로 맞는지 본다. 어느 쪽으로 봤는지는 올림 메시지의
  "내가 이해한 전제"에 쓴다. 사용자가 뒤집으면 그에 따른다.
  - **맞아 보이면**(예: 오타와 마침표는 맞고, 말투를 새로 정하고 싶음): 지금 PR은 작은 수정으로 마무리한다.
    사용자가 통과라고 하지 않았으면 통과로 적지 않는다(SKILL.md 5절). 올림 메시지에 "<ID>는 이대로 통과인가요?"를 첫 질문과 함께 묻고,
    그때까지 이 항목은 `확인 대기`로 둔다. 위의 `올림` 기록은 이 항목에 쓰지 않는다.
    통과라고 하면 로그 머리줄과 INDEX 상태를 `통과`(고친 적이 있으면 `통과 (수정 N건)`)로 바꾸고, 남은 제약에 "<커진 일>은 정식 절차로 올림"을 적어
    `chore: <ID> 확인 통과 기록` 커밋을 그 PR에 더한다. 병합은 사용자가 고른다. 통과가 아니면 아래 휩쓸린 경우로 간다.
  - **커진 일에 휩쓸리면**(예: 버튼 색을 바꿨는데 화면 색 전체를 다시 정하게 됨): 그 PR은 병합하지 않는다.
    기능 ID가 정해질 때까지는 PR을 닫지 않고 본문 맨 위에 "정식 절차로 올림, 병합하지 말 것"을 적어 둔다.
  - 커진 일의 `feat/<기능 ID>` 브랜치는 요구 파일을 처음 쓸 때 딴다(`references/requirements.md`). 어디서 딸지는 SKILL.md 7절의 선행 기능 규칙을 따른다.
    마무리한 PR이 이미 병합됐으면 main에서, 아직이면 그 `fix/` 브랜치에서 딴다. 휩쓸린 경우는 늘 그 `fix/` 브랜치에서 딴다.
    휩쓸린 경우 새 브랜치를 push한 뒤 옛 PR은 "`feat/<기능 ID>`로 옮김" 댓글을 달고 닫는다. 이미 push한 브랜치는 이름을 바꾸면 PR이 끊기기 때문이다.

## 발견했지만 안 건드린 것

작은 수정 중 발견한 다른 문제는 고치지 않는다. 로그에 `발견했지만 안 건드림: <무엇, 어디>`로 적고, 완료 보고의
"일부러 안 건드린 것"에 넣어 따로 할지 묻는다. ④면 첫 확인 보고의 결론에 넣는다. 사용자가 확인하면서 함께 정할 수 있다.
하는 김에 고치면 작은 수정이 조용히 커진다.

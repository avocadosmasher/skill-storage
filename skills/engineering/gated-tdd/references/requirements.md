# 요구 정리: 계획 전에 무엇을 만들지 합의

모든 작업 유형이 계획 전에 거친다. 분량은 모호함에 맞춘다. 분명한 기능이면 요구 두세 줄과 시나리오 몇 개로 끝나고,
모호한 기능이면 대화로 꺼낸 뒤 쓴다. 이미 있는 시스템 전체를 거슬러 문서화하지 않는다. 문서는 실제 변경이 지나간 자리에서만 자란다.

## 문서 세 가지

| 문서 | 위치 | 담는 것 | 언제 |
| --- | --- | --- | --- |
| 제품 명세 | `docs/spec/product.md` | 목적, 성공 기준, 범위, 만드는 방식, 기능 지도 | 제품을 처음 만들 때, 또는 기존 제품에 기능 여럿을 더하는데 아직 없을 때. 범위·기능 지도가 바뀔 때 고침 |
| 기능 요구 | `docs/spec/<기능 ID>.md` | 이번 기능이 동작을 어떻게 바꾸는지(델타) | 기능마다. 끝나면 `docs/archive/spec/`으로 옮김 |
| 동작 명세 | `docs/behavior/<영역>.md` | 지금 시스템이 영역별로 어떻게 동작하는지 | 기능을 마칠 때 델타를 합쳐서 자람 |

영역은 사용자가 알아듣는 기능 묶음으로 나눈다(`cart`, `auth`, `notify`). 처음 그 영역을 건드리는 기능이 파일을 만든다.

## 요구 대화

AI가 짐작으로 채우는 부분을 줄이고, 사용자가 원하는 것을 자기 말로 꺼내게 하는 것이 목적이다. 요청만으로 인수 기준과
하지 않을 것을 쓸 수 있으면 대화 없이 기능 요구를 쓰고, 추정한 것은 "내가 이해한 전제"에 추정으로 적는다.

- 대화를 시작하기 전에 제품 명세의 "하지 않을 것"을 본다. 요청이 거기에 있으면 질문보다 먼저 알린다:
  "이 기능은 YYYY-MM-DD 제품 명세에서 <이유>로 하지 않기로 했습니다. 그래도 추가할까요? 추가한다면 무엇이 바뀌었는지
  알려 주세요." 추가하기로 하면 그 답을 범위 변경의 이유로 요구 보고에 넣고(판정 질문 ②), 아니면 멈춘다.
- 첫 질문은 열린 질문 하나로, 구체적인 장면을 묻는다("이게 있었으면 했던 마지막 순간이 언제였나요?").
  선택지를 먼저 내밀지 않는다. 선택지는 답을 끌고 간다. 사용자가 막히거나 "알아서 해 줘"라고 하면 구체적인 안을 낸다.
- 한 번에 한 질문. 기존 코드·문서를 보면 알 수 있는 것은 묻지 않고 직접 본다. 외부 조사는 무엇을 찾을지 말하고 동의를 받는다.
- 훑을 영역이다. 질문 목록으로 읽어 주지 않는다.
  1. 무엇이고 왜 지금인지, 누가 어떤 순간에 쓰는지
  2. 성공의 모습, 하지 않을 것, 동작해도 실패인 것
  3. 참고한 것, 이미 가진 것(코드, 데이터, 계정, 예산)
  4. 만드는 방식 중 사용자가 직접 정할 것과 맡길 것
- 한 부분을 설명할 수 있게 되면 짧게 되읽어 주고 틀린 곳을 묻는다. 추측은 추측이라고 표시한다.
- 모호한 요구는 구체적인 예시로 바꿔 제안한다("빠르게" → "목록 첫 화면이 1초 안에 뜸"). 예시가 시나리오가 된다.
- 갈래가 많아 결정 트리를 캐물어야 하면 Skill 도구에 `grill-me-plus`가 있을 때 호출한다.
- 사용자가 질문을 건너뛰자고 하면 건너뛴다. 대신 AI가 정한 것을 문서에 모두 적고 같은 요구 보고로 받는다.

## 기능 요구 파일

`docs/spec/<기능 ID>.md`. 기능 ID는 영문 소문자와 하이픈이다. 요구는 동작을 바꾸는 단위(델타)로 쓴다.
기능 ID는 요구 대화가 끝나 이 파일을 처음 쓸 때 정하고, 그때 `feat/<기능 ID>` 브랜치를 딴다. 요구 보고에서 사용자가
이름을 바꾸면 파일과 브랜치 이름을 함께 바꾼다(`git branch -m`). 요구가 통과한 뒤에는 바꾸지 않는다.
기능 지도에 이미 있는 기능이면 그 ID를 쓴다.

```markdown
# <기능 ID>: <기능 이름>

최종 갱신: YYYY-MM-DD
영역: cart

## 문제
누가, 어떤 순간에, 무엇이 불편한가. 왜 지금인가.

## 사용자 흐름
조작 → 결과 순서로 한 흐름.

## 추가되는 동작
### 요구: <한 줄>
<시스템이 무엇을 하는지>
#### 시나리오: <이름>
- <상황>에서
- <조작>하면
- <결과>

## 바뀌는 동작
### 요구: <동작 명세에 이미 있는 요구 이름>
<바뀐 내용> (이전: <원래 내용>)

## 없어지는 동작
### 요구: <이름>
<없애는 이유>

## 하지 않을 것

## 내가 이해한 전제
항목마다 확인됨(근거) 또는 추정(근거).

## 열린 질문
```

- 비어 있는 절은 지운다. 시나리오는 그대로 Red 테스트가 될 만큼 구체적으로 쓴다.
- 바뀌는·없어지는 동작은 동작 명세에 있는 요구만 가리킨다. 동작 명세에 없는 기존 동작을 바꾸면 "바뀌는 동작"에 원래 동작을 직접 적는다.
- 기능 요구에서 정할 수 없는 기술 선택(저장 구조, 라이브러리)은 계획의 결정 목록으로 넘긴다.
- 바뀌는·없어지는 동작 때문에 기존 테스트의 기대값을 고치거나 테스트를 지워야 하면, 계획 작업 표의 보호 대상 변경 칸에
  그 테스트와 새 기대값을 적는다. 요구와 계획에서 판정받았으므로 사이클에서 다시 묻지 않는다.

## 제품 명세

`docs/spec/product.md`. 짓는 사람이 사용자에게 다시 묻지 않고 기능을 고를 수 있을 만큼 쓰되, 규모에 맞춘다.

```markdown
# <제품> 명세

최종 갱신: YYYY-MM-DD

## 목적
누가, 어떤 순간에, 왜 쓰는가.

## 성공 기준
확인할 수 있는 조건으로 쓴다.

## 범위
- 목표:
- 하지 않을 것: 항목마다 이유와 정한 날짜 (`- 유료 구독: 첫 해는 무료로 독자 반응부터 확인 (YYYY-MM-DD)`)
- 동작해도 실패인 것:

## 제약
기한, 비용 한도, 실행 환경, 이미 가진 것.

## 만드는 방식
| 항목 | 정한 것 | 누가 정했나 |
| --- | --- | --- |
| 언어·프레임워크 | | 사용자 / AI 기본값 / 기존 |
| 데이터 저장 | | |
| 테스트 도구 | | |
| 배포처 | | |

## 기능 지도
| 기능 ID | 기능 | 선행 | 사용자가 해볼 흐름 | 상태 |
| --- | --- | --- | --- | --- |

만들 순서:

## 열린 질문
```

기능 지도 규칙:

- 기능 ID는 제품 명세가 통과하면 바꾸지 않는다. 기능 요구는 `docs/spec/<기능 ID>.md`, 계획은 `docs/plan/<기능 ID>-개발계획.md`다.
- 선행은 한 방향으로만 잇는다. 두 기능이 서로를 필요로 하면 한 기능으로 합친다.
- 상태는 `예정`, `진행`, `완료`, `있음`(이 절차 전부터 있던 기능) 중 하나다.
- 기존 제품에서 처음 쓰면 요청받은 기능만 넣고, 그 기능이 기대는 기존 기능만 `있음`으로 한 줄씩 적는다.
- 사용자가 해볼 흐름이 없는 기능은 "없음"과 그 기능을 처음 드러내는 기능 ID를 적는다. 확인 지점의 근거가 된다.

기능을 더하거나 빼기, 성공 기준·범위 변경, 기능 지도의 순서 변경은 판정 질문 ②다. 제품 명세를 고치는 내용을
그 기능의 요구 보고에 함께 넣는다. "하지 않을 것"에 있던 기능을 추가하면 그 항목에서 추가하는 부분만 지우고("할인·쿠폰·포인트"에서 쿠폰만 넣으면 나머지는 남김),
사용자가 말한 이유를 결론에 쓴다.

## 요구 보고

결정 보고(SKILL.md 4절, `references/report-format.md`)의 한 종류다. 판정 ID는 기능 요구면 `SPEC-<기능 ID>`,
제품 명세 부분은 `SPEC-product`다. 기록은 `node scripts/log-new.mjs "SPEC-<기능 ID>: <기능 이름> 요구" --gate 결정`.
제품 명세와 함께 보고하면 기록은 하나로 쓰고 제목 끝에 `(제품 명세 포함)`을 붙인다.
판단 재료 자리에는 다음을 쓴다.

1. 요구 요약: 문제, 사용자 흐름, 추가·바뀌는·없어지는 동작의 요구 한 줄씩.
2. AI가 정한 것: 사용자가 말하지 않아 AI가 정한 항목과 이유. 들어 보지 못한 기본값은 거절할 수도 없다.
3. 제품 명세가 바뀌면 그 내용(기능 지도의 위치, 범위 변경)과 이유.
4. 열린 질문: 답에 따라 만들 것이 바뀌는 것만, 중요한 순서로.

제품 명세를 처음 쓰거나 고칠 때는 따로 보고하지 않고, 함께 시작하는 기능의 요구와 한 보고에 두 부분으로 넣는다.
둘 다 만들기 전에 "무엇을 만들지"를 정하는 일이라 같이 볼 때 판단이 쉽다. 판정 요청은 부분마다 받는다
("제품 명세: 통과 / 수정", "SPEC-<기능 ID>: 통과 / 수정").

- 둘 다 통과: 두 파일을 함께 커밋한다(`approve --for "SPEC-product SPEC-<기능 ID>"`).
- 기능 요구만 수정: 제품 명세를 먼저 커밋하고, 기능 요구만 고쳐 다시 보고한다.
- 제품 명세가 수정: 기능 요구가 그 위에 서 있으므로 둘 다 커밋하지 않고, 함께 고쳐 다시 보고한다.

보고 전에 기능 요구 파일(제품 명세가 함께면 그것도), 로그 항목, STATUS.md("판정 대기"에 판정 ID, "다음 할 일")를 쓴다.
이 파일들이 이 결정의 파일이다. 세션이 끊겨도 다음 세션이 STATUS에서 판정 대기를 보고 이어 간다.
보고 전에는 커밋하지 않는다. 보고하고 멈추며, 같은 턴에 계획이나 코드로 넘어가지 않는다.
통과하면 SKILL.md 5절대로 approve → 커밋 → push 하고 계획을 세운다.

## 동작 명세에 합치기

기능의 마지막 확인 지점을 통과하면(확인 지점이 없는 기능은 마지막 행을 커밋하면) 그 기능의 마감으로 한다.

1. 기능 요구의 델타를 `docs/behavior/<영역>.md`에 반영한다. 추가는 붙이고, 바뀐 것은 교체하고, 없어진 것은 지운다.
2. 시나리오마다 그것을 검증하는 테스트 위치를 적는다: `(테스트: tests/cart.test.ts "만료된 코드")`.
   검증 테스트가 없는 시나리오는 "(사람 확인: 확인 지점 M3)"처럼 확인 방법을 적는다.
3. 기능 요구 파일을 `docs/archive/spec/<기능 ID>.md`로 옮기고, 제품 명세 기능 지도의 상태를 `완료`로 고친다.
4. 커밋하고 다음 보고의 자동 진행 내역에 한 줄로 알린다. 요구 보고에서 이미 판정받은 내용이므로 다시 묻지 않는다.

동작 명세 형식:

```markdown
# <영역> 동작

최종 갱신: YYYY-MM-DD

## 요구: <한 줄>
<시스템이 무엇을 하는지>
### 시나리오: <이름>
- <상황>에서 <조작>하면 <결과> (테스트: <파일> "<테스트 이름>")
```

## spike (버리는 실험)

만들어 봐야 요구가 분명해지거나 기술이 되는지 모를 때(위험한 외부 연동 포함) 쓴다.

- 무엇을 알아내려는지와 시간 상자를 말하고 사용자 동의를 받는다.
- `spike/<주제>` 브랜치에서 테스트, 계획, 게이트 없이 빨리 만든다. 의존성 추가처럼 훅에 걸리는 변경이 필요하면
  저장소 밖 임시 폴더에서 한다. `--no-verify`로 넘기지 않는다.
- 끝나면 배운 것을 남긴다: `node scripts/log-new.mjs "SPIKE: <주제>" --status 기록`. 무엇을 확인하려 했는지,
  결과, 요구·계획에 미치는 영향을 쓴다.
- spike 코드는 작업 브랜치에 병합하지 않는다. 살리려면 계획에 새 행으로 넣고 Red부터 다시 만든다.

# 의존성 업데이트: 제품이 쓰는 패키지의 버전을 올리기

의존성 업데이트는 제품이 쓰는 패키지(라이브러리, 프레임워크, 테스트·빌드 도구)의 버전을 올리는 작업이다. 사용자가 보는 동작을 바꾸지 않으므로 요구를 생략한다(SKILL.md 2절).
들어올 패키지와 목표 버전은 늘 사용자가 보고 정한다. 버전은 설치하는 순간 정해지고, 범위 안의 새 버전에 악성 코드가 들어가는 공급망 공격도 있기 때문이다.
패키지 하나면 결정 보고 한 번(`DEP-<패키지>-<버전>`), 둘 이상이거나 코드를 고쳐야 하면 계획 보고 한 번(`PLAN-<이름>`)으로 받는다.

예시: Node 저장소에서 사용자가 "의존성 업데이트 좀 해 줘"라고 한다. `npm outdated`에 patch 15개, minor 6개, major 2개(vitest 2→3, react-router 6→7)가 나오고,
`npm audit`에 하위 의존성 `path-to-regexp`의 high 취약점 1건이 있다.

## 무엇이 보호 대상인가

매니페스트(`package.json`, `pyproject.toml`, `go.mod` 등)와 lock 파일(`package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`, `poetry.lock`, `uv.lock`, `Cargo.lock`, `go.sum`, `Gemfile.lock` 등)이
모두 보호 대상이다(`references/approval-gate.md`). `npm update`처럼 범위 안에서 lock 파일만 바꾸는 명령도 업데이트다.

- **판정 범위**: 판정받은 것은 패키지와 목표 버전이다. 매니페스트 변경을 판정받으면 그 설치가 만든 lock 파일 변경까지 덮으므로 칸에 lock 파일을 따로 적지 않는다.
  lock 파일에서 판정받은 패키지와 그 하위 의존성 **밖의** 패키지 버전이 바뀌었으면 범위를 넘은 것이다. 되돌리고 그 패키지만 올리는 명령으로 다시 한다.
- **패키지 관리자 버전**: 설치는 저장소가 정한 패키지 관리자 버전으로 한다(`package.json`의 `packageManager`와 corepack, `engines`, CI 설정). 다른 버전으로 설치하면 버전과 무관한 줄(`"peer": true` 같은 표시)이 무더기로 바뀐다.
  npm이면 `npx npm@<버전> install <패키지>@<버전>`처럼 맞춘다. 맞출 수 없으면 패키지 버전이 바뀌지 않은 줄은 범위 안으로 보고, 그 줄 수와 이유를 로그와 다음 보고에 쓴다.
- **의도하지 않은 lock 변경**: 패키지를 더하거나 올리지 않는 커밋에서 lock 파일이 바뀌었으면(설치하다 범위 안 업데이트가 끼어듦 등) 스테이징하지 않고 `git restore <lock 파일>`로 되돌린 뒤 lock 파일대로 다시 설치한다(`npm ci` 등). 결정으로 올리지 않는다.
- 게이트 스크립트가 lock 파일을 막지 않는 옛 버전이거나 `.gated-tdd.json`의 `decide`에 lock 파일이 없으면(SKILL.md 0절에서 알게 됨), 갱신 전까지 에이전트가 lock 파일을 보호 대상처럼 다룬다. 칸에 적고 판정받은 범위만 커밋한다.

## 어느 경로로 가나

- **패키지 하나**: 아래 조건이 모두 맞으면 계획 없이 결정 보고 한 번으로 한다(아래 "패키지 하나").
  1. 올리는 패키지가 하나다. 함께 올려야만 동작하는 묶음(`react`와 `react-dom`, 같은 버전으로 나오는 `@babel/*`)은 하나로 본다. 취약점 때문에 하위 의존성 하나만 올리는 것도 하나다.
  2. 매니페스트와 lock 파일 말고 고칠 것이 없다. 제품 코드, 테스트, 설정 파일 중 하나라도 고쳐야 하면 계획이다.
  3. 고정 테스트가 필요 없다. 아래 "테스트가 덮지 않는 사용처"에서 고정 테스트를 두는 경우면 계획이다.
  4. 확인 지점이 필요 없다. 화면을 그리는 라이브러리면 전후 캡처가 같아야 한다. 다르거나 캡처할 수 없으면 계획이다.
- **둘 이상이거나 위 조건에 맞지 않음**: 아래 "계획에 담는 것"대로 계획 보고(`PLAN-<이름>`)를 한다.
- 기능 계획 안에서 패키지를 더하거나 올리는 것은 지금처럼 그 계획의 보호 대상 변경 칸에 적는다(SKILL.md 2절). 목표 버전 고르기와 위 보호 대상 규칙은 같다.
- 버그의 원인이 패키지라 올려서 고치면 버그 수정의 대책 표에 그 행을 둔다(`references/maintenance.md`).
- 업데이트를 받아들이려면 사용자가 보는 동작이 바뀌어야 하면(변경 기록의 동작 변경) 그 패키지는 이 절차에서 빼고 기능 개발로 따로 한다.
- 알려진 취약점이 지금 이 제품에서 악용되고 있다는 근거가 보이면 업데이트보다 먼저 버그 수정의 "지금도 피해가 나고 있을 때"를 본다.

## 이름

| 쓰는 곳 | 패키지 하나 | 계획 |
| --- | --- | --- |
| 이름 | 패키지 이름과 목표 버전. `@`는 빼고 `/`는 `-`로 바꾼다 | 범위와 연월 (`2026-11-routine`, `jest-30`) |
| 브랜치 | `deps/lodash-4.17.21` | `deps/2026-11-routine` |
| 판정 ID | `DEP-lodash-4.17.21` | `PLAN-2026-11-routine` |

같은 패키지를 다음에 다시 올려도 버전이 달라 ID가 겹치지 않는다. 브랜치는 main에서 딴다.

## 대상 찾기

- 사용자가 패키지를 말했으면 그 패키지만 본다.
- "업데이트 해 줘"처럼 범위가 없으면 저장소의 패키지 관리자 명령으로 목록을 만든다(`npm outdated`·`npm audit`, `pip list --outdated`, `go list -m -u all`, `bundle outdated` 등).
  고르는 질문을 따로 하지 않는다. 찾은 것을 모두 계획의 업데이트 표에 넣고, 사용자는 계획 보고에서 뺄 행을 고른다.
- 점검 도구를 새로 설치해야 하면(`pip-audit` 등) 설치하지 않고, 확인하지 못한 범위로 계획 보고에 쓴다.
- 런타임과 CI(`.nvmrc`, Dockerfile의 베이스 이미지, 워크플로의 `actions/checkout@v4`)는 사용자가 말했을 때만 대상에 넣는다. 말하지 않았으면 확인하지 않은 범위로 쓴다.
- **하위 의존성의 취약점**(`express`가 끌어오는 `path-to-regexp` 등)은 고치는 방법을 아래 순서로 찾는다.
  1. 끌어오는 직접 의존성을 고친 하위 버전을 쓰는 버전으로 올린다.
  2. lock 파일만 고친다(`npm audit fix`, `--force` 없이). lock 파일에서 그 하위 패키지 밖의 버전이 바뀌면 되돌리고 다른 방법을 쓴다.
  3. 매니페스트의 강제 버전(`overrides`, `resolutions`)은 앞의 둘이 안 될 때만 쓰고 계획에 이유를 쓴다.
- Dependabot 같은 봇이 연 PR이 있으면 그 PR도 대상 목록이다. 처리를 맡으면 봇 브랜치에 커밋하지 않고 이 절차의 브랜치에서 올리며, 보고에 그 PR 번호를 쓴다.
  봇 PR은 사용자가 병합하거나 닫는다. 이 절차의 PR이 병합되면 봇이 보통 스스로 닫는다. 도입할 때 봇 설정을 권하지는 않는다.

## 목표 버전 고르기

- **공개된 지 7일이 지난 버전**에서 고른다. 공개일은 패키지 저장소에서 확인한다(`npm view <패키지> time --json`, PyPI의 `https://pypi.org/pypi/<패키지>/json`, `go list -m -json <모듈>@<버전>`의 `Time`).
  최신 버전이 7일이 안 됐으면 그 전 버전 중 7일이 지난 가장 새 버전을 고르고, 계획(또는 결정 보고)에 그 사실을 쓴다.
- **알려진 취약점을 고치는 버전**은 7일을 기다리지 않는다. 그 취약점을 고친 버전 중 가장 낮은 버전을 고르고, 취약점 ID(GHSA, CVE)와 심각도, 공개일을 보고에 쓴다.
- 하위 의존성은 설치 명령의 날짜 제한으로 막는다. npm은 `--before <7일 전 날짜>`, uv는 `--exclude-newer`처럼 패키지 관리자가 주는 옵션을 쓴다.
  보안 수정이라 기다리지 않는 패키지는 날짜 제한을 그 버전의 공개일로 둔다. 날짜 제한이 없는 패키지 관리자면 하위 의존성의 공개일은 확인하지 않은 범위로 보고에 쓴다.
- 설치는 목표 버전을 지정하는 명령으로 한다(`npm install <패키지>@<버전>`, `poetry add <패키지>@^<버전>`). 범위 안 최신을 고르는 명령(`poetry update <패키지>`)은 판정 뒤 더 새 버전을 고를 수 있다.
  설치 뒤 lock 파일의 그 패키지 버전이 목표와 같은지 본다. 매니페스트의 범위가 바뀌면 그것도 판정 범위에 쓴다.
- 계획이 통과한 뒤에는 계획의 목표 버전을 쓴다. 그 사이 더 새 버전이 나와도 바꾸지 않는다.
  목표 버전이 철회됐거나(yank, unpublish) 새 취약점이 알려졌으면 그 패키지를 빼고 완료 보고에 쓴다.

## 테스트가 덮지 않는 사용처

업데이트는 제품 코드를 고치지 않지만, 바뀐 패키지를 부르는 곳의 결과가 바뀔 수 있다. 고정 테스트(`references/characterization.md`)는 위험이 있는 곳에만 둔다.

- **major이거나 변경 기록에 동작 변경이 적힌 업데이트**: 바뀐 API를 부르는 곳이 영향 경로다. 그곳의 결과를 지키는 테스트가 없으면 업데이트 행 앞에 고정 테스트를 두고 따로 커밋한다.
- **그 밖의 patch·minor**: 기존 테스트·빌드·타입 검사로 끝낸다. 테스트가 덮지 않는 사용처는 계획의 위험에 `<패키지>: <사용처>, 지키는 테스트 없음`으로 적는다.
- 지키는 테스트는 그 패키지의 코드를 실제로 거쳐야 한다. 패키지 자체를 mock으로 바꾼 테스트는 지키지 않는다. 패키지의 바깥(HTTP 응답, DB)만 흉내 내는 테스트(`responses`, `msw` 등)는 지킨다.

## 계획에 담는 것

SKILL.md 2절의 계획에 아래를 더한다. 계획 보고(`PLAN-<이름>`)에서 업데이트 표와 작업 표를 함께 판정받는다.

- **업데이트 표**: `| 패키지 | 지금 → 목표 | 종류 | 공개일 | 이유 | 변경 기록 요약 | 사용처와 지키는 테스트 |`.
  종류는 patch·minor·major·하위, 이유는 정기·취약점 ID·다른 업데이트에 필요, 변경 기록 요약은 이 저장소에 닿는 동작 변경·지원 중단·필요한 코드 수정이다.
  취약점으로 올리는 하위 의존성은 종류를 `하위`로 하고 패키지 칸에 끌어오는 직접 의존성을 함께 쓴다(`path-to-regexp (express 아래)`).
  그 밖에 lock 파일에서만 바뀌는 하위 의존성은 표에 넣지 않고 행마다 "하위 의존성 n개 함께 바뀜"으로 적는다.
- **끝의 정의**: 기존 테스트가 모두 그대로 통과함(이 계획에서 판정받은 테스트 수정만 예외), 빌드·타입 검사 통과, 고정 테스트 값 그대로, 표의 패키지가 목표 버전임, 이유로 적은 취약점이 점검 명령에서 사라짐.
- **작업 표**: 한 행이 끝날 때마다 모든 테스트가 통과해야 한다. "먼저 작성할 실패 테스트 / 완료 기준" 칸에는 그 행을 지키는 테스트와 완료 기준을 쓴다.
  - 취약점 행을 먼저 둔다. 다른 행이 실패해도 목적이 남게 하기 위해서다.
  - patch·minor는 위험이 비슷한 것끼리 한 행에 묶는다(개발 도구, 서버 라이브러리, 화면 라이브러리).
  - major는 패키지마다 한 행이다(함께 올려야만 동작하는 묶음은 한 행). 작업 칸에 이 저장소에 닿는 깨지는 변경과 고칠 코드를 적는다. 하나씩 되돌릴 수 있게 뒤에 둔다.
  - 고정 테스트가 필요한 행은 그 앞에 고정 테스트 행을 둔다.
- **보호 대상 변경 칸**: 그 행의 패키지와 목표 버전을 업데이트 표로 가리킨다.
  예: `package.json: 업데이트 표의 개발 도구 묶음 9개 (표의 목표 버전)`, `package.json: vitest 2.1.8 → 3.0.5`, `package-lock.json: path-to-regexp 0.1.7 → 0.1.12 (express 아래, lock 파일만)`.
  테스트를 고쳐야 하면 아래 "테스트를 고쳐야 할 때"대로 적는다.
- **확인 지점**: 화면을 그리는 라이브러리(UI 컴포넌트, CSS 프레임워크, 차트)의 minor·major 행과, 사용자 흐름을 다루는 라이브러리(라우터, 폼)의 major 행 뒤에 둔다.
  해볼 흐름은 그 라이브러리를 쓰는 화면과 흐름이다. 그 밖의 행은 사용자가 해볼 동작이 바뀌지 않으므로 두지 않는다.
- 계획 보고의 판단 재료에는 대상 찾기 명령과 결과 요약, 7일 규칙으로 낮춘 버전, 확인하지 않은 범위(설치하지 않은 점검 도구, 런타임·CI, 날짜 제한이 없는 하위 의존성)를 쓴다.

## 테스트를 고쳐야 할 때

패키지를 올리면 기대값은 그대로인데 테스트 파일을 고쳐야 할 수 있다. 훅은 이것을 기존 테스트 변경으로 막는다.
`references/refactoring.md`의 "테스트를 고쳐야 할 때"와 같이 기계적 수정을 **종류**로 칸에 적어 계획 판정으로 받는다.

- 패키지 이름이나 API 이름이 바뀐 major(`react-router-dom` → `react-router`)는 리팩터링의 종류 중 import 경로와 이름 변경을 쓴다.
- 테스트 도구(vitest, jest, pytest 등)를 올릴 때는 아래 두 종류를 더 쓸 수 있다.

  | 종류 | 예 |
  | --- | --- |
  | 도구의 변경 기록에 이름만 바뀐 것으로 적힌 API (별칭 제거 포함) | `toBeCalledWith(` → `toHaveBeenCalledWith(` (Jest 30) |
  | 도구의 변경 기록에 적힌 스냅숏 머리말·직렬화 형식 | `Object {` → `{` (Jest 29의 기본 스냅숏 형식) |

칸에는 `테스트의 기계적 수정: 도구 API 이름 변경, 스냅숏 형식 (Jest 29 변경 기록, 기대값·입력 변경 없음)`처럼 근거가 되는 변경 기록과 함께 쓴다.

- 스냅숏은 실제로 차이가 날 때만 다룬다. 새 버전에서 그대로 통과하면 고치지 않는다.
  옛 형식을 유지하는 설정이 있으면(Jest의 `snapshotFormat`) 그쪽은 테스트를 고치지 않는다. 어느 쪽으로 할지 계획에 적는다.
- 스냅숏 형식을 바꾸기로 한 행에서만 전체 갱신 옵션(`-u`)을 쓸 수 있다. 그 뒤 바뀐 줄을 모두 대조해 형식 변경으로 설명되지 않는 줄이 하나라도 있으면 범위를 넘은 것이다.
- 도구의 동작이 바뀌어 단언이나 기대값을 고쳐야 하면(오류 비교가 엄격해짐 등) 기계적 수정이 아니다. 계획을 쓸 때 알았으면 고칠 단언을 테스트 이름마다 칸에 적고(판정 질문 ②),
  실행 중에 알게 되면 아래 "실행" 3단계대로 결정으로 올린다.

## 실행

행마다 SKILL.md 3절 사이클을 돌되, 새 실패 테스트가 없으므로 Red 대신 이렇게 한다.

1. 행을 시작하기 전에 모든 테스트가 통과하는지 본다. 이미 실패하는 테스트가 있으면 `references/refactoring.md`의 "실행" 1단계와 같이 한다.
2. 그 행의 패키지만 목표 버전으로, 날짜 제한 옵션을 붙여 설치한다. lock 파일에서 그 행의 패키지와 그 하위 의존성 밖의 버전이 바뀌었으면 되돌리고 다시 한다.
3. 테스트·빌드·타입 검사를 돌린다. 기대값을 고쳐 맞추지 않는다.
   - major 행이면 작업 칸에 적은 코드 수정을 한다.
   - 실패하면 원인 패키지를 찾는다. 묶음이면 반씩 나눠 설치해 좁힌다.
   - **patch·minor 묶음의 원인 패키지**(취약점 행 제외)는 그 행에서 빼고(되돌리고) 나머지로 진행한다. 범위를 줄이는 것이라 판정 없이 하고,
     완료 보고의 "계획 대비 달라진 점"에 이유(실패한 테스트, 필요한 수정)와 함께 써서 따로 할지 묻는다.
   - **major 행과 취약점 행**에서 적지 않은 코드·테스트 수정이 필요하거나 고정 테스트 값이 바뀌면 그 행을 되돌리고 결정으로 올린다(판정 ID는 행 ID, SKILL.md 3절 5단계).
     빼는 안과 고치는 안(고칠 코드, 테스트 이름마다 바뀌는 단언, 바뀌는 동작)을 함께 쓴다. 사용자가 보는 동작이 바뀌는 안이면 그 패키지는 기능 개발로 따로 한다고 쓴다.
   - 지원 중단 경고가 새로 나오면 완료 보고의 우려에 쓴다.
4. 화면 라이브러리의 patch 행은 바꾸기 전과 같은 조건으로 캡처해 비교한다(작은 수정의 4단계 규칙). 다르면 확인 지점을 더한다(등급은 올리기만 한다, SKILL.md 3절 5단계).
5. 스테이징한 테스트 파일을 모두 대조한다(`references/refactoring.md`의 "실행" 4단계). 테스트를 고치지 않았다고 생각한 행도 한다.
   스테이징한 매니페스트와 lock 파일도 그 행의 보호 대상 변경 칸과 대조한다.
6. 로그를 쓴다. Red 칸에는 `의존성 업데이트: 새 실패 테스트 없음, 지키는 테스트: <테스트 또는 고정 테스트>`를 쓴다.
   사유에는 `계획 판정: <패키지> <지금> → <목표> (업데이트 표)`와, 있으면 테스트의 기계적 수정 종류, 패키지 관리자 버전 차이로 바뀐 줄 수를 쓴다.
7. 로그까지 스테이징하고 `approve --for <행 ID>` → 커밋한다(SKILL.md 3절 8단계). approve와 커밋 사이에는 아무 파일도 고치지 않는다.

뺀 패키지를 따로 하기로 하면 그 패키지로 이 절차를 새로 시작한다. 코드나 테스트를 고쳐야 하므로 보통 계획이다.
결정이 새로 생기지 않으면 계획 보고 다음 정지는 완료 보고다(확인 지점을 둔 경우는 그 확인).

## 패키지 하나

1. **알림과 브랜치**: `의존성 업데이트로 처리함: <패키지> <지금> → <목표>`를 알리고 기다리지 않고 진행한다. main에서 `deps/<이름>`을 딴다.
2. **목표 버전과 변경 기록**: 위 "목표 버전 고르기"대로 고르고, 지금 버전부터 목표 버전까지의 변경 기록을 읽는다.
3. **설치와 검사**: 목표 버전을 지정하고 날짜 제한을 붙여 설치한 뒤 테스트·빌드·타입 검사를 돌린다. 화면 라이브러리면 전후 캡처를 비교한다.
   위 "어느 경로로 가나"의 조건에 맞지 않게 되면(코드를 고쳐야 함, 테스트 실패, 캡처가 다름) 계획으로 간다. 보고 전이라 되돌릴 기록이 없다.
   브랜치 이름을 `deps/<계획 이름>`으로 바꾸고(`git branch -m`, 상태 파일이 있으면 그 이름도 맞춤) 계획 보고에 이 사실을 쓴다.
4. **DEP 보고**: 결정 보고(SKILL.md 4절)의 한 종류다. 판단 재료 자리에는 다음을 쓴다.
   1. 지금 → 목표, 종류, 공개일 (7일이 안 됐으면 기다리지 않는 이유)
   2. 이유: 사용자 요청, 또는 취약점 ID와 심각도와 이 제품이 그 취약한 기능을 쓰는지
   3. 변경 기록 요약: 이 저장소에 닿는 것. 없으면 "없음"
   4. 바뀌는 파일과 하위 의존성 변화, 사용처와 지키는 테스트, 확인하지 않은 범위
   5. 같은 내용의 봇 PR이 있으면 그 번호와, 이 PR이 병합되면 닫히거나 닫아도 된다는 것
   보고 전에 로그(`node scripts/gated-tdd/log-new.mjs "DEP-<이름>: <패키지> <지금> → <목표>" --gate 결정`)와 상태 파일("판정 대기"에 `DEP-<이름>`,
   "다음 할 일"에 커밋하지 않은 매니페스트와 lock 파일, 설치 명령)을 쓰고, 상태 파일만 커밋하고 push한다(SKILL.md 1절). 보고하고 멈춘다.
5. **통과하면**: 커밋하기 전에 `git fetch`로 원격 main을 본다.
   - 원격 main의 매니페스트나 lock 파일이 브랜치를 딴 뒤 바뀌었으면, 설치한 변경을 되돌리고 `git merge origin/main`을 한 뒤(이 브랜치에는 상태 파일 커밋뿐이라 보호 대상이 부딪히지 않음) 같은 명령으로 다시 설치한다.
     바뀐 버전이 판정받은 것(그 패키지와 그 하위 의존성)과 같으면 같은 판정으로 커밋한다. 다르면 다시 보고한다.
   - 원격 main이 이미 목표 버전 이상을 담고 있으면(봇 PR이 먼저 병합됨) 커밋하지 않고, 로그와 상태 파일에 그 사실을 적어 알린다.
   - 그 밖에는 SKILL.md 5절대로 매니페스트, lock 파일, 로그를 `approve --for DEP-<이름>`으로 함께 커밋한다. 커밋 제목은 `chore: DEP-<이름> <패키지> <지금> → <목표>`다.
   push하고 PR을 연 뒤 PR 주소를 알린다. 판정할 것이 남지 않았으므로 완료 보고는 이 한 줄로 끝난다.
   수정이 오면(다른 버전으로) 다시 설치하고 다시 보고한다.

판정을 기다리는 동안 다른 작업이 끼어들면 커밋하지 않은 매니페스트와 lock 파일은 SKILL.md 7절의 "작업 보류"로 미뤄 둔다.

## lock 파일이 양쪽에서 바뀐 병합

작업 브랜치에 `git merge origin/main`을 할 때 lock 파일이 양쪽에서 바뀌었으면 손으로 합치지 않는다. 충돌 표시를 지우며 합친 lock 파일은 해시가 어긋나거나 어느 쪽의 의도와도 다를 수 있다.

1. lock 파일은 main 쪽을 받는다(`git checkout --theirs <lock 파일>`, 병합해 들어오는 쪽이 `--theirs`다). 매니페스트는 양쪽 변경을 합친다.
2. 이 브랜치가 판정받은 설치를 같은 명령으로 다시 한다. lock 파일의 버전 변화가 main 쪽 변경과 이 브랜치의 판정 범위를 합친 것과 같은지 본다.
3. 그다음은 SKILL.md 5절의 "main 반영"대로 `MERGE-main-<날짜>` 결정 보고를 한다. 보고에는 파일마다 main 쪽 변경, 이 브랜치 쪽 변경, 다시 설치한 결과를 쓴다.

## 마감

- 동작 명세(`docs/behavior/`)는 고치지 않는다. 동작이 그대로이기 때문이다.
- 완료 보고는 작은 수정과 같은 세 칸(바꾼 것 / 일부러 안 건드린 것 / 우려되는 점)에 아래를 더한다.
  - 업데이트 표의 최종 버전과 점검 명령의 전후 결과(취약점 수 등)
  - 계획 대비 달라진 점: 뺀 패키지와 이유 (없으면 "계획대로")
  - 확인하지 않은 범위
- push하고 PR을 연다. 병합은 사용자가 고른다.

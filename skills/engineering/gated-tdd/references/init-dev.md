# 초기 개발: 제품 명세부터 골격까지

제품이 아직 없을 때 쓴다. 빈 저장소이거나, 코드가 있어도 실행해 볼 제품이 없는 경우다.
제품이 있으면 기존 제품에 기능을 더하는 기능 개발이다. 그때는 이 파일이 아니라 `references/requirements.md`를 따른다.

## 순서

1. **최소 도입**: SKILL.md 1절을 한다. 테스트 도구 확인과 CI는 아직 도구가 없으므로 4단계 골격에서 한다.
   - 원격 저장소가 없거나 원격에 기본 브랜치가 없으면, 훅을 설치하기 전에 묻는다: 원격을 연결할지(주소),
     빈 첫 커밋을 기본 브랜치로 push할지. 훅을 설치한 뒤에는 보호 브랜치로 push할 수 없어 PR 대상이 생기지 않는다.
   - 로컬만 쓰겠다고 하면 PR 대신 사용자가 병합을 직접 고른다고 상태 파일에 적는다.
   - 기본 브랜치가 `main`이나 `master`가 아니면 `.gated-tdd.json`의 `protectedBranches`를 맞춘다.
   - 커밋이 하나도 없으면 기본 브랜치에 빈 첫 커밋을 만든 뒤 `chore/gated-tdd`를 딴다. 원격이 없어도 같다.
   - 아직 무엇으로 만들지 모르므로 `.gated-tdd.json`은 `references/approval-gate.md`의 기본값 내용으로 만들고, `AGENTS.md`의 테스트·빌드
     명령은 `미정 (골격에서 정함)`으로 쓴다. 도입 보고는 장치 설치만 판정받고, 보호 대상은 골격 계획에서 맞춘다고 쓴다.
2. **제품 명세**: `references/requirements.md`의 요구 대화로 `docs/spec/product.md`를 쓴다. 기능 지도의 첫 기능은
   항상 `skeleton`이다. 골격의 기능 요구 `docs/spec/skeleton.md`(가장 얇은 흐름 하나의 시나리오)도 함께 써서
   요구 보고 한 번에 두 부분(`SPEC-product`, `SPEC-skeleton`)으로 판정받고 멈춘다. 두 파일은 `feat/skeleton`
   브랜치에 쓴다. 도입 PR이 아직 병합되지 않았으면 `chore/gated-tdd`에서 딴다.
3. **골격 계획**: 통과하면 `docs/plan/skeleton-개발계획.md`를 SKILL.md 2절대로 세운다. 만드는 방식이 정해졌으므로
   아래 "게이트 설정" 행으로 보호 대상과 테스트·빌드 명령을 이 저장소에 맞춘다.
4. **골격**: 골격 사이클을 돌리고 첫 확인 지점에서 멈춘다.
5. **이후 기능**: 기능 지도 순서대로 기능 개발(요구 → 계획 → 사이클)을 한다.

제품 명세가 통과하기 전에는 짓지 않는다. 제품 코드, 프로젝트 생성, 의존성 설치, 계획 작성이 모두 해당한다.
읽기와 조사, 사용자가 동의한 spike(`references/requirements.md`)는 해도 된다.

## 골격

첫 기능은 가장 얇은 사용자 흐름 하나를 끝에서 끝까지 통과시키는 골격(walking skeleton)이다.
기능은 거의 없어도 이후 모든 행이 기댈 길(빌드, 테스트, 실행, CI, 합의했다면 배포)을 처음부터 이어 둔다.

작업 표의 출발점이다. 저장소에 맞게 고친다.

| 행 | 완료 기준 | 게이트 | 보호 대상 변경 |
| --- | --- | --- | --- |
| 프로젝트 생성과 의존성 | 제품 명세의 "만드는 방식"대로 생성, 빌드 성공 | 자동 | 생성 도구와 그 기본 의존성, 더하는 패키지 이름 |
| 테스트 러너 | 고의로 실패하는 테스트가 0이 아닌 코드로 끝남. 그 테스트는 확인만 하고 커밋하지 않음 | 자동 | 테스트 도구 패키지 |
| 게이트 설정 | `.gated-tdd.json`의 `decide`·`tests`가 고른 스택의 보호 경로(인증·권한 위치 등)와 테스트 파일 패턴을 담음, `AGENTS.md`의 테스트·빌드 명령이 실제로 동작함 | 자동 | `.gated-tdd.json`의 바뀌는 내용 전체 |
| 첫 흐름 | `skeleton.md`의 시나리오를 바깥 경계(브라우저, HTTP, CLI)에서 검증하는 테스트를 Red부터 통과 | 자동 (확인은 CI 뒤) | |
| CI | 재사용 워크플로 하나가 PR에서 위 테스트를 돌림 | 확인 지점: 첫 흐름을 직접 해봄 | `.github/workflows/`에 추가할 파일과 돌릴 명령 |
| 배포 (제품 명세에서 합의했을 때만) | 같은 흐름이 배포 환경에서 동작. PR에서 테스트를 통과한 코드만 배포됨(SKILL.md 1절) | 결정 (판정 질문 ③) | |

- 프로젝트 생성, 테스트 러너, CI처럼 설정 작업인 행은 완료 기준으로 판정한다(SKILL.md 3절).
- 첫 확인 지점은 첫 흐름을 사용자가 직접 해보는 것이다. 뒤의 모든 기능이 기대는 토대다. CI 행까지 끝낸 뒤에 두어,
  확인을 통과하면 바로 골격 마감이 되게 한다(마지막 확인 지점 통과가 기능 마감이다). 배포 행이 있으면 배포 환경에서
  같은 흐름을 해보는 확인 지점을 하나 더 두고, 그것이 마지막 확인 지점이 된다.
- 보호 대상 변경 칸에는 제품 명세에서 이미 정한 것과, 그 밖에 AI가 더한 것(의존성, 설정)을 나눠 쓴다.
  생성 도구가 만드는 기본 의존성은 "`<도구>` 기본값"으로 적고, 그 밖에 더하는 패키지는 이름으로 적는다.
  칸에 없는 패키지나 설정이 생기면 범위를 넘은 것이다(SKILL.md 3절 8단계).
- 확인 지점을 통과하면 `references/requirements.md`의 "동작 명세에 합치기"로 골격을 마감한다.

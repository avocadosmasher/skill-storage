# 게이트 TDD 개발 절차

작은 태스크 하나를 테스트 먼저 만들고, 사용자가 "통과"라고 말해야만 커밋한다.
에이전트는 구현·자동 검사·기록을 맡고, 사용자는 화면과 실제 동작만 판정한다.
사용자 대상 문서와 응답은 사용자의 언어로 쓴다.
에이전트의 모든 사용자 대상 응답은 개조식·두괄식으로 쓴다: 결론을 가장 먼저 말하고, 같은 내용을 반복하지 않는다.

## 0. 세션 시작

1. `STATUS.md`만 읽는다. 없으면 "1. 도입"부터 한다.
2. 과거 경위가 필요하면 `docs/log/INDEX.md`에서 한 줄을 고르고 그 항목 파일 하나만 연다.
   로그 전체를 통독하지 않는다.
3. 저장소의 작업 규칙과 현재 사용자 요청을 확인한다. STATUS의 "판정 대기"는
   실제 사용자 판정 기록·해당 커밋과 대조한다. 동일 변경의 통과와 커밋이 확인되면
   문서 갱신 지연으로 취급하고 재승인을 요구하지 않는다. 새 변경에는 별도 판정이 필요하다.
   증거가 없으면 미확인으로 두고 판정을 요청한다. 현재 작업의 검토·수정 요청은 먼저 수행한다.
4. 코드 탐색은 도구와 인덱스가 있으면 Graft를 먼저 쓴다.
   위치·설명은 `graft ask "작업" --source`, 전체 출현은 `graft grep "식별자"`,
   변경 전 호출 영향은 `graft callers 식별자 --depth all`로 확인한다.
   필요한 소스 범위만 읽고 큰 코드 변경 후 `graft build`로 갱신한다.

## 1. 도입 (장치가 없는 저장소)

사용자가 도입을 요청한 범위에서 준비한다. 기존 규칙·훅은 보존하고 통합한다.
이미 승인된 도입을 다시 묻지 않는다. 단순 기능 작업을 저장소 전체 절차 도입으로 확대하지 않는다.

- `AGENTS.md`: 이 파일의 2~6절을 저장소 규칙으로 옮긴다.
- `CLAUDE.md` 첫 줄: "세션을 시작하면 STATUS.md부터 읽는다."
- `STATUS.md`: `최종 갱신: YYYY-MM-DD` 줄, 지금(작업 브랜치·마지막 통과·판정 대기·다음 할 일), 최근 3건, 문서 위치 표.
- `docs/plan/` 계획 · `docs/decision/` 결정 근거 · `docs/log/` 작업 이력(항목당 1파일)
  · `docs/guide/` 사람이 읽는 운영법 · `docs/archive/` 끝난 단계.
- `docs/log/INDEX.md`: 표 `| 항목 | 날짜 | 결론 | 상태 | 파일 |`, 구분선은 `| --- | ... |`, 최신이 위.
- `scripts/log-new.mjs "<제목>" [--id X01] [--summary ..] [--status ..]`:
  이 스킬의 `assets/log-new.mjs`를 복사한다.
  `docs/log/NN-<slug>.md` 생성(시작 기준·문제·요청·Red·수정·자동 검사·남은 제약 틀),
  INDEX 표 머리 바로 아래에 한 줄 추가, STATUS의 "최종 갱신" 날짜 갱신을 한 번에 한다.
- `scripts/manual-review.mjs` + 테스트 + `.githooks/pre-commit`·`pre-push`: 이 스킬의 `assets/`에서 복사하고(부록 A)
  `git config core.hooksPath .githooks` (기존 훅 경로가 있으면 통합).
   `node --test scripts/manual-review.test.mjs`로 격리된 임시 저장소에서 최초 커밋과 일반 커밋의 승인·push가 가능하고,
   승인 없음·승인 후 스테이징 변경·추가 커밋 push·ref 삭제는 막히는지 확인한다.
- 테스트 도구 설치 후 고의 실패 시 명령이 0이 아닌 코드로 끝나는지 확인한다.
- CI: 검사를 재사용 워크플로 하나로 두고 PR 경로와 배포 경로가 같이 쓴다.
  배포에는 검사를 통과한 그 산출물을 올린다.

## 2. 계획: 구현 전에 사용자와 합의

`docs/plan/<기능>-개발계획.md`에 다음을 쓴다.

- 끝의 정의: 요청한 범위와 규모에 맞춰 합의한다. 작은 수정은 관련 검사·기록·사용자 판정으로 마감할 수 있다.
  배포가 범위에 있으면 배포 인수, 운영 기능이면 필요한 운영 안내를 포함한다.
  Fragments 전체 개발에서는 운영 배포 검증·운영 가이드·최종 보고서까지 합의했다.
  이미 합의한 핵심을 빼고 완료로 치지 않는다.
- 제외 범위: 이번에 하지 않는 것을 명시한다.
- 작업 표: `| ID | 작업 | 선행 | 먼저 작성할 실패 테스트 / 완료 기준 |`.
  한 행은 혼자서 통과/실패를 판단할 수 있는 크기. ID는 영역 알파벳 + 번호(A01, B02 …).
- 테스트 계층: 단위 / 통합(격리 fixture + 실제 빌드) / 브라우저(최종은 빌드 산출물 preview) / 실제 연동 / 배포 인수.
- 위험한 외부 연동은 앞쪽에 최소 실험으로 둔다. 실패하면 원인을 분류하고 대안을 먼저 제시한다.

## 3. 사이클: 판정 가능한 작은 작업 단위

1. **Red**: 기대 동작을 테스트로 먼저 쓰고 실행해 실패를 확인한다.
   - 설치 실패·서버 미실행은 Red가 아니다. 모듈 부재 실패와 assertion 실패를 구분해 기록한다.
   - 사례가 여럿이면 한 사례씩 Red → Green.
   - 설정 조사·외부 연결·문서 작업에는 억지 테스트를 만들지 않고 완료 기준으로 판정한다.
   - 내부 호출 순서나 CSS 클래스 문자열이 아니라 사용자가 보는 결과와 데이터 계약을 검증한다.
2. **Green**: 통과시키는 최소 구현.
3. **Refactor**: 정리 후 해당 테스트와 영향받는 회귀 테스트를 다시 돌린다.
4. **자동 검사**: 변경 영향과 저장소 필수 게이트에 맞춰 타입·단위·통합·빌드·E2E 중 필요한 검사를 수행한다.
   출력은 요약 리포터로, 실패했을 때만 상세를 본다.
5. **기록**: `node scripts/log-new.mjs "<ID>: <제목>"`로 항목을 만들고 채운다.
   INDEX의 결론 한 줄에는 제목이 아니라 "무엇이 문제였고 어떻게 정했는지"를 적는다.
   STATUS의 "지금"과 "최근 3건"을 갱신한다.
6. **스테이징**: 이 작업의 파일만 `git add`한다.
7. **작업 결과 보고**를 제시하고(4절) **멈춘다.** 다음 작업으로 넘어가지 않는다.

## 4. 작업 결과 보고 형식

개조식·두괄식으로 쓴다. 결론을 가장 먼저 말하고, 같은 사실을 두 번 말하지 않는다.
"이 규칙에 따라 멈춥니다" 같이 스킬 규칙을 인용하는 메타 설명은 쓰지 않는다.
항목이 둘 이상이면 한 문장에 늘어놓지 않고 번호 목록(1. 2. 3. ...)으로 쓴다.
"판정 필요: A, B"처럼 라벨 뒤에 쉼표로 잇는 것도 한 줄 나열이다.
그 아래 하위 목록이 필요하면 번호 대신 bullet(•)을 쓴다. 줄 안에서 구분이 필요해도
em dash(긴 줄표)로 잇지 않는다: 쟁점과 설명은 "선택:", "버린 대안:"처럼 이름 붙은 하위 항목으로
나누고, 화살표(→)는 조작과 그 결과처럼 방향이 있는 짝에만 쓴다.

- **결론**: 끝난 일과 지금 필요한 판정. 항목이 여러 개면 목록으로 쓴다.
- **판단 재료** (방향·스펙을 판정할 때): 쟁점마다 하위 항목으로 선택한 안, 검토했지만
  버린 대안과 이유, trade-off(이 선택으로 가능해지는 것·안 되는 것·미룬 것)를 나눠 쓴다.
  코드가 어떻게 짜였는지가 아니라 왜 이 방향을 골랐는지를 쓴다.
- **확인 방법** (실행해서 보고 판정할 때): 번호별로 "조작 → 기대 결과"를 짝지어 쓴다.
- **자동 검사**: 돌린 검사마다 통과·실패를 목록으로 쓰고, 돌리지 않은 범위와 이유를 밝힌다.
- **판정 요청**: "직접 확인 후 '통과' 또는 '수정: [문제와 원하는 변경]'으로 알려주세요."

판단 재료와 확인 방법은 상황에 맞게 하나만 쓰거나 둘 다 쓴다. 둘 다 없는 보고는 만들지 않는다.

### 시각 정보

글보다 빨리 읽히는 경우에만 쓴다. 해당하지 않으면 넣지 않는다.

| 상황 | 표현 |
| --- | --- |
| 대안 2개 이상을 기준 2개 이상으로 비교 | 표 (행: 대안, 열: 기준). 아니면 bullet 하위 항목 |
| 하위 작업 여럿 중 일부만 끝남 | bullet 뒤에 `[x]`(완료)·`[ ]`(남음). dash로 시작하는 마크다운 체크리스트(`- [x]`)는 쓰지 않는다 |
| 수치 전후 비교 | `응답 시간: 320ms → 180ms` 한 줄. 지표가 여럿이면 표 |
| 배치·색·크기 같은 시각 결정 | 캡처 이미지 경로 (아래 1) |
| 구조·흐름 설명 | 다이어그램 (아래 2) |

다른 스킬은 사용 가능한 스킬 목록에 있을 때만 연계한다. 없으면 자체 형식으로 쓴다.

1. 시각 결정
   • 있으면: Skill 도구로 `capture-compare`를 호출해 비교 시트를 만들고 그 경로를 적는다.
   • 없으면: 같은 조건(창 크기·데이터·상태)에서 후보를 직접 캡처해 경로를 나열한다.
     캡처할 수 없는 환경이면 후보별 차이를 표로 쓰고, 실제 화면에서 볼 위치를 적는다.
2. 구조·흐름
   • 있으면: Skill 도구로 `archify`를 호출해 다이어그램 파일을 만들고 그 경로를 적는다.
   • 없으면: 코드 블록 안에 화살표로 흐름을 그린다. 노드가 10개를 넘으면 그리지 않고
     번호 목록으로 단계를 쓴다.

사용자에게는 사람이 봐야 아는 것만 요청한다.
- 요청한다: 방향·스펙 선택, 배치·색·크기·문구 같은 심미 판단(화면이 바뀌면 캡처를 함께),
  실제 앱에서 눌러 보는 기능, 외부 계정·서비스가 얽힌 흐름.
- 요청하지 않는다: 자동 검사 실행, `git diff`로 내용 확인. 에이전트가 하고 결과만 보고한다.
- 사람이 볼 것이 없는 변경이면 그 사실과 근거를 밝히고 판정만 요청한다.
- 사용자가 직접 실행할 수 없는 환경이면 이유와 확인 시점·장소를 명시한다.

## 5. 판정 후

- **통과**: `node scripts/manual-review.mjs approve` → `git commit` → 개발 브랜치 `git push`.
  승인 이후에는 파일을 그대로 커밋한다. 로그·INDEX·STATUS의 상태·해시 갱신은
  다음 작업의 검토 범위에 포함한다. 다음 작업이 없으면 상태 갱신만 별도 검토받을 수 있다.
  다음 세션은 0절에 따라 실제 판정 기록·커밋을 확인하므로, 남아 있는 대기 문구만으로
  완료한 작업의 재승인을 요구하지 않는다. 자기 해시를 넣으려고 amend를 반복하지 않는다.
- **수정**: 고치고 → 자동 검사 → 새 가이드 → 판정 대기를 반복한다.
- 승인 후 파일이 바뀌면 다시 판정받는다.
- 금지: `--no-verify`, 훅 비활성화, 승인 파일 조작, 사용자 대신 '통과' 작성, 판정 전 approve 실행,
  이전 작업의 승인·무응답·자동 테스트 성공을 승인으로 해석하기.
- push가 실패하면 로컬 커밋을 보존하고 원인을 기록한다. 성공 확인 전에 완료라고 쓰지 않는다.

## 6. 판단 규칙

- **시각 결정**은 코드를 고치기 전에 2~8개 시안을 같은 조건에서 캡처해 비교 시트로 보여 주고 고르게 한다.
  사용 가능한 스킬에 `capture-compare`가 있으면 Skill 도구로 호출해 그 절차를 따르고, 없으면 직접 캡처한다(4절 시각 정보).
  고른 안을 반영하는 작업도 3절 사이클과 판정을 거친다.
- **추측하지 말고 잰다.** 성능·원인은 측정으로 확인하고, 측정 결과로 문제를 다시 정의한다.
- **선택지가 있는 결정**은 `docs/decision/`에 검토한 선택지·선택·근거·틀렸던 가정을 남긴다.
  구현 중 결정의 전제가 틀렸음이 드러나면 그 사실도 적는다.
- **운영 보호는 구조로.** 테스트는 운영 데이터를 고정값으로 쓰지 않고 산출물에서 읽어 검사한다.
  운영 쓰기는 명시적 opt-in이 있을 때만 열린다.
- **실패는 숨기지 않는다.** 화면·로그에 사유와 링크를 남긴다. 비밀값 생성 같은 중요한 단계는 실패하면 즉시 멈춘다.
- **규칙이 바뀌면** 테스트를 새 의도에 맞게 고치고 그 이유를 기록한다.
- **사용자에게 의미 있는 단위로 센다** (커밋 수가 아니라 바뀐 항목 수).
- **브랜치**: 개발은 `feat/<기능>`에서. 개발 브랜치 push ≠ 배포.
  `main` 병합은 그 배포 범위의 인수 조건 + build·preview 검증 + 사용자 판정 후 PR로.
  공개할 방법이 없는 반쪽 기능은 병합하지 않는다.

## 7. 마감

2절에서 합의한 산출물만 작성한다. 아래는 운영 기능 전체 개발의 예시다.

- `docs/guide/<기능>-운영가이드.md`: 평소 작업 흐름, 동작 원리, 시행착오와 선택, 한계, 설정 위치.
- 최종 보고서: 계획 요약이 아니라 실제로 무엇이 동작하는지와 근거(검사 결과·운영 반영 이력·사람이 확인한 것),
  제약과 미해결 항목, 후속 과제 표(우선순위·이유).
- 운영 배포까지 합의했다면 운영 사이트에서 해당 흐름을 확인한 뒤에 전체 완료로 표시한다.
  배포가 없는 작업에는 운영 검증을 요구하지 않는다.

## 부록 A. 승인 게이트

이 스킬의 `assets/`에 실제 파일이 있다. 저장소로 복사해 쓴다.

| 스킬 안 파일 | 저장소 위치 | 역할 |
| --- | --- | --- |
| `assets/manual-review.mjs` | `scripts/manual-review.mjs` | `approve`: HEAD·스테이징 트리 기록 / `check-commit`·`check-push`: 대조 |
| `assets/manual-review.test.mjs` | `scripts/manual-review.test.mjs` | 격리된 임시 저장소에서 게이트 동작 검증 (`node --test`) |
| `assets/githooks/pre-commit` | `.githooks/pre-commit` | `check-commit` 호출 |
| `assets/githooks/pre-push` | `.githooks/pre-push` | `check-push` 호출 |
| `assets/log-new.mjs` | `scripts/log-new.mjs` | 로그 항목 + INDEX 한 줄 + STATUS 날짜 |

복사 후 훅 파일에 실행 권한을 주고(`chmod +x .githooks/*`) `git config core.hooksPath .githooks`를 설정한다.

승인 정보는 `.git/manual-review.json`에 저장되며 버전 관리하지 않는다.
훅은 대화를 읽지 못하므로 실제 사용자 판정 확인은 에이전트의 책임이다.
이 예제는 첫 커밋 전의 기준을 null로 기록해 최초 커밋도 검증한다.
승인 트리와 다른 스테이징 내용은 차단하지만 미스테이징·미추적 변경은 검사하지 않는다.
push 검사는 승인받은 단일 커밋의 트리와 부모를 확인한다. 병합 커밋·여러 커밋의 일괄 push는
별도 승인 설계가 필요하며, 이 예제를 그대로 써서 지원한다고 간주하지 않는다.

# 게이트 TDD 개발 절차

작은 단위를 테스트 먼저 만들고 단위마다 커밋한다. 사용자는 두 가지만 판정한다.
AI가 대신 정할 수 없는 **결정**, 그리고 직접 해볼 수 있는 기능 묶음의 **확인**이다.
나머지는 기록과 알림을 남기고 묻지 않고 진행한다. main 병합은 사용자가 PR로 고른다.
사용자 대상 문서와 응답은 사용자의 언어로 쓴다. 보고는 4절의 두괄식·개조식 규칙을 따른다.

## 0. 세션 시작

1. `STATUS.md`만 읽는다. 없으면 "1. 도입"부터 한다.
2. `node scripts/budget.mjs start`로 세션 시작을 기록한다.
3. STATUS의 "판정 대기"·"확인 대기"를 실제 사용자 판정 기록·커밋과 대조한다. 판정이 확인되면
   문서 갱신 지연으로 보고 다시 묻지 않는다. 확인되지 않은 **확인 대기가 있으면 그 확인부터 요청하고,
   확인 전에는 다음 묶음으로 넘어가지 않는다.** 현재 작업의 검토·수정 요청은 먼저 수행한다.
4. 과거 경위가 필요하면 `docs/log/INDEX.md`에서 한 줄을 고르고 그 항목 파일 하나만 연다.
5. 코드 탐색은 도구와 인덱스가 있으면 Graft를 먼저 쓴다(`graft ask "작업" --source`,
   `graft grep "식별자"`, `graft callers 식별자 --depth all`). 큰 변경 후 `graft build`.

## 1. 도입 (장치가 없는 저장소)

사용자가 요청한 범위에서 준비한다. 기존 규칙·훅은 보존하고 통합한다. 승인된 도입을 다시 묻지 않는다.

- `AGENTS.md`: 이 파일의 2~7절을 저장소 규칙으로 옮긴다. `CLAUDE.md` 첫 줄: "세션을 시작하면 STATUS.md부터 읽는다."
- `STATUS.md`: `최종 갱신: YYYY-MM-DD`, 지금(작업 브랜치·마지막 커밋·판정 대기·확인 대기·다음 할 일),
  자동 진행 내역(마지막 정지 보고 이후), 최근 3건, 문서 위치 표.
- `docs/plan/` 계획 · `docs/decision/` 결정 근거 · `docs/log/` 작업 이력(항목당 1파일) · `docs/guide/` 운영법 · `docs/archive/` 끝난 단계.
  `docs/log/INDEX.md`는 표 `| 항목 | 날짜 | 결론 | 상태 | 파일 |`, 최신이 위.
- 스크립트와 훅: 이 스킬의 `assets/`에서 복사하고 `references/approval-gate.md`대로 설치·검증한다.
- `.gated-tdd.json`: 보호 경로·테스트 경로·보호 브랜치·예산 임계치를 이 저장소에 맞춰 제안하고 사용자가 확정한다.
- 테스트 도구는 고의 실패 시 0이 아닌 코드로 끝나는지 확인한다. CI는 재사용 워크플로 하나를 PR과 배포가 같이 쓴다.

## 2. 계획: 구현 전에 합의

`docs/plan/<기능>-개발계획.md`에 쓴다.

- **끝의 정의**와 **제외 범위**: 요청한 범위와 규모에 맞춘다. 합의한 핵심을 빼고 완료로 치지 않는다.
- **작업 표**: `| ID | 작업 | 선행 | 먼저 작성할 실패 테스트 / 완료 기준 | 게이트 |`.
  한 행은 혼자서 통과/실패를 판단할 수 있는 크기. ID는 영역 알파벳 + 번호(A01, B02 …).
- **게이트**: 행마다 AI가 제안하고 사용자가 확정한다.

  | 판정 질문 | 예이면 |
  | --- | --- |
  | ① 선택: 합리적인 안이 둘 이상이고 정답이 사용자의 의도·우선순위·제약에 달렸나? | 결정 |
  | ② 합의 변경: 계획·스펙·테스트 기대값·범위를 바꾸거나 모호한 요구를 해석하나? | 결정 |
  | ③ 되돌리기 어려움: 스키마·데이터 삭제, 공개 API 계약, 인증·권한, 개인정보, 비밀값, 비용, 배포? | 결정 |
  | ④ 사람만 확인 가능: 화면·문구·사용감, 실제 계정·기기·외부 연동? | 확인 지점에 묶음 |
  | 전부 아니오, 완료 기준을 자동 검사로 증명 | 자동 |

- **결정 목록**: 계획에서 미리 정할 수 있는 결정을 모아 한 번에 받는다. 지식·기능·보안·비용 네 갈래를 훑어
  결정이 숨은 곳을 찾는다. Skill 도구에 `grill-me-plus`가 있으면 호출해 결정을 캐묻는다.
- **확인 지점**: `| 확인 지점 | 포함 행 | 해볼 흐름 | 결과 |` 표로 둔다.
  1. 사용자 흐름 하나를 처음부터 끝까지 직접 해볼 수 있게 된 행에 둔다. 해볼 것이 없으면 두지 않는다.
  2. 뒤의 여러 행이 기대는 토대가 해볼 수 있는 상태가 되면 그 직후로 앞당긴다.
  3. 모호하거나 처음 다루는 영역은 짧게, 스펙이 분명하면 길게 잡는다.
  계획은 기능 하나를 데이터부터 화면까지 관통하는 **수직 슬라이스** 순서로 짠다.
- **테스트 계층**: 단위 / 통합(격리 fixture + 실제 빌드) / 브라우저(최종은 빌드 산출물 preview) / 실제 연동 / 배포 인수.
- 위험한 외부 연동은 앞쪽에 최소 실험으로 둔다. 실패하면 원인을 분류하고 대안을 먼저 제시한다.

## 3. 사이클

1. **Red**: 기대 동작을 테스트로 먼저 쓰고 실패를 확인한다. 설치 실패·서버 미실행은 Red가 아니다.
   사례가 여럿이면 한 사례씩. 설정 조사·외부 연결·문서 작업은 완료 기준으로 판정한다.
   내부 호출 순서가 아니라 사용자가 보는 결과와 데이터 계약을 검증한다.
2. **Green**: 통과시키는 최소 구현. 기존 테스트의 기대값을 고치거나 지우거나 skip해야 하면 판정 질문 ②다.
3. **Refactor**: 정리 후 해당 테스트와 영향받는 회귀 테스트를 다시 돌린다.
4. **자동 검사**: 변경 영향과 저장소 필수 게이트에 맞춰 수행한다. 요약 리포터로, 실패했을 때만 상세를 본다.
5. **등급 재확인**: 계획에 없던 ①②③이 생겼으면 결정으로 올린다. 실행 중에는 올리기만 한다(래칫).
   내리거나 확인 지점을 미루려면 사용자 허락이 필요하다.
6. **기록**: `node scripts/log-new.mjs "<ID>: <제목>" --gate 결정|확인|자동`, 사유와 근거 테스트를 채운다.
   INDEX 결론 한 줄에는 "무엇이 문제였고 어떻게 정했는지"를 쓴다. STATUS의 "지금"·"최근 3건"을 갱신한다.
7. **스테이징**: 이 작업의 파일만 `git add`한다.
8. **등급별 마무리**
   - 자동: 커밋하고, 진행 중에는 한 줄만 남기고 다음 단위로 간다.
   - 확인 지점: 커밋하고 확인 보고 후 **멈춘다.** 확인 전에는 다음 묶음으로 넘어가지 않는다.
   - 결정: 결정 보고 후 **멈춘다.** 판정 전에는 이 결정 위에 쌓지 않는다.
   - `pre-commit`이 보호 대상 변경으로 막으면 결정으로 올리고 결정 보고를 한다.
9. **예산**: 커밋 출력에 `[예산]` 줄이 있으면 6절대로 한다.

## 4. 보고

보고의 목적은 사용자가 방향을 판단하고 결정할 재료를 갖게 하는 것이다. 형식 상세, 예시, 보내기 전 점검은
`references/report-format.md`에 있다. 정지 보고를 쓰기 전에 그 파일을 연다.

- **읽는 사람**: 마지막 정지 보고 이후의 대화를 보지 않은 사용자. 도구 결과·파일 내용으로만 알게 된 사실은
  사용자가 모른다고 보고, 판정에 쓰이면 보고에 적는다. 보고 밖을 가리키는 말("그 문제", "기존 방식")을 쓰지 않는다.
- **두괄식**: 첫 블록 "결론"만 잘라 읽어도 끝난 일, 필요한 판정, 판정에 영향을 주는 전제를 안다.
  1~3개 bullet로 쓰고, 한 줄로 억지로 줄이지 않는다.
- **개조식** (한국어): 한 줄에 한 사실. 끝은 명사형(~함, ~됨, ~음, ~필요, ~예정, ~추정)으로 맺고
  "~합니다", "~입니다", "~다"로 끝내지 않는다. 어미만 바꾸고 주어·대상·수치·조건·시제는 지우지 않는다.
  판정 요청, 질문, 코드·명령·인용은 예외. 적용 범위: 보고, 진행 중 알림, STATUS.md, 로그.
  운영가이드와 최종 보고서 본문은 평서문으로 쓴다.
- **우선순위**: 판단 재료 > 짧음 > 중복 금지. 중복 금지는 같은 문장의 반복을 막는 규칙이지, 판정에 필요한 사실을 빼는 규칙이 아니다.
- **정지 보고 순서**: 결론 → 자동 진행 내역(ID, 결론 한 줄, 자동 사유, 커밋) → 계획 대비 위치 → 내가 이해한 전제
  → 판단 재료 또는 확인 방법 → 자동 검사 → 판정 후 → 판정 요청.
- **결정 보고**: 내가 이해한 전제(항목마다 확인됨/추정)는 반드시 쓴다. 쟁점마다 지금 정하는 이유, 선택(추천과 확신도),
  버린 대안과 이유, trade-off, 모르는 것, 잘못 정했을 때의 비용. 판정 요청: "'통과' 또는 '수정: [문제와 원하는 변경]'".
- **확인 보고**: 해볼 흐름을 "조작 → 기대 결과"로, 이번 묶음에서 바뀐 구조를 짧게. 전제가 바뀌었으면 전제도 쓴다.
- 자동 검사는 돌린 검사마다 통과·실패, 돌리지 않은 범위와 이유.
- 사용자에게 자동 검사 실행이나 `git diff` 확인을 시키지 않는다. 에이전트가 하고 결과만 보고한다.

## 5. 판정 후

- **결정 통과**: `node scripts/manual-review.mjs approve --for <ID>` → 커밋 → 작업 브랜치 push.
- **확인 통과**: 로그·STATUS 상태와 계획의 확인 지점 `결과`를 갱신하고 다음 묶음으로 간다.
- **수정**: 고치고 → 자동 검사 → 같은 결정·확인 지점을 다시 보고한다. 결과에 수정 건수를 남긴다.
- **main 병합**: 그 범위의 인수 조건 + build·preview 검증 후 PR을 열고, 병합은 사용자가 고른다.
- 금지: `--no-verify`, 훅 비활성화, 승인 파일 조작, 사용자 대신 '통과' 작성, 판정 전 approve,
  main 직접 push, 무응답·자동 테스트 성공·이전 판정을 새 결정이나 확인의 통과로 해석하기.
- push가 실패하면 로컬 커밋을 보존하고 원인을 기록한다. 성공 확인 전에 완료라고 쓰지 않는다.

## 6. 예산

판단은 단위 경계(커밋 직후)에서만 한다. 커밋 출력의 `[예산]` 줄이 판단 재료다.

- `작은 단위만 진행`: 남은 행 중 작은 것만 하고, 큰 행은 다음 세션으로 넘긴다.
- `정지`: STATUS.md의 "지금"·"다음 할 일"·"확인 대기"를 인계용으로 갱신하고 커밋한 뒤 멈춘다. 새 세션을 권한다.
- 끊는 것도 묻지 않고 알린다. 수치와 이유만 쓴다. 줄이 없으면 계속한다.
- 수치 공급(어댑터)과 임계치 설정은 `references/approval-gate.md`에 있다.

## 7. 판단 규칙

- **시각 결정**은 코드를 고치기 전에 2~8개 시안을 같은 조건에서 캡처해 고르게 한다. Skill 도구에
  `capture-compare`가 있으면 호출하고, 없으면 직접 캡처한다. 고른 안을 반영하는 작업도 사이클을 거친다.
- **추측하지 말고 잰다.** 성능·원인은 측정으로 확인하고, 측정 결과로 문제를 다시 정의한다.
- **선택지가 있는 결정**은 `docs/decision/`에 선택지·선택·근거·틀렸던 가정을 남긴다.
- **운영 보호는 구조로.** 테스트는 운영 데이터를 고정값으로 쓰지 않는다. 운영 쓰기는 명시적 opt-in일 때만.
- **실패는 숨기지 않는다.** 비밀값 생성 같은 중요한 단계는 실패하면 즉시 멈춘다.
- **규칙이 바뀌면** 테스트를 새 의도에 맞게 고치고 그 이유를 기록한다.
- **사용자에게 의미 있는 단위로 센다** (커밋 수가 아니라 바뀐 항목 수).
- **브랜치**: 개발은 `feat/<기능>`에서. 작업 브랜치 push ≠ 배포. 공개할 방법이 없는 반쪽 기능은 병합하지 않는다.

## 8. 마감

2절에서 합의한 산출물만 작성한다. 운영 기능 전체 개발이면 `docs/guide/<기능>-운영가이드.md`
(작업 흐름, 동작 원리, 시행착오와 선택, 한계, 설정 위치)와 최종 보고서(실제로 동작하는 것과 근거,
제약과 미해결 항목, 후속 과제 표)를 쓴다. 운영 배포까지 합의했다면 운영 사이트에서 흐름을 확인한 뒤 완료로 표시한다.

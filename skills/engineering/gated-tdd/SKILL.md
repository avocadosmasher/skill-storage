# 게이트 TDD 개발 절차

작은 단위를 테스트 먼저 만들고 단위마다 커밋한다. 사용자는 두 가지만 판정한다.
AI가 대신 정할 수 없는 **결정**, 그리고 직접 해볼 수 있는 기능 묶음의 **확인**이다.
나머지는 기록과 알림을 남기고 묻지 않고 진행한다. main 병합은 사용자가 PR로 고른다.
사용자 대상 문서와 응답은 사용자의 언어로 쓴다. 보고는 4절의 두괄식·개조식 규칙을 따른다.

## 0. 세션 시작

1. `STATUS.md`만 읽는다. 없으면 6번에서 작업 유형을 고른 뒤 "1. 도입"부터 한다.
2. `node scripts/budget.mjs start`로 세션 시작을 기록한다. 스크립트가 아직 없으면 도입에서 복사한 직후에 한다.
   장치가 있는데 `git config core.hooksPath`가 `.githooks`가 아니면(새로 clone한 저장소) 먼저 설정하고 알린다.
3. STATUS의 "판정 대기"·"확인 대기"를 실제 사용자 판정 기록·커밋과 대조한다. 판정이 확인되면
   문서 갱신 지연으로 보고 다시 묻지 않는다. 확인되지 않은 **확인 대기가 있으면 그 확인부터 요청하고,
   확인 전에는 다음 묶음으로 넘어가지 않는다.** 현재 작업의 검토·수정 요청은 먼저 수행한다.
4. 과거 경위가 필요하면 `docs/log/INDEX.md`에서 한 줄을 고르고 그 항목 파일 하나만 연다.
5. 코드 탐색은 도구와 인덱스가 있으면 Graft를 먼저 쓴다(`graft ask "작업" --source`,
   `graft grep "식별자"`, `graft callers 식별자 --depth all`). 큰 변경 후 `graft build`.
6. **작업 유형**을 고른다. 고른 유형과 근거는 첫 보고의 "내가 이해한 전제"에 쓴다.
   신호가 겹쳐 모호하면 판정 질문 ①로 보고 사용자에게 묻는다.

   | 유형 | 신호 | 시작 |
   | --- | --- | --- |
   | 초기 개발 | 제품이 아직 없음 (빈 저장소, 또는 실행해 볼 제품이 없음) | `references/init-dev.md`: 제품 명세 → 골격 → 기능 개발 |
   | 기능 개발 | 제품이 있고, 기능을 더하거나 사용자가 보는 동작을 바꿈 | 2절: 요구 → 계획 → 3절 사이클 |
   | 유지보수 (버그 수정, 리팩터링, 의존성) | 기존 동작을 고치거나 보존함 | 기능 개발과 같음. 동작을 보존하는 작업(리팩터링, 의존성)은 요구를 생략함 |

## 1. 도입 (장치가 없는 저장소)

사용자가 도입이나 게이트 TDD 적용을 요청했으면 아래 파일 준비는 다시 묻지 않는다. 도입 커밋은 게이트 파일이
보호 대상이라 판정이 필요하므로, `.gated-tdd.json` 확정과 함께 결정 보고 한 번(판정 ID `도입`)으로 받는다.
기존 규칙·훅은 보존하고 통합한다. 도입은 `chore/gated-tdd` 브랜치에서 한다. 초기 개발이면 `references/init-dev.md`의 순서를 따른다.
도입이 통과해 커밋하면 기능 작업을 기다리지 않고 바로 push하고 PR을 열어, 사용자가 병합을 고르게 한다(원격이 없으면 직접 병합을 고르게 한다).
도입은 작고 기능과 무관해서, 먼저 main에 들어가야 이후 기능 브랜치가 main에서 시작한다.

- `AGENTS.md`: 절차를 옮겨 적지 않는다. 채택 선언과 이 저장소의 값만 둔다. 이 선언이 있어야 다음 세션의
  에이전트가 스킬을 불러오고, 스킬과 함께 `references/`도 따라온다.
  ```markdown
  ## 개발 절차
  이 저장소는 gated-tdd 절차를 채택했다. 기능 개발, 버그 수정, 리팩터링 전에 Skill 도구로 `gated-tdd`를 불러 따른다.
  - 테스트: `<명령>` / 빌드: `<명령>`
  - 보호 대상: `.gated-tdd.json`
  - 상태와 문서: `STATUS.md`, `docs/`
  - 새로 clone하면: `git config core.hooksPath .githooks` (훅은 clone마다 켜야 한다)
  ```
- `CLAUDE.md`: 첫 줄 "세션을 시작하면 STATUS.md부터 읽는다.", 둘째 줄 `@AGENTS.md`.
- `STATUS.md`: `최종 갱신: YYYY-MM-DD`, 지금(작업 브랜치·마지막 커밋·판정 대기·확인 대기·다음 할 일),
  자동 진행 내역(마지막 정지 보고 이후), 최근 3건(최신이 위), 문서 위치 표.
- `docs/spec/` 제품 명세·기능 요구 · `docs/behavior/` 영역별 동작 명세 · `docs/plan/` 계획 · `docs/decision/` 결정 근거 ·
  `docs/log/` 작업 이력(항목당 1파일) · `docs/guide/` 운영법 · `docs/archive/` 끝난 단계. 폴더는 첫 파일을 쓸 때 만든다.
  `log-new.mjs`는 `STATUS.md`와 `docs/log/INDEX.md`(아래 표 머리와 `| --- |` 구분선)가 있어야 돌아가므로, 도입의 첫 기록 전에 둘을 먼저 쓴다.
  `docs/log/INDEX.md`는 표 `| 항목 | 날짜 | 결론 | 상태 | 파일 |`, 최신이 위.
- 스크립트와 훅: 이 스킬의 `assets/`에서 복사하고 `references/approval-gate.md`대로 설치·검증한다.
- `.gated-tdd.json`: 보호 경로·테스트 경로·보호 브랜치·예산 임계치를 이 저장소에 맞춰 제안하고 사용자가 확정한다.
  초기 개발이면 기본값 내용(`references/approval-gate.md`의 예시)으로 만들고 골격 계획에서 맞춘다.
- 테스트 도구는 고의 실패 시 0이 아닌 코드로 끝나는지 확인한다. 테스트 도구가 아직 없으면(초기 개발) 골격에서 한다.
- **배포되는 코드는 PR에서 테스트를 통과한 코드여야 한다.** 방법은 기존 배포 방식에 맞추고 계획이나 도입 보고에 쓴다.
  - 배포를 CI(GitHub Actions 등)가 하면 재사용 워크플로 하나를 PR과 배포가 같이 쓴다.
  - 플랫폼이 main을 직접 가져가 배포하면(Vercel, Netlify 등) 배포 방식은 바꾸지 않는다. 개발 변경은 PR로만 main에
    들어가므로, PR 보고에 CI 결과를 붙이고 사용자가 CI 통과를 보고 병합하는 것으로 보장한다.
  - 비용이 드는 저장소 설정을 기본으로 권하지 않는다. GitHub 브랜치 보호처럼 요금제에 따라 유료인 설정은 무료로 쓸 수 있을 때
    (공개 저장소 등)만 선택 사항으로 안내한다. `directPush`와 함께 켜면 GitHub가 main 직접 push를 거절하므로, 사용자 본인을
    우회 허용에 넣어야 한다는 점을 같이 쓴다.
  - 플랫폼이 PR마다 미리보기 주소를 만들면 확인 지점의 해볼 곳으로 쓴다.
- **main으로 바로 올리던 경로**가 있는지 본다(블로그 글처럼 개발 절차 밖의 콘텐츠). 있으면 도입 후 막히는 일을 도입 보고에
  쓰고, `.gated-tdd.json`의 `directPush`로 예외를 둘지 같은 보고에서 묻는다(`references/approval-gate.md`).
- Claude Code면 예산 어댑터 설치 안내(`references/approval-gate.md`)를 도입 결정 보고에 한 번 넣는다.

## 2. 요구와 계획: 구현 전에 합의

1. **요구**: `references/requirements.md`대로 기능 요구 `docs/spec/<기능 ID>.md`를 쓰고, 요구 보고
   (판정 ID `SPEC-<기능 ID>`)를 한 뒤 멈춘다. 제품 명세가 있으면 기능 지도에서 그 기능의 자리를 확인하고,
   범위나 기능 지도가 바뀌면 같은 보고에 넣는다(판정 질문 ②).
2. **계획**: 요구가 통과하면 `docs/plan/<기능 ID>-개발계획.md`를 쓰고, 게이트·확인 지점·결정 목록을
   계획 보고 한 번(판정 ID `PLAN-<기능 ID>`)으로 확정받은 뒤 사이클을 시작한다.

계획에 담는 것:

- **끝의 정의**와 **제외 범위**: 기능 요구의 시나리오와 "하지 않을 것"에서 가져온다. 합의한 핵심을 빼고 완료로 치지 않는다.
- **작업 표**: `| ID | 작업 | 선행 | 먼저 작성할 실패 테스트 / 완료 기준 | 게이트 | 보호 대상 변경 |`. 실패 테스트는 기능 요구의 시나리오에서 나온다.
  한 행은 혼자서 통과/실패를 판단할 수 있는 크기. ID는 영역 알파벳 + 번호(A01, B02 …).
- **게이트**: 행마다 AI가 제안하고 사용자가 확정한다.

  | 판정 질문 | 예이면 |
  | --- | --- |
  | ① 선택: 합리적인 안이 둘 이상이고 정답이 사용자의 의도·우선순위·제약에 달렸나? | 결정 |
  | ② 합의 변경: 계획·스펙·테스트 기대값·범위를 바꾸거나 모호한 요구를 해석하나? | 결정 |
  | ③ 되돌리기 어려움: 스키마·데이터 삭제, 공개 API 계약, 인증·권한, 개인정보, 비밀값, 비용, 배포? | 결정 |
  | ④ 사람만 확인 가능: 화면·문구·사용감, 실제 계정·기기·외부 연동? | 확인 지점에 묶음 |
  | 전부 아니오, 완료 기준을 자동 검사로 증명 | 자동 |

  결정 목록과 보호 대상 변경 칸에서 미리 판정받아 ①②③이 모두 풀리는 행은 자동으로 제안한다.
  사용자가 실제 내용을 직접 보고 싶은 행은 결정으로 확정하면 된다.
- **결정 목록**: 계획에서 미리 정할 수 있는 결정을 모아 한 번에 받는다. 지식·기능·보안·비용 네 갈래를 훑어
  결정이 숨은 곳을 찾는다. Skill 도구에 `grill-me-plus`가 있으면 호출해 결정을 캐묻는다.
- **보호 대상 변경**: 그 행이 건드릴 보호 대상(`references/approval-gate.md`의 "무엇을 막나")을 무엇을 어떻게
  바꾸는지까지 적고, 근거(결정 목록 항목, 기능 요구의 바뀌는 동작)를 괄호로 단다. 예: `package.json`에 `pg` 추가 (D1),
  기존 테스트 "댓글 버튼이 보인다"의 기대값을 "안 보인다"로 (요구의 바뀌는 동작). 계획이 통과하면 이 칸까지 판정받은 것이다.
  보호 대상을 건드리지 않는 행은 비운다.
- **확인 지점**: `| 확인 지점 | 포함 행 | 해볼 흐름 | 결과 |` 표로 둔다.
  1. 사용자 흐름 하나를 처음부터 끝까지 직접 해볼 수 있게 된 행에 둔다. 해볼 것이 없으면 두지 않는다.
  2. 뒤의 여러 행이 기대는 토대가 해볼 수 있는 상태가 되면 그 직후로 앞당긴다.
  3. 모호하거나 처음 다루는 영역은 짧게, 스펙이 분명하면 길게 잡는다.
  계획은 기능 하나를 데이터부터 화면까지 관통하는 **수직 슬라이스** 순서로 짠다.
- **테스트 계층**: 단위 / 통합(격리 fixture + 실제 빌드) / 브라우저(최종은 빌드 산출물 preview) / 실제 연동 / 배포 인수.
- 위험한 외부 연동은 앞쪽에 최소 실험으로 둔다. 실패하면 원인을 분류하고 대안을 먼저 제시한다.

## 3. 사이클

1. **Red**: 기대 동작을 테스트로 먼저 쓰고 실패를 확인한다. 설치 실패·서버 미실행은 Red가 아니다.
   사례가 여럿이면 한 사례씩. 설정 조사·외부 연결·문서 작업은 완료 기준으로 판정한다.
   내부 호출 순서가 아니라 사용자가 보는 결과와 데이터 계약을 검증한다.
2. **Green**: 통과시키는 최소 구현. 기존 테스트의 기대값을 고치거나 지우거나 skip해야 하면 판정 질문 ②다.
3. **Refactor**: 정리 후 해당 테스트와 영향받는 회귀 테스트를 다시 돌린다.
4. **자동 검사**: 변경 영향과 저장소 필수 게이트에 맞춰 수행한다. 요약 리포터로, 실패했을 때만 상세를 본다.
5. **등급 재확인**: 계획에 없던 ①②③이 생겼으면 결정으로 올린다. 실행 중에는 올리기만 한다(래칫).
   내리거나 확인 지점을 미루려면 사용자 허락이 필요하다.
6. **기록**: `node scripts/log-new.mjs "<ID>: <제목>" --gate 결정|확인|자동`, 사유와 근거 테스트를 채운다.
   INDEX 결론 한 줄에는 "무엇이 문제였고 어떻게 정했는지"를 쓴다. STATUS의 "지금"·"최근 3건"을 갱신한다.
   보호 대상 변경 칸이 있는 행은 사유에 `계획 판정: <근거>`를 이때 쓴다.
7. **스테이징**: 이 작업의 파일만 `git add`한다. 보호 대상 변경 칸이 있는 행은 `node scripts/manual-review.mjs guarded`로
   걸리는 목록을 미리 본다.
8. **등급별 마무리**
   - 자동: 커밋하고, 진행 중에는 한 줄만 남기고 다음 단위로 간다.
   - 확인 지점: 커밋하고 확인 보고 후 **멈춘다.** 확인 전에는 다음 묶음으로 넘어가지 않는다.
   - 결정: 결정 보고 후 **멈춘다.** 판정 전에는 이 결정 위에 쌓지 않는다.
   - 보호 대상 변경이 있으면(`guarded` 목록, 또는 `pre-commit`이 막음) 그 행의 보호 대상 변경 칸과 스테이징된 변경을 대조한다.
     칸 범위 안이면 계획 판정으로 `approve --for <행 ID>` → 커밋한다. 승인은 그 순간 스테이징된 파일 묶음에 붙으므로,
     로그를 포함한 모든 파일을 먼저 쓰고 스테이징한 뒤 approve하고, approve와 커밋 사이에는 아무 파일도 고치지 않는다.
     칸에 없거나 범위를 넘으면(적지 않은 패키지·테이블·열·테스트) 결정으로 올리고 결정 보고를 한다. 애매하면 넘은 것으로 본다.
9. **예산**: 커밋 출력에 `[예산]` 줄이 있으면 6절대로 한다.

## 4. 보고

보고의 목적은 사용자가 방향을 판단하고 결정할 재료를 갖게 하는 것이다. 형식 상세, 예시, 보내기 전 점검은
`references/report-format.md`에 있다. 정지 보고를 쓰기 전에 그 파일을 연다.

- **읽는 사람**: 마지막 정지 보고 이후의 대화를 보지 않은 사용자. 도구 결과·파일 내용으로만 알게 된 사실은
  사용자가 모른다고 보고, 판정에 쓰이면 보고에 적는다. 보고 밖을 가리키는 말("그 문제", "기존 방식")을 쓰지 않는다.
- **두괄식**: 첫 블록 "결론"만 잘라 읽어도 끝난 일, 필요한 판정, 판정에 영향을 주는 전제를 안다.
  1~3개 bullet로 쓰고, 한 줄로 억지로 줄이지 않는다.
- **개조식** (한국어): 한 줄에 한 사실. 끝은 명사형(~함, ~됨, ~음, ~필요, ~예정, ~추정)으로 맺고
  "~합니다", "~입니다", "~다"로 끝내지 않는다. 어미만 바꾸고 주어·대상·수치·조건·시제는 지우지 않는다.
  판정 요청, 질문, 코드·명령·인용은 예외. 적용 범위: 보고, 진행 중 알림, STATUS.md, 로그.
  운영가이드와 최종 보고서 본문은 평서문으로 쓴다.
- **우선순위**: 판단 재료 > 짧음 > 중복 금지. 중복 금지는 같은 문장의 반복을 막는 규칙이지, 판정에 필요한 사실을 빼는 규칙이 아니다.
- **판정이 아닌 질문**(요구 대화, 원격 연결 등)으로 멈출 때도 STATUS.md가 있으면 "다음 할 일"에 `사용자 답 대기: <질문 요약>`을 쓴다.
  세션이 끊겨도 다음 세션이 그 질문부터 이어 간다.
- **정지 보고 순서**: 결론 → 자동 진행 내역(ID, 결론 한 줄, 자동 사유, 커밋) → 계획 대비 위치 → 내가 이해한 전제
  → 판단 재료 또는 확인 방법 → 자동 검사 → 판정 후 → 판정 요청.
- **결정 보고**: 내가 이해한 전제(항목마다 확인됨/추정)는 반드시 쓴다. 쟁점마다 지금 정하는 이유, 선택(추천과 확신도),
  버린 대안과 이유, trade-off, 모르는 것, 잘못 정했을 때의 비용. 판정 요청: "'통과' 또는 '수정: [문제와 원하는 변경]'".
- **확인 보고**: 해볼 흐름을 "조작 → 기대 결과"로, 이번 묶음에서 바뀐 구조를 짧게. 전제가 바뀌었으면 전제도 쓴다.
- 자동 검사는 돌린 검사마다 통과·실패, 돌리지 않은 범위와 이유.
- 사용자에게 자동 검사 실행이나 `git diff` 확인을 시키지 않는다. 에이전트가 하고 결과만 보고한다.

## 5. 판정 후

- **결정 통과**: 이 결정의 파일만 `git add` → `node scripts/manual-review.mjs approve --for <ID>` → 커밋 → 작업 브랜치 push.
  결정은 보고 전에 커밋하지 않는다. 행이 없는 결정의 ID는 도입 `도입`, 제품 명세 `SPEC-product`, 기능 요구 `SPEC-<기능 ID>`,
  계획 `PLAN-<기능 ID>`다. 계획 판정은 보호 대상 변경 칸의 근거가 되므로 다른 결정처럼 기록하고 커밋한다.
  행이 없는 결정도 보고 전에 로그 항목과 STATUS.md "판정 대기"를 쓰고, 통과하면 결정 문서와 함께 커밋한다.
- **확인 통과**: 로그·STATUS 상태와 계획의 확인 지점 `결과`를 갱신하고 다음 묶음으로 간다.
- **기능 마감**: 기능의 마지막 확인 지점을 통과하면 `references/requirements.md`의 "동작 명세에 합치기"를 한다.
- **수정**: 고치고 → 자동 검사 → 같은 결정·확인 지점을 다시 보고한다. 결과에 수정 건수를 남긴다.
- **main 병합**: 그 범위의 인수 조건 + build·preview 검증 후 PR을 열고, 병합은 사용자가 고른다.
- 금지: `--no-verify`, 훅 비활성화, 승인 파일 조작, 사용자 대신 '통과' 작성, 판정 전 approve,
  main 직접 push(`directPush` 경로만 바꾸는 push는 예외), 무응답·자동 테스트 성공·이전 판정을 새 결정이나 확인의 통과로 해석하기
  (계획의 보호 대상 변경 칸 범위 안의 커밋만 예외).
- push가 실패하면 로컬 커밋을 보존하고 원인을 기록한다. 성공 확인 전에 완료라고 쓰지 않는다.

## 6. 예산

판단은 단위 경계(커밋 직후)에서만 한다. 커밋 출력의 `[예산]` 줄이 판단 재료다.

- `작은 단위만 진행`: 남은 행 중 작은 것만 하고, 큰 행은 다음 세션으로 넘긴다.
- `정지`: STATUS.md의 "지금"·"다음 할 일"·"확인 대기"를 인계용으로 갱신하고 커밋한 뒤 멈춘다. 새 세션을 권한다.
- 끊는 것도 묻지 않고 알린다. 수치와 이유만 쓴다. 줄이 없으면 계속한다.
- 수치 공급(어댑터)과 임계치 설정은 `references/approval-gate.md`에 있다.

## 7. 판단 규칙

- **시각 결정**은 코드를 고치기 전에 2~8개 시안을 같은 조건에서 캡처해 고르게 한다. Skill 도구에
  `capture-compare`가 있으면 호출하고, 없으면 직접 캡처한다. 고른 안을 반영하는 작업도 사이클을 거친다.
- **버리는 실험(spike)**은 사용자 동의를 받고 `references/requirements.md`의 spike 규칙대로 한다. spike 코드는 병합하지 않는다.
- **추측하지 말고 잰다.** 성능·원인은 측정으로 확인하고, 측정 결과로 문제를 다시 정의한다.
- **선택지가 있는 결정**은 `docs/decision/`에 선택지·선택·근거·틀렸던 가정을 남긴다.
- **운영 보호는 구조로.** 테스트는 운영 데이터를 고정값으로 쓰지 않는다. 운영 쓰기는 명시적 opt-in일 때만.
- **실패는 숨기지 않는다.** 비밀값 생성 같은 중요한 단계는 실패하면 즉시 멈춘다.
- **규칙이 바뀌면** 테스트를 새 의도에 맞게 고치고 그 이유를 기록한다.
- **사용자에게 의미 있는 단위로 센다** (커밋 수가 아니라 바뀐 항목 수).
- **브랜치**: 도입은 `chore/gated-tdd`, 기능은 요구부터 `feat/<기능 ID>`에서 한다. 제품 명세는 함께 보고하는 기능의 브랜치에 쓴다. 선행 기능(도입 포함)이 아직 main에
  병합되지 않았으면 그 브랜치에서 분기하고 보고의 전제에 쓴다. 작업 브랜치 push ≠ 배포. 공개할 방법이 없는 반쪽 기능은 병합하지 않는다.

## 8. 마감

2절에서 합의한 산출물만 작성한다. 운영 기능 전체 개발이면 `docs/guide/<기능>-운영가이드.md`
(작업 흐름, 동작 원리, 시행착오와 선택, 한계, 설정 위치)와 최종 보고서(실제로 동작하는 것과 근거,
제약과 미해결 항목, 후속 과제 표)를 쓴다. 운영 배포까지 합의했다면 운영 사이트에서 흐름을 확인한 뒤 완료로 표시한다.

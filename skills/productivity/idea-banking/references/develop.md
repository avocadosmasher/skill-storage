# 아이디어 발전과 정리

## 구체화

대상 카드와 관련 기록을 읽고 이번 대화의 목적을 확인한다. 사용자가 시간을 정했다면 그에 맞춰 범위를 줄인다. 정하지 않았다면 짧은 1차 정리를 제공하고, 판단을 바꾸는 정보가 부족할 때만 질문한다.

처음부터 모든 항목을 채우려 하지 말고 필요한 내용을 선택한다.

- **해결할 문제**: 어떤 상황에서 누가 무엇 때문에 불편한가?
- **기대 결과**: 원하는 변화나 결과물은 무엇인가?
- **작은 첫 버전**: 가장 중요한 행동 하나를 가능하게 만드는 범위는?
- **필요한 전제**: 데이터, 권한, 기술, 시간 가운데 무엇이 준비되어야 하는가?
- **미확인 사항**: 실제로 알아보기 전에는 결론 내릴 수 없는 것은?
- **첫 검증 행동**: 예시 한 건, 수동 시뮬레이션, 작은 프로토타입 등으로 무엇을 확인할 수 있는가?

사용자가 말한 사실, AI 제안, 검증되지 않은 가정을 구별한다. 대상 사용자나 사업 가능성을 임의로 확정하지 않는다. “기술적으로 가능해 보임”과 “현재 조건에서 작동함을 확인함”을 구별한다. 학습 아이디어는 문제 해결 제품 틀을 강제하지 않고, 배우려는 이유·최소 실습·성취 확인 방식으로 정리한다.

특정 API 지원, 제품 기능, 최신 비용, 정책 등 외부 사실이 판단에 필요하면 실제 자료를 확인한다. 확인한 출처의 URL과 확인 날짜를 기록한다. 검증하지 못한 전제는 미확인으로 남긴다. 단순 저장 시에는 웹 조사를 하지 않는다.

사용자가 아이디어 발전을 요청했다면 발전 내용을 카드의 추가 메모로 저장한다. 가벼운 목록 추천만 했을 때에는 후보 전체의 상태를 바꾸지 않는다. 후속 작업을 시작할 준비가 되었는지는 사용자의 결정을 반영한다.

## 비교와 연결

두 기록의 원문을 읽어 같은 상황·대상·결과를 다루는지 비교한다. 예를 들어 회의록에서 할 일을 뽑는 Agent와 회의 일정을 잡는 Agent는 기술이 같아도 목표가 다르다. 학습과 만들기가 같은 주제를 공유할 때는 학습이 구현을 돕는 관계로 연결할 수 있다.

관련성을 저장할 때 `add_related_ids`를 사용한다. 양방향 연결이 필요하면 두 카드를 각각 읽고 수정한다. 하나만 성공하면 성공 범위를 정확히 알린다.

## 사용자가 합치기를 요청했을 때

1. 대상들이 명확하면 비교한 뒤 대표 기록을 정한다. 대표 선택이 중요하고 의도가 불명확할 때만 묻는다.
2. 대표 기록에 각 원본 ID, 원본의 고유한 내용, 통합 설명을 메모로 추가한다. 양쪽을 관련 ID로 연결한다.
3. 대표 기록의 저장이 성공한 뒤 나머지 기록을 `archived`로 바꾸고 대표 ID를 메모에 남긴다.
4. 원문과 원본 파일은 유지한다. 이후 검색에서 보관된 원본을 포함할 수 있다.

## 다시 할 일을 고를 때

사용자의 시간과 관심이 있으면 그 조건을 우선한다. 조건이 없다면 바로 시도하기 쉬운 후보와 장기적으로 발전시킬 후보를 짧게 설명하고 첫 행동을 제안한다. 근거 없이 난이도·비용·가치를 점수화하지 않는다.

첫 행동은 완료 여부를 알 수 있는 형태로 쓴다. “공부하기”보다 “예제 입력 하나를 정하고 원하는 출력과 비교하기”가 다음 대화를 이어 가기 쉽다.

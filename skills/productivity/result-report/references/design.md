# result-report 디자인 명세 v1

어느 모델이 써도 같은 모양의 보고서가 나오도록, 보고서에 쓸 수 있는 것과 쓰지 않는 것을 정한다. 보고서는 `assets/result-report.html`을 복사해 `{{ }}` 자리만 채워 만든다. 완성 모습은 `references/example.html`을 기준으로 삼는다.

## 1. 고정하는 것

- `<style>` 블록은 한 글자도 바꾸지 않는다. 색 · 크기 · 간격을 바꾸고 싶어도 고치지 않는다.
- 새 CSS 클래스를 만들지 않는다. 아래 "쓸 수 있는 부품"의 클래스만 쓴다.
- `style="..."` 인라인 스타일을 쓰지 않는다.
- `<script>`, 외부 글꼴 · CSS(`<link>`, `@import`), 이미지, 이모지, 아이콘 글꼴을 쓰지 않는다.
- 다크 모드, 애니메이션, 접기 · 펼치기, 탭을 넣지 않는다.
- 절 번호와 제목은 틀 그대로 둔다: `1. 무엇을 만들었나`, `2. 결과`, `3. 주요 결정`, `4. 검증 중 발견한 문제`, `5. 남은 과제`. 1의 소절도 `1.1 만드는 제품`, `1.2 전체 워크플로와 이번 작업의 위치`, `1.3 만든 묶음` 그대로다.

## 3. 쓸 수 있는 부품

### 3.1 머리

```html
<h1>{제목}</h1>
<div class="meta">{제품} · {담당} · {기간} · {PR · 배포 상태}</div>
```

- 제목: "{N주차 · 기능 이름} 결과 보고서" 꼴, 25자 안
- 메타: 가운뎃점 ` · `으로 4칸. 칸마다 20자 안

### 3.2 요약 상자

```html
<div class="summary">
  {한 문단}
  <ul><li>{핵심}</li><li>{핵심}</li><li>{핵심}</li></ul>
</div>
```

- 문단: 2~3문장. 무엇을 마쳤고 어떻게 판단했는지
- 핵심: 정확히 3줄. 한 줄 80자 안. "무엇을 → 왜 바꿨나" 꼴

### 3.3 흐름 그림 (`.wf`)

```html
<div class="wf">
  <div class="legend2">
    <span><span class="sw b-mine"></span>이번 작업({나})</span>
    ...쓰는 색만...
  </div>
  <div class="layer">
    <div class="lt">{층 이름} <span>{층 설명}</span></div>
    <div class="row">
      <div class="box b-mine"><b>{칸 이름}</b><small>{설명}</small><span class="fn">{코드 이름}</span></div>
    </div>
  </div>
  <div class="down">▼ {다음 층으로 가는 이유}</div>
  ...
</div>
```

- 층: 3~5개. 위에서 아래로 사용자 쪽 → 흐름 → 실행 → 도구 · 연동 → 저장 · 외부
- 한 줄(`.row`)에 칸 2~4개. 넘으면 줄을 하나 더 둔다
- 순서가 있는 흐름은 `<div class="row steps">`에 칸과 `<div class="arrow">→</div>`를 번갈아 둔다. 한 줄에 칸 4개까지, 칸 이름 앞에 ①②③ 번호
- 칸 이름 14자 안, `small` 설명 35자 안, `.fn` 코드 이름 하나(길면 대표 하나)
- `b-both` 칸에는 `<span class="who">{누가 무엇을}</span>`을 `small` 다음에 한 줄
- 층 사이 `.down`은 "▼ " 다음에 15자 안
- 층 안 맨 아래 보충 한 줄이 필요하면 `<div class="loop">{설명}</div>` (예: 단계마다 저장)
- 범례에는 그림에 실제로 쓴 색만 둔다. 혼자 하는 프로젝트면 `b-peer` · `b-both`를 쓰지 않는다
- 그림 위 문단에 "파란 칸이 이번 작업, ..." 식으로 색의 뜻을 한 문장으로 쓴다

### 3.4 기능 묶음 (`.feature`)

```html
<div class="feature">
<p><b>① {묶음 이름} ({번호가 있으면})</b></p>
<table>
  <tr><td class="k">역할</td><td>{...}</td></tr>
  <tr><td class="k">동작</td><td>{...}</td></tr>
  <tr><td class="k">특징</td><td><ul><li>{...}</li></ul></td></tr>
  <tr><td class="k">구현</td><td><div class="impl">
    <div class="grp">{종류 이름}</div>
    <div class="it"><span class="chip c-fn">{코드 이름}</span><span class="what">{하는 일}</span></div>
  </div></td></tr>
</table>
</div>
```

- 줄 이름은 역할 · 동작 · 특징 · 구현 네 개, 이 순서
- 역할: 1~2문장. 제품에서 맡는 일
- 동작: 2~3문장. 사용자나 모델이 무엇을 하면 어떻게 되나
- 특징: 2~5개 항목. 항목마다 "규칙 + 이유" 한두 문장
- 구현: 아래 3.5
- 1.3 맨 위에 `<p class="note">` 한 줄과 `.chip-legend` 범례를 한 번 둔다. 범례에는 실제로 쓴 종류만

### 3.5 구현 칩

- 한 줄에 칩 하나 + 설명 하나(`.it`). 두 열로 놓지 않는다
- 같은 종류끼리 모으고, 순서는 `c-entry` → `c-config` → `c-flow` → `c-tool` → `c-fn`
- 종류가 바뀌는 곳에 `.grp` 한 줄(종류 이름)
- 칩 글자는 코드에 있는 이름 그대로. 괄호 · 인자 목록을 붙이지 않는다(`save_session`, `save_session()` 아님). 명령은 공백 그대로(`app create`)
- 설명(`.what`)은 30자 안, 명사형으로 끝냄("지원처 만들기", "보관함과 다시 대조")
- 묶음 하나에 칩 3~10개. 더 많으면 사용자가 알아야 할 것만 남긴다
- 종류 이름은 프로젝트에 맞게 정하고(SKILL.md 표), 보고서 안에서는 하나로 통일한다

### 3.6 표

- 2. 결과: `<table class="result">`, 머리 `기능 · 한 일 · 확인한 것`. 기능 칸 아래 번호는 `<br><span class="note">{번호}</span>`
- 3. 주요 결정: 결론 칸에는 고른 안과 한계를 쓴다. 다시 볼 조건 · 한계는 기록에 있거나 사실에서 바로 따라 나오는 것만 쓰고, 없으면 쓰지 않는다. 결정마다 `<h3>3.N {질문 꼴 제목}</h3>` + 줄 이름 `문제 · 검토한 안 · 근거 · 결론`(`td.k`) 표. 결정 3~6개. 작은 결정 여럿은 마지막에 `<h3>3.N 그 밖의 결정</h3>` 한 표(머리 `항목 · 결론과 이유`)로 묶는다
- 5. 남은 과제: `<table class="todo">`, 머리 `과제 · 담당 · 시점`. 과제 칸은 `<b>{과제}</b><p>{쉬운 설명 2~3문장}</p>`

### 3.7 그 밖

- 4. 검증 중 발견한 문제: `<ul>`의 `<li><b>{문제 이름}</b>: {무엇이 틀렸고 어떻게 바로잡았나}</li>`. 없으면 "이번에는 없음." 한 줄
- 보충 설명은 `<p class="note">`
- 코드 이름 · 경로 · 명령은 본문에서 `<code>`로 감싼다. 본문에서는 함수 이름을 주어로 쓰지 않는다

## 4. 글

- 문장 끝은 명사형(~함, ~음, ~임, ~됨). "~다", "~요"로 끝내지 않는다. 표의 짧은 항목은 명사로 끝나도 된다
- 한 문장에 한 사실. 한 문장 80자 안을 권장
- 용어는 처음 나올 때 쉬운 말로 풀어 쓴다. 작업 중에 만든 줄임말 · 번호(A3, F-18 등)는 본문에서 혼자 쓰지 않고 설명과 함께 쓴다
- 테스트 개수는 2. 결과 표에도 넣지 않는다. 필요하면 `<p class="note">` 한 줄
- 숫자는 기록에서 확인한 것만. 단위를 붙인다(2ms, 75KB, 40회)
- em dash(U+2014), en dash(U+2013)를 쓰지 않는다. 범위는 `~`, 나열은 ` · `

## 5. 모바일

CSS에 이미 들어 있다. 640px 이하에서 기능 표의 줄 이름이 내용 위로 쌓이고, 그림 칸이 세로로 쌓인다. 이 동작을 위해 기능 표는 반드시 `.feature` 안에 둔다.

## 6. 검사

다 쓰면 `node scripts/check-report.mjs <보고서 경로>`를 실행한다. 실패 항목이 하나라도 있으면 고치고 다시 실행한다. 경고는 읽고 이유가 있으면 둔다.

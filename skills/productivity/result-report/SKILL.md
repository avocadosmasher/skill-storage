# result-report

작업이 끝난 뒤 그 결과를 읽는 사람(제품 방향과 결과물을 책임지는 사람, 팀원, 나중의 나)이 코드를 열지 않고도 "무엇을 만들었고, 왜 그렇게 정했고, 무엇이 남았는지"를 알 수 있는 HTML 보고서 한 장을 만든다. 틀은 `assets/result-report.html`이다.

## 원칙

- **깔끔한 문서체.** 한 열, 흰 바탕, 표와 짧은 문단. 화려한 카드 · 대시보드 · 큰 숫자 타일을 쓰지 않는다. "보기 좋게"는 화려하게가 아니라 읽기 쉽게라는 뜻이다.
- **맥락 먼저.** 기능 번호나 함수 이름부터 말하지 않는다. 그것이 무엇이고 제품에서 어떤 역할인지 한두 문장으로 먼저 쓴다.
- **핵심 로직에 집중.** 무엇을 어떤 규칙으로 판단 · 처리하는지가 중심이다. "테스트 N개 통과" 같은 숫자는 눈에 띄지 않게 한 줄로만 둔다. 확인 근거는 "무엇을 · 어떻게 · 결과"로 쓴다.
- **쉬운 말.** 내부 용어나 작업 중에 만든 줄임말은 피하거나 처음 나올 때 풀어 쓴다.
- **함수 이름은 첨부.** 함수 이름을 설명의 주어로 쓰지 않는다. 기능을 쉬운 말로 설명하고, 맡은 코드는 표의 "구현" 줄에 칩으로 붙인다.
- **문장 끝은 명사형.** ~함, ~음, ~임, ~됨으로 맺는다. 사용자가 다른 문체를 정했으면 그것을 따른다.
- **지어내지 않는다.** 수치 · 결정 이유 · 날짜는 저장소 · 기록에서 확인한 것만 쓴다. 확인하지 못한 것은 "확인 안 됨"으로 둔다.

## 절차

### 1. 범위와 독자 확인

다음이 대화에 없으면 한 번에 묻는다. 기록에서 알 수 있는 것은 묻지 않는다.

- 보고 범위: 기간, 브랜치 · PR, 기능 묶음
- 나와 동료의 구분: 그림에서 "이번 작업(나)"와 "동료"를 가르는 기준. 혼자 하는 프로젝트면 동료 색을 쓰지 않는다
- 저장 위치: 사용자가 정한 곳. 정하지 않았으면 저장소에 커밋되지 않는 개인 폴더를 제안한다
- 문체: 기본은 명사형 어미

### 2. 재료 모으기

- 저장소의 README · 문서 · 주차 기록, 범위 안의 커밋과 PR 본문 · 리뷰
- 결정 기록(ADR, 설계 노트, 결정 문서): 선택지 · 근거 · 결론
- 실측 · 확인 기록: 무엇을 어떻게 재서 무엇이 나왔는지
- 남은 일: 열린 PR, 인수인계 문서, TODO
- 코드에서 기능마다 맡은 함수 · 설정 · 명령의 이름. 이름은 코드에서 직접 확인한다

### 3. 틀을 복사해 채우기

`assets/result-report.html`을 저장 위치로 복사하고 `{{ }}` 자리를 채운다. 쓰지 않는 칸 · 절은 지운다.

| 절 | 쓰는 것 |
| --- | --- |
| 요약 상자 | 무엇을 마쳤고 어떻게 판단했는지 한 문단 + 핵심 세 줄(무엇을 왜 바꿨나) |
| 1.1 만드는 제품 | 제품이 무엇이고 누가 어떻게 쓰는지, 이번 작업과 직접 관련된 약속(어기면 어떤 일이 생기나) |
| 1.2 전체 흐름 그림 | 아래 "흐름 그림" |
| 1.3 만든 묶음 | 묶음마다 역할 · 동작 · 특징 · 구현. 특징은 핵심 규칙과 그 이유 |
| 2. 결과 | 기능 · 한 일 · 확인한 것(무엇을 어떻게 확인했고 결과는) |
| 3. 주요 결정 | 결정을 질문 형태 제목으로. 문제 · 검토한 안 · 근거(실측 · 자료) · 결론(고른 안, 한계, 다시 볼 조건) |
| 4. 검증 중 발견한 문제 | 무엇이 틀렸고 어떻게 바로잡았나 |
| 5. 남은 과제 | 과제마다 무엇이고 왜 남았는지 쉬운 말 두세 문장, 담당, 시점 |

### 4. 흐름 그림

시스템 전체를 위에서 아래로 층(사용자 → 흐름 → 실행 → 도구 · 연동 → 저장 · 외부)으로 나누고, 층마다 칸을 둔다. 칸 아래 작은 글씨로 그 칸의 코드 이름을 적는다. 순서가 있는 흐름은 `steps` 줄에 화살표로 잇는다.

칸 색은 누가 언제 만든 것인지를 뜻한다.

| 클래스 | 뜻 |
| --- | --- |
| `b-mine` | 이번 작업(나). 파랑 |
| `b-peer` | 이번 기간에 동료가 만든 것. 옅은 자주 |
| `b-both` | 함께 만든 것. 옅은 보라. 칸 안에 `.who`로 누가 무엇을 했는지 한 줄 |
| `b-past` | 이전에 이미 있던 것. 옅은 회색 |
| `b-next` | 아직 안 한 것. 흰색 점선 |

그림 위에 이 색의 뜻을 한 문장으로 쓰고, 범례를 둔다.

### 5. 구현 칩

1.3의 "구현" 줄에는 그 기능을 맡은 코드 이름을 칩으로 한 줄에 하나씩 둔다. 칩 오른쪽에 하는 일을 짧게 쓴다. 두 열로 나란히 놓지 않는다(설명이 길면 줄이 어긋난다).

칩 색은 코드의 종류다. 종류는 프로젝트에 맞게 고르고, 1.3 맨 위 범례에 종류마다 뜻을 한 줄로 쓴다. 같은 종류끼리 모으고 `.grp`로 묶음 이름을 단다.

| 클래스 | 일반 뜻 | 에이전트 프로젝트 예 | 웹 서비스 예 |
| --- | --- | --- | --- |
| `c-entry` | 사용자가 직접 부르는 진입점 | CLI 명령 | 화면 · API 경로 |
| `c-config` | 동작을 정하는 정의 · 설정 | 에이전트 정의 | 설정 · 스키마 |
| `c-flow` | 여러 단계를 이어 부르는 흐름 · 실행 | 실행 함수 | 서비스 · 유스케이스 |
| `c-tool` | 도구 · 외부 연동 | 모델이 부르는 도구 | 외부 API 클라이언트 |
| `c-fn` | 저장 · 읽기 · 판정 같은 처리 | 함수 | 함수 · 저장소 |

종류가 다섯보다 적으면 쓰지 않는 색은 범례에서도 뺀다.

### 6. 확인

- 브라우저로 열어 PC 폭(약 900px)과 모바일 폭(375px)을 캡처해 본다. 헤드리스 브라우저는 창을 아주 좁게 만들지 못하는 경우가 많으니, 모바일은 너비 375px `iframe`에 보고서를 넣은 페이지로 캡처한다.
- 모바일에서는 표 항목 이름이 내용 위로 쌓이고, 그림 칸이 세로로 쌓여야 한다(틀에 이미 들어 있음).
- 남은 `{{ }}` 자리, 확인하지 않은 수치, 내부 줄임말이 없는지 본다.

### 7. 알리기

저장 경로와, 보고서에서 사용자가 판단해야 할 것(남은 과제 · 결정)만 짧게 알린다. 보고서 내용을 대화에 다시 옮겨 적지 않는다.

## 하지 않는 것

- 기록에 없는 수치나 이유를 지어내지 않는다.
- 공개 저장소 · 공유 문서에 보고서를 커밋하거나 올리지 않는다. 저장 위치는 사용자가 정한다.
- 함수 이름 나열로 기능 설명을 대신하지 않는다.
- 사용자가 고친 형식은 그 보고서에만 반영하고 끝내지 않는다. 다음에도 쓸 규칙이면 이 스킬과 틀에 반영하자고 제안한다.

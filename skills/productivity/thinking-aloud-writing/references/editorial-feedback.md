# 수정 요청 분석과 저자 선호의 지속 반영

수정 요청은 현재 원고를 고칠 근거이자 다음 집필의 판단 자료다. 모든 교정을 공용 규칙으로 바꾸거나, 취향을 객관적인 정답으로 단정하지 마라. 분석 때문에 요청한 수정을 미루지도 마라.

## 수정 이유를 찾고 현재 원고에 반영하라

- 사용자의 요청·대체 문장과 수정 전 원고를 가능한 범위에서 보존하고 실제 차이를 확인하라. 원본이 없으면 확인 가능한 요청만 분석하고 비교를 수행했다고 말하지 마라. 수정본 대조의 세부 기준은 [composition.md](composition.md)의 사용자 수정본 절을 따른다.
- 사용자가 밝힌 이유를 우선하라. 이유가 없으면 변화에서 드러난 의도를 잠정적으로 해석하되 사용자의 확정된 취향으로 기록하지 마라. 집필 방향이 크게 갈리는 경우에만 필요한 질문을 하라.
- 문제의 단위를 찾아라. 단어·문장 리듬의 문제인지, 문단 연결·도입 설계·정보 배치·글의 범위 문제인지 구분하라. 문단의 배경이 빠져 어색한데 접속어나 말끝만 바꾸는 식으로 대응하지 마라.
- 요청된 부분과 연결된 예고·참조·마무리까지 고쳐라. 같은 문제가 원고의 다른 부분에도 있는지 확인하되, 부분 수정 요청을 이유로 글 전체의 관점과 구성을 새로 정하지 마라.

## 적용 범위를 나누어 기록하라

| 교정의 성격 | 반영할 곳 | 구분 기준 |
| --- | --- | --- |
| 사실·오탈자·표기 수정 | 원고와 필요한 근거 기록 | 날짜 한 번을 고친 것으로 문체 선호를 만들지 않음 |
| 이번 글의 선택 | 현재 작업의 구성·검토 메모 | “이번 글은 짧게”를 모든 글의 분량 제한으로 넓히지 않음 |
| 저자·블로그의 지속 선호 | 해당 저자·프로젝트의 작성 기준 | 도입 흐름, 설명 깊이, 말투처럼 다음 글에서도 사용할 선호. 글 종류·적용 조건을 함께 남김 |
| 공용 스킬의 판단 누락 | 요청 범위에 포함된 스킬 원본 | 특정 도입 형식을 강제하는 대신, 기존 저자 선호를 읽고 수정 이유를 분석하는 절차를 보완 |

명시적인 “앞으로도” 요청은 한 번이어도 지속 선호로 반영할 수 있다. 반복된 교정에서 추정한 선호는 잠정 상태로 남겨라. 작업 대화의 개조식 선호를 블로그 본문 문체로 옮기지 마라. 예시 속 오탈자와 미확인 경험·동향을 선호나 검증된 사실로 받아들이지 마라.

## 다음 작성에서 찾을 수 있게 저장하라

- 기존 저자·프로젝트 작성 기준을 먼저 사용하라. 여러 저자가 쓰면 대상 저자를 명시해 다른 사람의 기준과 섞지 마라. 같은 선호를 별도 상태 파일 여러 개에 복제하지 마라.
- 기존 기준 파일이 없으면 프로젝트의 작업 문서 규약에 맞는 위치를 정하라. 지속 기준에 아직 반영할 수 없으면 현재 작업의 `notes/author-preferences.md` 같은 로컬 메모에 임시 보존하고, 인계 문서에 경로와 미반영 범위를 연결하라. 다른 도구의 루트 `STATUS.md`를 덮어쓰지 마라.
- 기록은 **선호와 이유, 저자·적용 조건, 명시적 요청인지 추정인지, 근거가 된 요청의 위치**를 찾을 수 있을 만큼만 남겨라. 구분에 도움이 되면 짧은 수정 전후 예를 더하되, 작은 교정마다 별도 문서나 긴 분석 보고서를 만들지 마라.
- 새 교정은 관련 항목을 갱신하라. 이번 글의 예외는 예외로 두고, 지속 선호가 바뀌었으면 낡은 지시를 활성 규칙으로 중복 유지하지 마라. 해석이 잘못됐다고 확인되면 추정도 폐기하라.
- 다음 글·다음 세션에서는 해당 기준의 관련 부분을 읽고 초안과 전달 전 검토에 적용하라. 이미 답을 받은 취향을 다시 인터뷰하지 마라. 기준이 현재 글의 목적과 충돌하면 현재 지시를 우선하고, 판단에 필요한 차이만 확인하라.
- 파일을 쓸 수 없으면 변경안과 반영하지 못한 범위를 전달하라. 대화 밖에 저장하지 않았는데 다음 세션에서도 기억한다고 말하지 마라. 다른 환경으로 옮길 때는 기준 파일과 진입점의 연결도 함께 옮겨야 한다.

다음은 기록 방식의 예시이며 기본 문체 규칙이 아니다.

> 저자 A / 경험 중심 회고의 도입 / 명시적 선호: 주제와 관련된 관찰에서 저자의 생각·선택으로 이어간 뒤 글을 쓰는 이유를 설명한다. 갑작스러운 참가 사실로 시작하면 독자가 맥락을 잡기 어렵다는 교정에서 나왔다. 고정 인사말이나 문단 수는 요구하지 않는다. 근거: 해당 작업의 도입 리뷰.

## 공용 스킬 개선과 개인화를 구분하라

사용자의 수정 요청마다 원고 반영과 필요한 선호 기록을 수행하라. 공용 스킬 원본의 수정은 별도로 요청받은 범위에서 수행하라. 사용자가 지속 개선을 요청했다면 그 범위 안의 개선마다 같은 허락을 되묻지 마라. 다만 저자 개인의 취향을 다른 사용자에게 강제하는 변경으로 확대하지 마라.

공용 스킬을 고칠 때는 원본 저장소와 그 설계·검증 절차를 따르고, 설치된 플러그인 캐시를 직접 고치지 마라. 원본에 접근할 수 없으면 적용 가능한 변경안을 남겨라. 수정 요청 자체를 커밋·푸시·배포 승인으로 해석하지 마라.

공개 스킬에는 일반화한 판단 기준만 넣고 비공개 원고·메일·프로젝트 자료를 사례로 복사하지 마라. 개인 선호를 공개 저장소에 넣어야 한다면 공개할 범위를 확인하라. 사용자에게는 핵심 수정 이유와 다음에도 적용할 기준만 짧게 설명하고, 분석 메모를 블로그 본문에 삽입하지 마라.

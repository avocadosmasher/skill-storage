# 구조: 유즈케이스 흐름 (use-case flow)

입력 하나가 시스템의 처리 단계를 차례로 지나 결과물이 되는 과정을 보여 주는 시연 구조. 사용자가 자주 쓸 기본 구조다(2026-11-24 한 PoC의 공모전 데모로 확정: 지원 티켓 하나가 가리기 → 정리 → 근거 검증 → 노트로 가는 3분 37초 영상). 뼈대 시나리오: `assets/scenarios/template-usecase-flow.mjs`.

## 언제 쓰나

- "요청이 들어와 → 몇 단계를 거쳐 → 결과가 나온다"로 설명되는 제품(에이전트, 파이프라인, 자동화, 승인 흐름)
- 아키텍처 그림의 단계를 화면과 연결해 보여 주고 싶을 때
- 맞지 않는 경우: 기능 여러 개를 나란히 소개(기능 투어), 화면 하나를 깊게(튜토리얼). 그때는 장면을 기능별로 나누고 흐름 띠를 쓰지 않거나, 새 구조 문서를 이 폴더에 더한다

## 뼈대

| 순서 | 장면 | 화면 예 | 흐름 띠 | 핵심 |
| --- | --- | --- | --- | --- |
| 0 | `intro` 카드 | | 전체 켬 | 제목 한 줄: "입력 하나가 결과가 되기까지", "모든 값은 가상" |
| 1 | 입력 | 고객 포털·양식 | 첫 단계 | 실제로 입력하는 모습. 되돌릴 수 없는 제출은 `dryRun:"skip"` + 새 값 `capture` |
| 2 | 받기·처리 대기 | 처리 기록 목록 | 받기 단계 | `wait`(`cut`) + `sweep`으로 단계가 차례로 켜짐 + `${since:제출 단계}` 걸린 시간 자막 |
| 3…n | 처리 단계마다 | 그 단계의 흔적이 남는 화면 | 그 단계(지나온 단계는 자동으로 옅게) | 흐름 순서 그대로. 한 화면에 여러 단계가 순서대로 있으면 위에서 아래로, 자막에 단계 번호 |
| n+1 | 결과물 | 사용자가 실제로 받는 화면 | 마지막 단계 | 이야기의 끝. 결과에서 앞 장면(상세)으로 가는 길도 짚어 줌 |
| n+2 | 운영 도구 (선택) | 설정·사전·기록 화면 | `active: [], done: "all"` | 흐름 밖. 둘러보기만, 저장·삭제 없음 |
| 끝 | `outro` 카드 | | 전체 켬 | 사용자에게 남길 한 문장 |

## 만드는 순서

1. 아키텍처 단계 이름을 `flow.stages`에 왼쪽→오른쪽으로 적는다(9개 안팎, 한 칸 6자 안팎). 서비스 안 단계는 `numbered`·`span`·`note`로 묶는다
2. 단계마다 "그 단계가 남긴 흔적이 보이는 화면"을 찾는다. 흔적이 한 화면에 순서대로 모여 있으면 그 화면을 한 장면으로 쓴다
3. 장면 순서를 흐름 순서로 고정한다. 화면 사이를 링크로 못 가면 `capture.fetch`로 주소를 읽어 `goto`
4. 장면 첫 단계에 `bridge` (`kicker: "장면 N"`, `title: "<번호> <단계>: <한 줄>"`, `sub`, `active`)
5. 자막은 단계 번호로 시작하면 흐름 띠와 이어진다("2 정보 정리: …")
6. `validate` → `dry`(되돌릴 수 없는 단계 건너뜀, 필요한 변수는 `--var`) → `preview` 경고 없음 확인 → 사용자 확인 → `record` → `transitions`·`preview` → `render`
7. 길이 목표: 3~4분(5분 안). 카드 3초 × (장면 수 + 2), 자막 단계 평균 4~5초로 어림한다

## 체크리스트 (보여 주기 전)

- [ ] 흐름 띠의 진한 주황이 장면마다 오른쪽으로만 움직이는가
- [ ] `preview`/`render`에 `경고:`가 없는가 (자막 2초 미만, 5분 초과)
- [ ] 첫 장면 전, 탭 전환 직후에 이전 화면·빈 화면이 1초 넘게 남지 않는가 (영상에서 카드 앞뒤를 뽑아 본다)
- [ ] `transitions.png`에서 실명·이메일·아바타가 모두 흐린가, 출력 파일에 실명 0건인가
- [ ] 걸린 시간 자막이 녹화 중 잰 값(또는 출처를 밝힌 값)인가
